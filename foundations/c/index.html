3.1 指针与数组:数组名会退化,指针加法按元素大小走 principle

数组在内存里是一段连续的元素;指针保存的是地址。int a[4] 的 a 在表达式里几乎总是"首元素地址"。

int a[4] = {3, 6, 9, 12};   /* 假设 int 占 4 字节,起始地址 0x1000 */

  p = a          p = a + 1        p = a + 3
    |               |                |
    v               v                v
+-------+-------+-------+-------+
|   3   |   6   |   9   |  12   |   每格 4 字节
+-------+-------+-------+-------+
  a[0]    a[1]    a[2]    a[3]
 0x1000  0x1004  0x1008  0x100C     地址为示意,不是本机真实地址
规则写法含义
数组名退化a == &a[0]在表达式中 a 代表首元素地址,不是整个数组
指针加法p + 1前进 sizeof(*p) 字节;int 指针一次走 4 字节,不是 1 字节
下标等价p[i] == *(p + i)p[-1] 也合法,等于 *(p - 1),只要没走出数组范围
指针相减p - a得到元素个数(不是字节数),类型是 ptrdiff_t
元素个数sizeof(a) / sizeof(a[0])只在数组定义所在作用域成立;传进函数后 a 退化成指针,sizeof(a) 变成 8(64 位)
易错点:&a 的数值和 a 相同,但类型是 int (*)[4]:&a + 1 前进 16 字节(整个数组),而 a + 1 前进 4 字节。写代码时先问"这个 +1 是按什么单位走的"。

3.2 位操作:置位 / 清零 / 翻转 / 读取 principle

嵌入式里最常见的动作是"只改一个寄存器的某一位,别动其他位"。四种基本操作都基于位掩码(mask)。

目的写法(设 n 为位号,0 起)解释
置位(0→1)x |= (1u << n);OR 0 不变、OR 1 置 1;其他位保持
清零(1→0)x &= ~(1u << n);AND 1 不变、AND 0 清零;先取反得到"只有第 n 位是 0"的掩码
翻转x ^= (1u << n);XOR 1 翻转、XOR 0 不变
读取(x >> n) & 1u把第 n 位移到最低位,再用 1 掩掉其他位
取一段(x >> n) & 0x0F取从第 n 位起的 4 位(字段)
写回一段x = (x & ~(0x0Fu << n)) | (v << n);先清字段再或上新值,不破坏相邻位
为什么写 1u:有符号 int 左移进入符号位是未定义行为;用无符号的 1u、并让掩码变量用 uint8_t / uint32_t,行为才是可移植的。清零时 ~(1u << n) 的高位是全 1,配合无符号变量才安全。

假设一个控制寄存器的位定义是:bit3 = ENABLE,bit1 = IRQ,bit0 = START。对应的三种写法:

ctrl |=  (1u << 3);   /* 打开使能,其他位不动 */
ctrl &= ~(1u << 1);   /* 关闭中断 */
ctrl ^=  (1u << 0);   /* 翻转启动位 */

这一段是原理说明;真实运行结果见「操作实验 · 实验 01」,那里对 uint8_t ctrl 逐步打印了二进制与十进制值。

3.3 编译链接四阶段:预处理 → 编译 → 汇编 → 链接 principle

一条 gcc main.c -o app 背后其实有四个阶段。拆开看,每一步都有明确的输入与产物。

main.c源码
→
gcc -Emain.i 预处理
→
gcc -Smain.s 编译
→
gcc -cmain.o 汇编
→
gcc 链接app 链接
阶段命令产物做了什么
预处理gcc -E main.c -o main.i.i(纯 C 文本)展开 #include、替换 #define、处理条件编译
编译gcc -S main.c -o main.s.s(汇编文本)语法/类型检查,生成目标平台汇编
汇编gcc -c main.c -o main.o.o(ELF 可重定位文件)把汇编翻译成机器码 + 符号表,还不能运行
链接gcc main.o sensor.o -o appapp(ELF 可执行文件)合并多个 .o,解析外部符号,补上启动代码与库
头文件不是独立编译单元:#include "sensor.h" 只是把文件内容原样粘进 .c。所以 gcc -c main.c 能找到同目录的 sensor.h,但换到别的目录编译就会报 fatal error: sensor.h: No such file or directory。
符号怎么解析:main.o 里调用了 sensor_pack,但定义不在这个文件里,nm 把它标成 U(undefined);链接器在 sensor.o 里找到 T sensor_pack(代码段定义),把地址填进去。少给一个 .o,链接就报 undefined reference。

Git 的核心不是"上传代码",而是把改动拆成一个个可以回看的提交。三个区各自承担不同职责。

→ git commit →

→ git push →
远端(可选)备份/协作
动作命令要点

3.5 调试:printf 插桩 vs gdb 断点 principle

两条路线各有适用场景,先用 printf 快速缩小范围,再用 gdb 看现场。

路线做法优点代价
printf 插桩在关键分支打印变量与状态,必要时 fflush(stdout)零学习成本,能快速验证假设要改代码;崩溃时可能丢输出
gdbgcc -g -O0 编译,gdb 下断点、单步、打印变量、看调用栈不改代码就能看现场、能定位崩溃行需要记住命令;优化后变量可能被优化掉
gdb 命令作用
break crash.c:26在指定文件行下断点(也可写函数名 break main)
run启动程序,直到断点或信号
bt打印调用栈,崩溃时第一行就是出错位置
p 变量打印变量值,例如 p bad、p ring.buf
info locals打印当前帧所有局部变量
next / step单步(不进入函数 / 进入函数)
continue / quit继续到下一个断点 / 退出
最容易被误判的坑:程序崩溃前 printf 一行都没打印,不代表没执行。stdout 接终端时是行缓冲,接管道/文件时是全缓冲;进程被 SIGSEGV 终止时缓冲区来不及刷新,输出就丢了。用 stdbuf -o0 ./app、fflush(stdout) 或直接写 stderr 就能看见。实测记录见实验 03。

LAB 01

指针与位操作:把每一步打印出来

compiled · gcc 13.3.0

目标:亲手看到置位/清零/翻转对 8 位变量的影响,以及指针偏移、数组名退化、指针相减的真实数值。

  1. 建目录,准备一个干净的工作区。
    终端
    $ mkdir -p /tmp/c-course-lab/build
$ cd /tmp/c-course-lab
  2. 把下面的程序保存为 bitops.c。
    bitops.c保存到 /tmp/c-course-lab/bitops.c
    #include <stdio.h>
#include <stdint.h>

static void show(const char *tag, uint8_t v)
{
    printf("%-14s0b", tag);
    for (int i = 7; i >= 0; --i) {
        putchar(((v >> i) & 1u) ? '1' : '0');
    }
    printf("  0x%02X  %3u\n", v, v);
}

int main(void)
{
    uint8_t ctrl = 0x12; /* 0b0001_0010 */

    show("start", ctrl);
    printf("bit3=%u bit1=%u\n", (unsigned)((ctrl >> 3) & 1u), (unsigned)((ctrl >> 1) & 1u));

    ctrl |= (uint8_t)(1u << 3);   /* 置位:bit3 = 1 */
    show("set bit3", ctrl);

    ctrl &= (uint8_t)~(1u << 1);  /* 清零:bit1 = 0 */
    show("clear bit1", ctrl);

    ctrl ^= (uint8_t)(1u << 3);   /* 翻转:bit3 取反 */
    show("toggle bit3", ctrl);

    int a[4] = {3, 6, 9, 12};
    int *p = a;                   /* 数组名退化为首元素地址 */
    printf("a[0]=%d *(a+2)=%d p[3]=%d\n", a[0], *(a + 2), p[3]);

    p = a + 1;                    /* 指针 +1 = 前进一个 int(4 字节) */
    printf("*p=%d *(p+2)=%d p-a=%ld sizeof(int)=%zu\n",
           *p, *(p + 2), (long)(p - a), sizeof(int));

    int sum = 0;
    for (int *q = a; q < a + 4; ++q) {
        sum += *q;
    }
    printf("sum=%d\n", sum);
    return 0;
}
  3. 编译并运行。开启 -Wall -Wextra,让常见错误在编译期暴露。
    终端
    $ gcc -Wall -Wextra -std=c11 -O2 -o build/demo bitops.c
$ ./build/demo
  4. 预期输出(以下为本机真实输出,不是示意):
    实际输出 · gcc 13.3.0 · 2026-11-27
    start         0b00010010  0x12   18
bit3=0 bit1=1
set bit3      0b00011010  0x1A   26
clear bit1    0b00011000  0x18   24
toggle bit3   0b00010000  0x10   16
a[0]=3 *(a+2)=9 p[3]=12
*p=6 *(p+2)=12 p-a=1 sizeof(int)=4
sum=30

逐行看什么

  • start:初值 0x12 = 0b0001_0010 = 18。
  • set bit3:OR 上 bit3,值从 0x12 变 0x1A,其他位不动。
  • clear bit1:AND 取反掩码,0x1A 变 0x18;bit3 仍然是 1。
  • toggle bit3:XOR 翻转 bit3,0x18 变 0x10。
  • p[3] 和 *(a+2):下标与指针偏移等价。
  • p-a=1:指针相减得到"相隔几个元素",不是字节数;sizeof(int)=4 解释了为什么 1 个元素 = 4 字节。
  • sum=30:3+6+9+12=30,指针遍历数组的常见写法。

读代码写结果(指针 + 位操作)

先不要运行,把每一步的结果写在纸上,再展开答案核对。

uint8_t s = 0x09;          /* 0b0000_1001 */
s |= (uint8_t)(1u << 2);   /* ① 之后 s = ? */
s &= (uint8_t)~(1u << 0);  /* ② 之后 s = ? */
s ^= (uint8_t)(1u << 3);   /* ③ 之后 s = ? */

int a[4] = {3, 6, 9, 12};
int *p = a + 1;
printf("%d %d\n", *p, *(p + 2));   /* ④ 输出? */
展开答案与推导
  • ① 置位 bit2:0b0000_1001 | 0b0000_0100 = 0b0000_1101 = 0x0D(13)。
  • ② 清零 bit0:0b0000_1101 & 0b1111_1110 = 0b0000_1100 = 0x0C(12)。
  • ③ 翻转 bit3:0b0000_1100 ^ 0b0000_1000 = 0b0000_0100 = 0x04(4)。
  • ④ p = a + 1 指向 a[1] = 6;*(p + 2) = a[3] = 12;输出 6 12。
LAB 02

编译链接四阶段:两个 .o 才能链接成程序

compiled · gcc 13.3.0

目标:分别执行预处理、编译、汇编、链接,亲眼看四类产物;故意只链接 main.o,读懂 undefined reference 报错,再用 nm 找到原因并修好。

准备三个文件(同一目录 /tmp/c-course-lab):

sensor.h
#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

/* 把 12 位原始值(0..4095)线性映射到 0..255 */
uint8_t sensor_scale(uint16_t raw);

/* 低 8 位放数值,bit8 放"超出量程"标志 */
uint16_t sensor_pack(uint16_t raw);

#endif
sensor.c
#include "sensor.h"

uint8_t sensor_scale(uint16_t raw)
{
    if (raw > 4095u) {
        raw = 4095u;
    }
    return (uint8_t)((raw * 255u + 2047u) / 4095u);
}

uint16_t sensor_pack(uint16_t raw)
{
    uint16_t v = sensor_scale(raw);

    if (raw > 4095u) {
        v |= (uint16_t)(1u << 8);
    }
    return v;
}
main.c
#include <stdio.h>
#include "sensor.h"

int main(void)
{
    const uint16_t raw[] = {0, 512, 2048, 4095, 5000};

    for (unsigned i = 0; i < sizeof(raw) / sizeof(raw[0]); ++i) {
        uint16_t packed = sensor_pack(raw[i]);
        printf("raw=%4u scale=%3u overflow=%u packed=0x%04X\n",
               raw[i],
               (unsigned)(packed & 0xFFu),
               (unsigned)((packed >> 8) & 1u),
               (unsigned)packed);
    }
    return 0;
}

第 4 步:故意只链接 main.o(预期失败)

终端
$ gcc build/main.o -o build/app
/usr/bin/ld: build/main.o: in function `main':
main.c:(.text+0x50): undefined reference to `sensor_pack'
collect2: error: ld returned 1 exit status

这个报错来自链接器 ld,不是编译器:main.o 里对 sensor_pack 的调用只有一个符号名,没有函数体。用 nm 检查:

终端

实际输出
0000000000000000 T main
                 U printf
                 U sensor_pack
                 U __stack_chk_fail

T = 本文件定义的代码(main);U = 未定义、需要链接时由别处提供(printf 来自 libc,sensor_pack 来自 sensor.o,__stack_chk_fail 来自 libc 的栈保护支持)。

LAB 03

用 gdb 抓住段错误:从 139 到 crash.c:26

compiled · gcc 13.3.0 · gdb 15.1

目标:制造一次确定的段错误,理解退出码 139、stdout 缓冲陷阱,并用 gdb 得到出错文件、行号与变量值。

crash.c保存到 /tmp/c-course-lab/crash.c
#include <stdio.h>

struct ring {
    int buf[4];
    int head;
};

static void ring_push(struct ring *r, int v)
{
    r->buf[r->head] = v;
    r->head = (r->head + 1) % 4;
}

int main(void)
{
    struct ring ring = {{0}, 0};

    for (int i = 0; i < 6; ++i) {
        ring_push(&ring, i * 10);
    }
    printf("head=%d buf=[%d %d %d %d]\n",
           ring.head, ring.buf[0], ring.buf[1], ring.buf[2], ring.buf[3]);

    struct ring *bad = NULL;
    printf("about to deref NULL\n");
    bad->head = 1; /* 故意制造段错误,给 gdb 演示用 */

    return 0;
}

第 1 步:带调试信息编译并直接运行

终端
$ gcc -g -O0 -Wall -Wextra -std=c11 crash.c -o build/crash
$ ./build/crash
$ echo $?
实际输出
段错误(核心已转储)
139

"段错误(核心已转储)"是 shell 在中文 locale 下打印的;英文 locale 下是 Segmentation fault (core dumped)。退出码 139 = 128 + 11,11 是 SIGSEGV 的信号编号。注意:程序里两行 printf 一个字都没出现——不是没执行,见下一步。

第 2 步:关掉 stdout 缓冲,同样的程序就能看到输出

终端
$ stdbuf -o0 ./build/crash
$ echo $?
实际输出
head=2 buf=[40 50 20 30]
about to deref NULL
段错误(核心已转储)
139

结论:程序确实执行到了 printf。输出被重定向时 stdout 是全缓冲,进程被信号杀死时缓冲区没有刷新,所以直接运行时看不到。调试崩溃程序时,这一点经常让人误判"根本没走到这里"。

第 3 步:gdb 直接定位崩溃行

终端
$ gdb -q -batch -ex 'run' -ex 'bt' -ex 'p bad' ./build/crash
实际输出(地址随运行环境变化,行号稳定)
[Thread debugging using libthread_db enabled]
Using host libthread_db library "/lib/x86_64-linux-gnu/libthread_db.so.1".

Program received signal SIGSEGV, Segmentation fault.
0x000055555555526c in main () at crash.c:26
26	    bad->head = 1; /* 故意制造段错误,给 gdb 演示用 */
#0  0x000055555555526c in main () at crash.c:26
$1 = (struct ring *) 0x0

gdb 直接给出三件事:信号类型(SIGSEGV)、出错文件行号(crash.c:26)、可疑变量(bad = 0x0)。没有 gdb 时,你只有"段错误"三个字和退出码 139。

第 4 步:在崩溃前下断点,看现场

终端
$ gdb -q -batch -ex 'break crash.c:26' -ex 'run' -ex 'p ring.head' -ex 'p ring.buf' -ex 'p bad' ./build/crash
实际输出(断点地址随构建变化)
Breakpoint 1 at 0x1268: file crash.c, line 26.
[Thread debugging using libthread_db enabled]
Using host libthread_db library "/lib/x86_64-linux-gnu/libthread_db.so.1".

Breakpoint 1, main () at crash.c:26
26	    bad->head = 1; /* 故意制造段错误,给 gdb 演示用 */
$1 = 2
$2 = {40, 50, 20, 30}
$3 = (struct ring *) 0x0

读结果:6 次 ring_push 后 head=2,缓冲区被覆盖成 {40, 50, 20, 30}(环形缓冲写满后从头覆盖);bad 是空指针,下一行解引用必然崩溃。这类"程序逻辑本身没崩,空指针才崩"的情况,正是 gdb 比 printf 更快的地方。

06

故障排查

principle 条目来自真实操作记录与 gcc 13.3.0 实际报错;每条按"现象 → 检查步骤 → 预期结果 → 下一分支"组织

1. 编译报错 fatal error: sensor.h: 没有那个文件或目录

现象
main.c:2:10: fatal error: sensor.h: 没有那个文件或目录,随后 compilation terminated.,退出码 1。
检查步骤
① 看 #include "sensor.h" 是引号还是尖括号;② ls 确认 sensor.h 与 main.c 在同一个目录;③ 确认当前编译的是哪个 main.c(是不是把文件复制到了别的目录);④ 需要跨目录时用 -I 目录。
预期结果
在正确目录执行 gcc -c main.c -o build/main.o 没有任何输出、退出码 0,ls build/main.o 能看到文件。
下一分支
若文件确实存在仍报错,检查文件名大小写(Windows 拷来的文件常是 Sensor.h)与是否误存成 sensor.h.txt;仍不行就把头文件与 .c 放进同一目录重试。

2. 链接报错 undefined reference to `sensor_pack'

现象
/usr/bin/ld: build/main.o: in function `main': + undefined reference to `sensor_pack' + collect2: error: ld returned 1 exit status。
检查步骤
① nm build/main.o 看 sensor_pack 是否为 U;② 确认 sensor.c 是否已经用 gcc -c 生成 sensor.o;③ 确认链接命令里是否真的写上了 build/sensor.o。
预期结果
nm build/main.o 显示 U sensor_pack(需要外部提供);链接命令改为 gcc build/main.o build/sensor.o -o build/app 后无输出、退出码 0。
下一分支
补上 sensor.o 后仍报错:检查 sensor.c 里的函数名拼写是否与声明一致,以及是否漏了 #include "sensor.h" 导致定义被写成另一个名字。

3. 程序段错误,但崩溃前的 printf 一行都没出现

现象
./build/crash 只显示 段错误(核心已转储),退出码 139;程序里的 printf 输出全部消失。
检查步骤
① 确认 stdout 是否接终端还是被管道/文件重定向;② 用 stdbuf -o0 ./build/crash 重跑;③ 在关键 printf 后加 fflush(stdout); 或改用 fprintf(stderr, ...)。
预期结果
用 stdbuf -o0 后能看到 head=2 buf=[40 50 20 30] 与 about to deref NULL,证明 printf 确实执行过。
下一分支
若仍无输出,程序可能连 main 都没进(动态库加载失败等);用 gdb ./build/crash 后 run 看最早停在哪里。

4. 编译警告 format `%u' expects argument of type `unsigned int'

现象
warning: format `%u' expects argument of type `unsigned int', but argument 2 has type `long int' [-Wformat=],并附带 %lu 提示。
检查步骤
① 对照 printf 格式符与变量真实类型;② 确认是否用 unsigned 强转或换格式符;③ 保持 -Wall -Wextra 编译,不要关警告。
预期结果
修正后 gcc -Wall -Wextra 零警告(退出码 0、无 warning 输出)。
下一分支
类型较多时统一用 stdint.h 的 uint32_t + PRIu32,或先强转成 (unsigned) 再交给 %u,不要靠"碰巧能跑"。

5. gdb 只显示地址,没有 crash.c:26 行号

现象
0x00005555555550f2 in main (),bt 也只有 #0 0x... in main (),没有源文件名和行号。
检查步骤
① 确认编译时是否加了 -g;② 确认是否加了 -O0(优化会重排/删掉变量);③ 重新编译后再在 gdb 里 run、bt。
预期结果
带 -g -O0 重编译后,bt 显示 in main () at crash.c:26,p bad 显示 (struct ring *) 0x0。
下一分支
若加了 -g 仍无行号,检查是否运行了旧的二进制(路径写错),ls -l build/crash 确认时间戳后重新编译。

6. Git 提交报"作者身份未知 / 无法自动探测邮件地址"

现象
作者身份未知 + fatal: 无法自动探测邮件地址(得到 'czy@czy.(none)'),退出码 128。
检查步骤
① git config user.name 与 git config user.email 是否为空;② 新机器/新容器上是否从未配置过;③ 本仓库内配置即可,不必全局。
预期结果
git config user.name "C Course Lab" 与 git config user.email "lab@example.com" 之后,git commit 成功,git log --oneline 出现提交。
下一分支
若多人共用机器,用 git config --global 配个人身份,避免覆盖别人的提交者信息;CI 环境用 GIT_AUTHOR_NAME 等环境变量显式指定。
