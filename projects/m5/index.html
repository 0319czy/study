M5 交付:让别人能复现你的系统

交付不是"把代码发过去",而是让别人按文档能复现、能检查、能排障。本页给出交付包结构、自检清单和常见缺失; 完成自检后,你的 M0–M4 才算真正交付。

前置:M0 采集 · M1 通信 · M2 多任务 · M3 网关 · M4 展示

1. 目标与成果

项内容
能力交付一套可部署、可维护的设备系统:材料齐全、步骤可复现、结果可检查、故障有排查
可检查结果别人按你的文档从零复现;每个阶段有证据标识;交付自检 10/10 通过
证据标识principle · compiled · hardware-pending(实物验证由你完成)

2. 前置知识

需要会用在哪去哪补
M0–M4 全链路交付内容就是这条链路的证据项目总览
Git 与版本源码版本、证据版本C 与工程工具
排障方法故障排查表的"现象—检查—预期—下一分支"工具与资料

3. 原理与图示:交付包结构

sensor-monitor/ ├── README.md # 一页看懂:是什么、怎么跑、验收点 ├── hardware/ # 接线图、BOM、电平说明 │ ├── wiring.svg / .png │ └── bom.csv # 型号、数量、备注 ├── firmware/ # STM32 工程(M2 多任务) │ ├── Core/ … │ └── README.md # 版本、工具链、烧录步骤 ├── gateway/ # Linux 网关(M3) │ ├── serial_reader.c │ ├── store.py │ └── systemd/*.service ├── dashboard/ # 仪表盘(M4) │ └── index.html ├── docs/ │ ├── protocol.md # M1 帧格式与错误码 │ ├── test-record.md # 测试记录:时间/环境/结果 │ └── troubleshooting.md # 现象—检查—预期—下一分支 └── evidence/ # 证据:截图、日志、串口抓包

关键:README 是入口,不是附属品;每份证据要写清"证明了什么、没证明什么"。

4. 操作实验:交付自检

交付自检清单(10 项)

已完成 0 / 10

自检未满 10 项不要宣称"交付完成";缺一项就写进"待办",不要用"基本完成"糊过去。

5. 结果检查

检查项通过标准
可复现另一台机器按 README 能跑通最小链路(采样→网关→仪表盘)
可检查每个阶段有"预期输出"与实测对照
可排障至少 5 条故障有明确检查步骤与分支
可维护版本、日志、配置、数据保留策略写清楚

6. 故障排查

现象检查步骤预期结果下一分支
别人复现失败让他在干净环境按 README 逐步执行并记录卡住的位置能定位到某一步补步骤/补依赖/补截图
版本对不上核对 README/firmware/gateway 的版本号与证据时间版本一致固定版本并重新出证据
日志缺失检查日志路径、权限、轮转策略日志能按时间查补 systemd 日志与保留策略
接线图与实物不符对照 BOM 与实物照片逐针核对针脚/电平一致重画接线图并标版本
