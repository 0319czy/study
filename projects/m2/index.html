PROJECT M2 · 多任务

M2 多任务:让采集、通信、心跳互不阻塞

在 M0 的采集与 M1 的帧协议之上,把单循环拆成三个 FreeRTOS 任务:采集每 10ms、通信每 20ms、心跳每 500ms; 用队列解耦"生产"与"消费",用优先级与阻塞保证截止时间,用看门狗兜住最坏情况。 本页的时序图与统计全部由页内模拟器实时计算,不依赖任何外部资源。

证据标识:principle 原理与标准做法 · simulated 页内模拟计算 · hardware-pending 需你在开发板上实测

2.1 本页用到的几个词

词在这套设备里的含义
tickFreeRTOS 的系统节拍。configTICK_RATE_HZ = 1000 时 1 tick = 1ms,所以 10 / 20 / 500ms 都能被整 tick 表示。
抢占更高优先级任务一旦就绪,立刻打断当前任务(同一时刻只有一个任务在跑)。
截止时间本页取"释放时刻 + 周期":周期任务必须在本周期结束前完成,否则算一次超期(deadline miss)。
队列任务间传递数据的唯一通道;采集只管放,通信只管取,两边不直接调用对方。
阻塞任务主动让出 CPU 并进入 Blocked,等事件(数据到达、超时)再被唤醒;不占 CPU。
看门狗独立看门狗 IWDG,超时 500ms 未喂狗就复位芯片;本页的设计是"采集任务活着才喂狗"。

3/8 原理与图示

先看清三个任务如何分工、数据怎么流动,再谈调度与最坏情况。

3.1 任务划分:周期、优先级、栈、阻塞点

任务周期优先级栈职责允许的阻塞点
采集 acq10ms3(最高)512 wordADC 采样、换算、组帧、xQueueSend(…, 0)只允许 vTaskDelayUntil;入队不等待
通信 comm20ms2768 wordxQueueReceive(…, 0) 取空、打包、UART 发送、500ms 链路超时判定UART 发送超时 ≤ 10ms
心跳 hb500ms1(最低)256 word发 CMD 0x02 心跳帧,刷新网关侧存活计时只允许 vTaskDelayUntil

优先级按"周期越短、优先级越高"(Rate Monotonic)排。采集是数据源头,它被拖慢会连锁影响队列与心跳; 但它执行只有 2ms,占空比 20%,不会饿死别人。这不是唯一正确的排法,但必须能解释你的排法。

3.4 优先级与抢占:先看截止时间,再看利用率

固定优先级抢占式调度下,CPU 永远给"就绪任务里优先级最高的那个"。周期越短的任务截止时间越紧, 所以按周期从短到长分配优先级(Rate Monotonic)。对 n 个周期任务,利用率 U = Σ(Ci / Ti);当 U ≤ n(2^(1/n) − 1) 时一定可调度(n=3 时上界约 77.98%)。 超过上界不代表一定失败,但必须靠实测确认。

配置采集通信心跳U结论
本页基线3/105/201/50055.2%≤ 77.98%,0 超期
通信耗时 16ms3/1016/201/500110.2%> 100%,处理器过载,必然超期
抢占的两个副作用:① 高优先级任务会把低优先级任务切成碎片,低优先级任务的实际完成时间取决于"剩下的空档"; ② 同优先级任务按时间片轮转,不要依赖同优先级之间的先后顺序。

3.5 阻塞与优先级反转

阻塞是"把 CPU 让出去等事件":队列空时通信任务 xQueueReceive(portMAX_DELAY) 进入 Blocked, 数据一到立刻被唤醒。忙等(while (!ready) {})则相反:任务一直 Ready,CPU 空转,优先级的坏处被放大。

图 2:优先级反转的三个角色:低优先级持锁、中优先级抢占、高优先级等锁。修法:B 用互斥量(优先级继承)+ 缩短临界区。

手段能解决什么不能解决什么
用 xSemaphoreCreateMutex()持锁者被中优先级抢占时临时提升优先级,缩短高优先级任务的等待持锁时间本身很长、锁里做阻塞 I/O
临界区只包必要操作缩短等待上界,让最坏情况可计算设计上的锁竞争(多个任务抢同一总线)
高优先级任务不等低优先级从结构上消除反转必须共享外设时的互斥需求

3.6 看门狗:喂狗要证明"系统真的在跑"

IWDG 由独立时钟驱动,一旦开启就不能关。本设计把喂狗放在采集任务里:采集每 10ms 跑完一轮才 HAL_IWDG_Refresh, 因此"采集被饿死/卡死"会在 500ms 内变成一次确定的复位,而不是永远卡住。更严格的做法是"多任务计数 + 监控任务检查全部计数都在动,才喂狗", 避免只证明某一个任务活着。

3.7 代码骨架(STM32 HAL + FreeRTOS,principle)

/* ---- 句柄与帧结构:队列深度 8,元素是整帧,不做零拷贝 ---- */
static TaskHandle_t  hAcq, hComm, hHb;
static QueueHandle_t qFrame;

typedef struct {
    uint16_t temp_centi;      /* 温度 ×100,2345 = 23.45℃ */
    uint16_t humi_centi;      /* 湿度 ×100 */
    uint8_t  seq;
} frame_t;

/* ---- 采集任务:10ms,优先级 3 ---- */
static void task_acq(void *arg)
{
    TickType_t last = xTaskGetTickCount();
    frame_t f;

    for (;;) {
        f.temp_centi = sensor_read_temp_centi();   /* HAL_ADC 采样 + 换算,见 M0 */
        f.humi_centi = sensor_read_humi_centi();
        f.seq        = seq_next();

        /* 队列满时绝不阻塞:采集是数据源头,阻塞会连锁拖垮通信与心跳 */
        if (xQueueSend(qFrame, &f, 0) != pdPASS) {
            g_drop_frames++;                        /* 丢帧计数,诊断页显示 */
        }

        HAL_IWDG_Refresh(&hiwdg);                   /* 真正跑完一轮才喂狗 */

        /* 固定周期:按绝对时刻唤醒,避免 vTaskDelay(10) 的累积漂移 */
        vTaskDelayUntil(&last, pdMS_TO_TICKS(10));
    }
}

/* ---- 通信任务:20ms,优先级 2 ---- */
static void task_comm(void *arg)
{
    TickType_t last = xTaskGetTickCount();
    frame_t f;

    for (;;) {
        /* 把本周期能取到的帧发完,取空就返回;不在队列上阻塞 */
        while (xQueueReceive(qFrame, &f, 0) == pdPASS) {
            uint8_t  buf[16];
            uint16_t n = frame_build(buf, sizeof(buf), &f);  /* AA 55 ... XOR */
            HAL_UART_Transmit(&huart1, buf, n, 10);          /* 10ms 超时保护 */
        }
        vTaskDelayUntil(&last, pdMS_TO_TICKS(20));
    }
}

/* ---- 心跳任务:500ms,优先级 1 ---- */
static void task_hb(void *arg)
{
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        frame_send_hb(&huart1);                    /* CMD 0x02,LEN = 0 */
        vTaskDelayUntil(&last, pdMS_TO_TICKS(500));
    }
}

/* ---- 创建:调度器启动前,栈深度单位为 word ---- */
void m2_start(void)
{
    qFrame = xQueueCreate(8, sizeof(frame_t));
    configASSERT(qFrame != NULL);

    xTaskCreate(task_acq,  "acq",  512, NULL, 3, &hAcq);
    xTaskCreate(task_comm, "comm", 768, NULL, 2, &hComm);
    xTaskCreate(task_hb,   "hb",   256, NULL, 1, &hHb);

    vTaskStartScheduler();
}

优先级继承的关键一行:总线保护必须用互斥量,而不是二值信号量。
SemaphoreHandle_t bus = xSemaphoreCreateMutex(); ← 有继承 · xSemaphoreCreateBinary(); ← 无继承

6/8 故障排查

先按"现象"定位,再做最小验证。每行都给出预期结果和下一分支,不要一上来就改代码。

现象先查什么预期结果下一分支
任务不调度 / 系统像死机 是否有 while (!flag) {} 这类忙等或死循环;用调试器暂停,看 PC 停在哪个函数 PC 停在某个任务的空转循环里,其它任务计数不再增长 改成阻塞等待或至少 vTaskDelay(1);用实验 C 复现并确认看门狗复位
队列溢出 / 丢帧计数持续增长 打印 uxQueueMessagesWaiting(qFrame) 与 g_drop_frames;核对生产与消费速率 队列长期接近深度 8,丢帧随生产速率线性增长 提高消费能力(批量打包 / 提高波特率)或降低采样率;加深度只能推迟,见实验 B
优先级反转:通信偶发几十~几百 ms 延迟 是否在等一个低优先级任务持有的锁;锁是二值信号量还是互斥量 换成 xSemaphoreCreateMutex() 后,最大延迟明显下降 缩短临界区、把总线访问集中到一个任务、避免持锁时做阻塞 I/O
看门狗复位 读 RCC->CSR 的 IWDGRSTF;确认喂狗是否只在"健康路径"里 复位原因 = 独立看门狗,且发生在某任务长时间未运行时 加任务心跳计数与复位日志;把喂狗条件改成"所有计数都在动"
心跳周期漂移(越跑越偏) 心跳任务用的是 vTaskDelay(500) 还是 vTaskDelayUntil 用 vTaskDelay 时误差逐周期累积,实测周期 > 500ms 改 vTaskDelayUntil,记录 100 个周期的抖动范围
栈溢出 / 中断里调用阻塞 API 触发断言 是否开了 configCHECK_FOR_STACK_OVERFLOW;ISR 里是否用了 xQueueSend、HAL_Delay 断言能定位到具体任务或 ISR;改成 FromISR 版本后消失 加大栈前先查大数组/递归;ISR 只做入队与置标志,处理放回任务
排查顺序建议:先确认"还有没有任务在按时运行"(计数/GPIO 翻转),再确认"谁占着 CPU 或锁",最后才怀疑硬件。 本页的三个实验可以帮你先在没有板子的情况下把假设跑一遍。
