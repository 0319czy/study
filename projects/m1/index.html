PROJECT M1 · 通信

M1 通信:把一帧说清楚

M0 的产出是"一个数";M1 要把它变成"一条两端都能核对的消息":帧头定位边界、LEN 说明长度、 SEQ 编号、CMD 区分数据类型、XOR 自校验,并且在 500 ms 没有消息时明确报超时,而不是假装一切正常。 本页的构造器、错误注入和超时模拟都可以直接改参数复算,但它们是模拟;真实串口上的那一帧标注为 hardware-pending,需要你上板完成。

帧长 6 + LEN(6~14 字节) 超时阈值 500 ms 错误类型 4 类 校验 XOR 单字节

前置:M0 采集(需先能读到数据并解释单位)。本页不包含 CRC、重传或应答,契约没有定义的东西不擅自加。

principle由契约规则与手算/脚本可复现的结论,不依赖某块板子。
simulated本页浏览器内脚本的运行结果:真实计算,但不是实物收发。
hardware-pending需要你在开发板 + 串口上完成;本页不代填、不冒充实测数据。

01

目标

用一句话说:M1 结束时,你能把 M0 的温度/湿度按 AA 55 | LEN | SEQ | CMD | DATA | XOR 发出,并写一个能把"好帧、坏帧、没帧"分开处理的接收端。

项内容
能力按契约实现 0x01 传感器帧与 0x02 心跳帧的构造与解析;按固定顺序定位四类错误;判定并统计 500 ms 超时
可检查结果① 手算 23.45 ℃ / 56.78 % / SEQ=1 的完整帧与 XOR,与构造器一致;② 在错误注入里复现四类错误并说出处理动作;③ 用超时模拟解释"间隔 vs 阈值"的判定与统计;④ 在真实串口抓到一帧并核对(待你完成)
交付物协议一页纸(帧表 + 命令表 + 错误处理表)、发送函数、接收解析函数、抓帧记录(时间/波特率/工具)
不在本阶段CRC、重传/应答、多字节长度、分片、加密。契约没定义,不要私自加进帧里,否则 M3 网关会对不上
证据标识principle 规则可手算 · simulated 浏览器内模拟 · hardware-pending 需实物验证
为什么 M0 不够?串口打印 23.45,56.78 人类看得懂,机器却不知道:温度从哪个字节开始、这一串有没有坏、 数据是不是十秒前的旧值。帧恰好回答三件事——边界(帧头 + LEN)、可信度(XOR)、新鲜度(SEQ + 500 ms 超时)。

完成标准:默认参数构造出的帧是 AA 55 04 01 01 29 09 2E 16 E3(XOR = 0xE3);你能不查页面独立复核这条链。

原理与图示

principle

先记住一条主线:帧是"自描述 + 自校验"的字节序列。下面每个字段都只回答一个问题,不多也不少。

3.1 帧结构:每个字段只回答一个问题

帧头AA
帧头55

SEQ01
CMD01
DATA[0]29

XOR 覆盖偏移 0 ~ 8(AA 到最后一个 DATA 字节),不含自己的 E3
字段字节取值作用 / 边界
帧头 AA 552固定让接收端能从任意噪声中重新对齐;坏一字节即"帧头错"

最小帧 = 心跳 6 字节;最大帧 = 6 + 8 = 14 字节。LEN 写成"整帧长度"是最常见的错误之一,例子里整帧 10 字节而 LEN = 4。

3.2 两种命令:同一层帧,不同语义

CMDLENDATA接收端如何解释
0x01 传感器4[0..1] int16 小端,温度 ×100
[2..3] uint16 小端,湿度 ×100		温度 = raw / 100 ℃;湿度 = raw / 100 %
0x02 心跳0无只表示"链路还活着",不产生数据
其他——契约外:解析器标"未知命令",不得当有效数据用

注意:0x01 与 0x02 的 LEN 是硬约定。CMD=0x01 但 LEN≠4、或 CMD=0x02 但 LEN≠0,都属于契约不符,应丢弃并记录日志。

3.3 数字怎么放进字节:×100 定点 + 小端

先把小数变成整数,再拆成两个字节。以 23.45 ℃、56.78 % 为例:

量原始类型计算原始值物理范围分辨率
温度int16round(T × 100)2345-327.68 ~ +327.67 ℃0.01 ℃
湿度uint16round(RH × 100)56780 ~ 655.35 %0.01 %
DATA[0] = 0x29低字节,先发
线上顺序 →
DATA[1] = 0x09高字节,后发
还原 →
0x0929 = 2345÷100 = 23.45 ℃

为什么不用 float?定点在 MCU 与 Linux 上结果完全一致、不依赖浮点格式、占 2 字节且可精确复算; float 虽然有 4 字节,但两端字节序/格式约定更麻烦。代价是必须自己处理溢出:超出范围要截断并告警,不能让补码回绕成"−327.68"或"655.35"。

3.4 XOR 校验:一条链,两个用途

规则只有一句:XOR = buf[0] ⊕ buf[1] ⊕ … ⊕ buf[5+LEN-1],即从 AA 一直异或到 DATA 的最后一个字节, 结果作为 1 字节附在末尾。

示例帧的逐字节链(每一步都能手算):

AA ^ 55 = FF
FF ^ 04 = FB
FB ^ 01 = FA
FA ^ 01 = FB
FB ^ 29 = D2
D2 ^ 09 = DB
DB ^ 2E = F5
F5 ^ 16 = E3   ← XOR = 0xE3,追加到帧尾

由此得到一个非常实用的自检:把 XOR 字节也一起异或,合法帧的结果必为 0x00 (E3 ⊕ E3 = 00)。接收端既可以"重算前 9 字节再比较",也可以"整帧异或判零",两者等价。

边界也要说清:XOR 是弱校验。它能发现任意单比特错误,但发现不了"同一位上偶数个比特翻转"这类互相抵消的错误, 也发现不了字节顺序互换。生产环境通常用 CRC16;本契约固定 XOR,不要为了"更安全"擅自换成 CRC—— 那会让两端算出的校验永远对不上。要换就升协议版本,两端同时改。

3.5 解析顺序:先结构,后校验,最后语义

四类错误的判定有严格先后,顺序错了会把"没发完"误报成"校验错"。按下面五步走:

  1. 找帧头:前两字节必须是 AA 55。失败 → 帧头错
  2. 看长度:LEN ≤ 8。失败 → LEN 超限(LEN>8)
  3. 等收全:缓冲区至少 6 + LEN 字节(含 XOR 尾)。失败 → 帧尾缺失/未收全
  4. 验校验:重算前 6+LEN-1 字节的 XOR,与末字节比较。失败 → XOR 错
  5. 解语义:按 CMD 解释 DATA;CMD 与 LEN 不符(如 0x01 却 LEN=2)属契约不符,不是上面四类收发错误,单独记日志。

这里的"帧尾"就是 XOR 字节(本协议没有额外的结束符)。所以"帧尾缺失"= 缓冲区还没到 6+LEN, "未收全"= 同一件事的另一种说法。出现这种情况时保留缓冲继续收,不要立刻清空,否则永远拼不出整帧。

3.6 超时:500 ms 没来有效帧,就要说"没来"

判定公式:now − t_last_valid > 500 ms → 超时。其中 t_last_valid 是最后一条通过校验的有效帧的到达时刻。 链路是否活着,可以由任意有效帧(含心跳 0x02)刷新;但要看"传感器数据是否断流",必须单独用 0x01 帧计时。 本页的超时模拟按后者统计(只算 0x01 的到达间隔),检验的是数据新鲜度。

为什么 500 ms 合理?一帧最多 14 字节,115200 8N1 下约 1.2 ms;500 ms 不是"帧太长",而是给"整帧没来"留的宽限, 大约能容忍两三个发送周期。反过来,如果你的发送周期本身就 ≥ 500 ms,这个阈值没有意义——那是契约前提没对齐,应先改周期,而不是把阈值调大。

时序举例:300 ms 收到帧并开始计时;到 800 ms 满 500 ms 仍无帧,报超时;900 ms 帧到达,清除标志、从 900 ms 重新计时。
实现建议(不是契约):把"链路超时"与"传感器数据断流"分开计时。心跳 0x02 可以刷新链路活跃时间, 但不能替代 0x01 的数据新鲜度;否则"传感器坏了但心跳还在"会被判成健康。本页超时模拟只统计 0x01 帧的到达间隔。

3.7 线上长什么样:LSB 先发的 8N1

以 DATA[0] = 0x29 为例,0x29 = 0b0010_1001,UART 从最低位开始发:1、0、0、1、0、1、0、0。

LSB 先发是 UART 的默认约定,也是"小端"在协议里的同一种直觉:低位在前。抓包时看到的第一位是起始位(低),最后一位是停止位(高)。

    参考实现 · 固件侧发送骨架 principle

    与构造器完全同规则:先拼 AA … DATA,对这段异或得到 XOR,再追加到帧尾。 该骨架未在实物上编译运行(属 hardware-pending),编译前请按你的工程确认 huart1 与时钟。 

    /* 发送一帧 0x01 传感器数据:t100 / h100 均以 0.01 为单位 */
void proto_send_sensor(int16_t t100, uint16_t h100, uint8_t seq)
{
    uint8_t  f[10];
    uint16_t t = (uint16_t)t100;              /* 负数按 int16 补码转无符号 */

    f[0] = 0xAA;
    f[1] = 0x55;
    f[2] = 4;                                 /* LEN:只数 DATA 的 4 字节 */
    f[3] = seq;
    f[4] = 0x01;                              /* CMD:传感器数据 */
    f[5] = (uint8_t)(t & 0xFF);               /* 低字节先发(小端) */
    f[6] = (uint8_t)(t >> 8);
    f[7] = (uint8_t)(h100 & 0xFF);
    f[8] = (uint8_t)(h100 >> 8);

    uint8_t x = 0;
    for (uint8_t i = 0; i < 9; i++) {          /* AA … DATA[3],不含 XOR 自身 */
        x ^= f[i];
    }
    f[9] = x;

    HAL_UART_Transmit(&huart1, f, sizeof f, 10);  /* 10 B ≈ 0.87 ms @115200 8N1 */
}
    记录实验:把每次构造的输入、完整帧、XOR、判定结果抄到一张表里(M5 的测试记录会用到)。 示例帧已用独立 Node 脚本核算为 AA 55 04 01 01 29 09 2E 16 E3,得到 XOR = 0xE3;页面默认参数按同一规则生成,应完全一致。

    故障排查

    principle

    按"物理层 → 帧结构 → 完整性 → 校验 → 语义 → 时序"的顺序查,每步都有可观察的预期结果,不要跳步猜。

    现象检查步骤预期结果下一分支
    解析器一直报"帧头错",字节流不以 AA 55 开头 ① 两端是否都是 115200 8N1;② 是否共地;③ TX/RX 是否交叉;④ 串口助手切十六进制看原始流 原始流前两字节是 AA 55,空闲电平为高 仍乱码 → 查时钟源与 USB-TTL 电平(3.3 V/5 V);上电瞬间噪声 → 先丢弃若干字节再搜索帧头
    每次报"XOR 错",接收值与计算值差一个固定值 核对发送端异或是否从 AA 起、是否漏算/多算字节、是否把 XOR 自身也算进去;用本页构造器同参数对照 手算链末值 = 帧末字节 发送端对而接收端错 → 检查是否按 LEN 截取,是否把下一帧首字节算进了本帧
    帧完整但温度显示 23450 ℃ 或 0.23 ℃ 查是否重复乘/除 100;是否按大端解析(高低字节颠倒);是否把原始整数当浮点直接打印 2345 / 100 = 23.45 ℃,且 0x0929 的低字节 0x29 先出现 字节序错 → 交换 DATA[0]/DATA[1];缩放错 → 只在显示层除一次 100
    报"未收全/帧尾缺失",缓冲区总差 1~2 字节 查 read() 返回值是否被当成整帧;是否处理半包/粘包;DMA 缓冲是否被下一帧覆盖 缓冲区累积到 6+LEN 再解析,多余字节留给下一帧 仍缺 → 查 UART 溢出标志 ORE/中断优先级;改用 DMA + 空闲中断按帧接收
    超时统计里频繁出现 > 500 ms 的间隔 查采集+发送的实际周期;是否有 HAL_Delay/printf 阻塞;高优先级任务是否抢占发送;看门狗是否复位 发送周期稳定且 < 500 ms(建议 ≤ 400 ms,留 20% 余量) 周期正常仍超时 → 分段计时(采集耗时 vs 发送耗时),查 DMA 未启动、波特率不匹配导致整帧丢失
    温湿度恒为 0.00 或 -327.68 ℃ / 655.35 % 查传感器初始化返回值;DATA 是否全 0x00 或全 0xFF;是否未采样就发送;结构体 memset 后是否忘了赋值 上电后读到合理范围,且变化趋势与 M0 的 ADC 读数一致 全 0 → 查传感器句柄与供电;全 FF → 查读失败分支是否把错误码当数据发了

    排查记录至少写三列:时间、波特率、当时看到的原始十六进制。没有原始字节的"我觉得是 XX 问题"不算排查结论。
