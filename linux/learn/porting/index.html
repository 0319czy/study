移植与升级

内核 API 会变，硬件描述也会变。建立“查版本、读头文件、跑基线、逐项适配”的移植方法，而不是背 API。

版本差异API 变更设备树适配ABIstable API移植

学习目标

  • 用版本对照卡评估从 5.x 迁到 6.x 的改动面
  • 区分稳定 ABI、内核内部 API 与设备树绑定
  • 为一次移植准备可复现的验证清单
ONE SENTENCE

移植不是“把旧代码贴到新内核”，而是按版本核对 API、设备树绑定与配置，建立可复现的验证与回滚流程。

生活化比喻

搬家不是把家具硬塞进新房子，而是先量尺寸、改接口、再逐件验收

新内核可能改了接口、删了旧 helper、变了设备树绑定。先列清单（调用哪些 API）、量尺寸（目标内核头文件/绑定）、做适配（最小改动），最后逐项验收并保留回滚。

为什么重要 / 用在哪里

  • 内核内部 API 不保证稳定；旧教程/旧 BSP 代码在新内核上经常编译失败或行为变化。
  • 设备树绑定也可能演进；同样的属性在新内核可能不再被接受。
  • 移植需要证据：目标版本、构建日志、运行日志、测试结果与回滚方案缺一不可。
  • “能编译”不等于“能工作”；probe、数据通路、并发与卸载都要验证。

核心概念

internal kernel API

内核内部 API

函数签名、结构体字段、宏都可能变化；没有跨版本稳定保证。移植时以目标内核头文件与源码为准。

stable ABI

稳定 ABI

用户态系统调用/ABI、部分设备树绑定与 sysfs 接口相对稳定，但边界因子系统而异。不能把“稳定”理解为“永远不变”。

device tree binding

设备树绑定

属性名、cell 数量、必填项可能随 binding 文档变化；迁移时要查目标内核的 Documentation/devicetree/bindings。

build against target

目标构建

必须用目标内核的 build 目录与配置编译，不能用宿主机另一版内核代替；架构/交叉编译也要一致。

regression test

回归测试

每次移植后验证 probe、读写、中断、DMA、卸载、并发与错误路径；保留测试脚本与日志。

rollback

回滚

保留旧内核/旧模块/旧 dtb 与配置；升级失败时能快速回到可工作状态。

常见错误与排查

01

旧驱动在新内核编译失败。

常见原因
API 签名/字段/宏变化，或旧 helper 被移除。
排查 / 修复
查目标内核头文件与 git 历史；做最小适配；不要用宏强行绕过类型检查。
02

编译通过，但 probe 不执行或设备不工作。

常见原因
设备树 binding 变化、compatible 不匹配、资源 cell 数变化，或配置项未开启。
排查 / 修复
对照目标 binding 文档与 dts；检查 status/compatible/资源；看 deferred probe。
03

升级后偶发崩溃，回滚困难。

常见原因
没有保留旧内核/旧模块/旧 dtb；测试只覆盖 happy path。
排查 / 修复
升级前备份并记录回滚步骤；加入并发/错误/卸载测试；保留可复现日志。

版本与边界

本页默认以 Linux 6.x / ARM64 为基线。API 签名、头文件路径与设备树绑定可能随版本变化； 旧内核请直接查对应版本源码与文档。代码示例是学习示意，不承诺在任意内核/板卡上直接编译运行。

本站不连接真实内核或开发板；示例中的主设备号、dmesg、模块名均为教学数据，不能替代目标环境验证。
