内核与驱动基础

用公司总部、办事窗口与翻译官三个比喻，建立内核分层、用户态/内核态、系统调用与驱动分类的整体认知。

内核架构用户态内核态系统调用VFS模块

学习目标

  • 说清用户态与内核态的分工，以及系统调用为什么存在
  • 区分模块（.ko）与内置驱动，理解各自适用场景
  • 能画出“应用 → VFS → 驱动 → 总线 → 设备”的最小路径
ONE SENTENCE

Linux 内核负责管理和保护硬件资源；驱动是内核里把统一请求翻译成具体硬件操作的那层代码。

生活化比喻

内核是公司总部，用户态是前台，驱动是翻译官

你在前台填一张“我要读 32 字节”的申请单，不能直接冲进机房。前台把单子从办事窗口递进总部，总部按流程找到负责这台设备的翻译官；翻译官再和硬件沟通，最后把结果送回前台。

为什么重要 / 用在哪里

  • 驱动代码运行在内核态，拥有很高权限，也意味着一次空指针或越界可能拖垮整机。
  • 同一个“读文件”动作，可能落到磁盘、字符设备、网络文件系统；VFS 把它们统一成 read/write 等接口。
  • 内核模块可以动态加载，但模块、驱动、设备节点、probe 是不同阶段，不能用“insmod 成功”代替整条链路。
  • 理解用户态/内核态边界，才能明白为什么不能把用户指针直接交给硬件，为什么中断里不能睡眠。

核心概念

User Mode / Kernel Mode

用户态与内核态

CPU 的两种权限级别。用户态不能执行特权指令、不能直接访问内核内存；内核态可以访问硬件和全部地址空间。ARM64 常简化为 EL0/EL1，x86 常简化为 ring 3/ring 0。

System Call

系统调用

用户程序进入内核的受控入口。read、write、ioctl、mmap 最终都会触发一次模式切换；内核先校验参数，再分派给 VFS 或具体子系统。

VFS

虚拟文件系统

内核的文件操作抽象层。它不关心底层是字符设备还是磁盘，只根据 file_operations 找到对应回调。

Loadable Module / Built-in

内核模块与内置驱动

模块编译成 .ko，可在运行时 insmod/rmmod；内置驱动编进 vmlinux，随内核启动。两者使用同一套内核 API，区别在部署方式与生命周期。

Driver Classes

驱动分类

常见有字符设备、块设备、网络设备，以及按总线划分的 platform、I2C、SPI、USB 驱动。分类回答的是“设备以什么方式被访问”，不是“代码放在哪个目录”。

Execution Context

执行上下文

进程上下文、软中断、硬中断的规则不同。最关键的一条：中断上下文不能睡眠，所以不能在里面调用可能阻塞的函数或拿互斥锁。

关键 API 与代码

代码是学习示意，以 Linux 6.x / ARM64 为默认基线。每个 API 都列出参数与返回值；不要只抄代码， 先确认它运行在什么上下文、失败时怎么回滚。

用户态：通过系统调用访问设备

API 逐个解释
open用户态
int open(const char *pathname, int flags);

参数：pathname：设备节点路径；flags：O_RDONLY/O_WRONLY/O_RDWR 等

返回：成功返回文件描述符；失败返回 -1 并设置 errno。

read用户态
ssize_t read(int fd, void *buf, size_t count);

参数：fd：open 返回的描述符；buf：用户缓冲区；count：最多读取字节数

返回：成功返回实际字节数，0 常表示 EOF；失败返回 -1 并设置 errno。

注意：用户态看到的是字节流；具体数据由驱动的 read 回调产生。

内核态：驱动里的 read 回调（简化示意）

API 逐个解释
copy_to_user进程上下文；不能用于中断上下文中的用户地址访问。
unsigned long copy_to_user(void __user *to, const void *from, unsigned long n);

参数：to：用户目标地址；from：内核源地址；n：要复制的字节数

返回：返回未能复制的字节数；0 表示全部成功，非 0 常转成 -EFAULT。

注意：不要直接解引用用户指针；也不要用 memcpy 代替。

__user内核源码标注
char __user *ubuf

参数：这是地址空间标注，不是运行时类型

返回：无返回值；用于让编译器/静态检查识别用户指针。

注意：看到 __user 就应该想到 copy_to_user/copy_from_user。

版本对照卡

6.x 是默认基线，旧版只做定位提示。发行版可能回移植补丁，迁移时请直接看目标内核头文件。

版本对照用户态 / 内核态边界

系统调用号与 ABI

6.x 基线

Linux 6.x：用户态通过 libc 或 syscall() 使用架构维护的 ABI

旧版对照

不同架构、32/64 位兼容层的 syscall 编号可能不同

影响：硬编码 syscall 编号在跨架构或兼容层时容易出错；驱动本身不应依赖用户态 syscall 编号。

边界：SYS_read 由 libc/内核头文件提供；具体编号因架构与 ABI 而异，这里只做定位提示。

当前：用户程序运行

1 / 7
步骤 1
用户程序运行

main() 在用户态 EL0（x86 简化为 ring 3）执行，使用用户栈；此时不能访问内核地址，也不能直接操作设备寄存器。

观察问题：为什么用户程序不能直接调用驱动里的函数？内核态是否意味着“什么都能做、哪里都能睡”？

结论提示：用户态只能通过受控入口进入内核；内核态有更高权限，但仍受执行上下文约束。中断上下文不能睡眠，用户地址必须用 copy_*_user 访问。

EL0/EL1 是 ARM64 的简化表述；x86 常写作 ring 3/ring 0。具体异常入口与寄存器约定以架构手册为准。

常见错误与排查

01

驱动一读用户缓冲区就 Oops，日志出现空指针或非法地址。

常见原因
把用户态指针当成普通内核指针直接解引用，或者没有检查 copy_to_user 的返回值。
排查 / 修复
所有用户地址都用 copy_to_user/copy_from_user；检查返回值并返回 -EFAULT；不要在中断上下文访问用户地址。
02

insmod 报 Invalid module format。

常见原因
模块编译时使用的内核版本/配置与目标机不一致，vermagic 不匹配。
排查 / 修复
用目标机 /lib/modules/$(uname -r)/build 重新编译；确认架构与内核配置一致。
03

用户态 read 返回 -1，errno 为 EFAULT 或 EINVAL。

常见原因
驱动没有正确处理用户缓冲区、长度或偏移；也可能把用户态 API 与内核态 API 混用。
排查 / 修复
检查 copy_to_user 返回值、len 边界与 *ppos；先在用户态用 strace 确认调用参数。
