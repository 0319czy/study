性能与实时性

上下文切换、中断延迟、抢占模型与 PREEMPT_RT：理解“平均很快”不等于“最坏情况可接受”。

学习目标

  • 区分吞吐、延迟与抖动三个指标
  • 解释中断禁用、关抢占与自旋锁如何放大最坏延迟
  • 知道 PREEMPT_RT 改变了什么、没有改变什么
ONE SENTENCE

性能不只看平均值：吞吐、延迟与抖动要分开看；实时性关心的是最坏情况，而不是“通常很快”。

生活化比喻

平均通勤 20 分钟，不代表每天都能准时到

实时系统关心的不是“平均响应多快”，而是“最坏一次会不会超过截止时间”。一次长关中断、一次持锁、一次 page fault，都可能让最坏延迟飙升。

为什么重要 / 用在哪里

  • 工业控制、音视频、机器人控制对最坏延迟敏感；平均值好看没有意义。
  • 关中断、持自旋锁、页错误、缓存未命中和优先级反转都会放大延迟。
  • PREEMPT_RT 改变了内核的可抢占性，但不是“自动实时”；应用与驱动仍要配合。
  • 性能优化必须先用数据定位瓶颈，不能凭感觉改代码。

核心概念

throughput / latency / jitter

吞吐 / 延迟 / 抖动

吞吐是单位时间处理量，延迟是单次响应时间，抖动是延迟波动。实时系统优先看最坏延迟与抖动。

context switch

上下文切换

CPU 从一个执行流切到另一个执行流，需要保存/恢复状态。频繁切换有开销，也可能引入调度延迟。

interrupt latency

中断延迟

从中断发生到处理函数开始执行的时间，受关中断、更高优先级中断、硬件与虚拟化影响。

preemption model

抢占模型

内核可在编译时选择不同抢占级别：从“只在显式点抢占”到“几乎处处可抢占”。抢占越好，最坏延迟通常越低，但吞吐/复杂度有代价。

priority inversion

优先级反转

高优先级任务等待低优先级任务持有的锁，而低优先级又被中优先级任务抢占，导致高优先级被间接阻塞。可用优先级继承/设计规避。

PREEMPT_RT

PREEMPT_RT

一组实时化补丁/配置，减少不可抢占区、把中断处理线程化等。是否可用取决于内核版本、配置与硬件。

API 逐个解释
cyclictest用户态性能测试
cyclictest -p <prio> -m -n -i <interval_us> -l <loops>

参数：-p：实时优先级；-m：锁定内存；-n：使用 clock_nanosleep；-i：间隔微秒；-l：循环次数

返回：输出延迟统计；具体格式以 rt-tests 版本为准。

注意：需要相应权限与实时调度配置；测试结果受 CPU 隔离、负载、虚拟化影响。

常见错误与排查

01

平均延迟很低，但偶发超时。

常见原因
只看平均值；最坏延迟被关中断、锁、页错误、调度或虚拟化放大。
排查 / 修复
记录 max/p99/p99.9；控制变量；用 cyclictest、ftrace、perf 找最坏路径。
02

打开 PREEMPT_RT 后仍有超时。

常见原因
应用优先级/CPU 隔离/中断线程优先级没配好；驱动仍有长临界区或关中断。
排查 / 修复
检查线程优先级、IRQ 线程、CPU 隔离、锁与关中断窗口；RT 不是自动保证。
03

高优先级任务被低优先级任务间接阻塞。

常见原因
优先级反转：高优先级等锁，低优先级持锁被中优先级抢占。
排查 / 修复
缩短临界区、使用优先级继承（如 rt_mutex）、重新设计共享资源。
