内核模块

从 module_init/module_exit 写起，理解许可证、模块参数、依赖关系，以及 insmod、modprobe、dmesg 的实际工作流。

学习目标

  • 写出一对可加载/卸载的最小模块骨架
  • 解释 MODULE_LICENSE 与 taint、模块依赖、vermagic 的作用
  • 用 dmesg 与 modinfo 排查“加载了但没反应”
ONE SENTENCE

内核模块是可以在运行时插入内核的 .ko 代码包，通过 module_init/module_exit 获得生命周期入口。

生活化比喻

模块是“外派团队”，不是普通可执行程序

你把一个外派团队送进公司总部：先查工牌（vermagic/签名/许可证），再由领队报到（module_init）。团队可以调用总部提供的公共接口（导出符号），但不能自己另起一套规则；离场时要交接清楚（module_exit）。

为什么重要 / 用在哪里

  • 大多数板级驱动以模块形式开发和调试：改一行、重编、卸载、再加载，比反复重启内核快得多。
  • 模块能动态进出内核，所以必须讲清生命周期：谁分配、谁释放、失败怎么回滚。
  • 模块不是独立进程。它共享内核地址空间，调用内核导出符号，出错会影响整机。
  • 理解 vermagic、签名、taint 与依赖，能解释“为什么同一份 .ko 在这台机器上装不上”。

核心概念

module_init / module_exit

模块入口与出口

module_init 注册加载时调用的初始化函数，返回 0 表示成功；module_exit 注册卸载时调用的清理函数，返回 void。两者都只是宏，不是普通函数调用。

MODULE_LICENSE

模块许可证

声明模块许可证。它会影响能否使用 EXPORT_SYMBOL_GPL 导出的符号，也会影响内核 taint 状态；它不是“法律建议”，也不能替代对具体许可证的阅读。

module_param

模块参数

把模块内的变量暴露为加载参数或 sysfs 属性。参数类型、权限位与描述都要明确；权限为 0 时通常不创建 sysfs 文件。

modules.dep

模块依赖

模块可能调用其他模块导出的符号。modprobe 会根据 modules.dep 先加载依赖；insmod 只加载你指定的那一个文件，不自动解决依赖。

vermagic / module signature

vermagic 与签名

vermagic 记录模块编译时的内核版本与关键配置；签名策略由内核配置、Secure Boot 与发行版决定。两者都可能导致“编译成功但加载失败”。

taint

内核污染

内核用 taint 标记“当前运行环境不再纯净”，例如加载树外或未签名模块。taint 不一定代表立刻出错，但会影响问题报告的可信度。

API 逐个解释
module_initinsmod/modprobe 加载阶段的进程上下文
module_init(init_function);

参数：init_function：int (*)(void) 类型的初始化函数

返回：宏本身无返回值；初始化函数返回 0 表示成功，返回负 errno 表示失败。

注意：初始化失败时，已申请的资源要按相反顺序释放；不要返回未定义的错误码。

module_exitrmmod/modprobe -r 卸载阶段
module_exit(exit_function);

参数：exit_function：void (*)(void) 类型的清理函数

返回：无返回值；卸载失败不能靠它“返回错误”。

注意：如果设备仍被打开、资源仍被引用，卸载可能被阻止；清理函数应当幂等、顺序正确。

MODULE_LICENSE模块元数据
MODULE_LICENSE("GPL");

参数：许可证字符串，例如 "GPL"、"GPL v2"、"Dual BSD/GPL"

返回：无返回值；写入模块元数据。

注意：使用 GPL-only 导出符号时通常需要兼容的许可证声明；具体义务请阅读许可证原文。

module_param模块加载/参数解析
module_param(name, type, perm);

参数：name：变量名；type：int、bool、charp 等；perm：sysfs 权限位，0 表示不暴露

返回：宏本身无返回值；在模块加载时建立参数入口。

注意：参数值可能在加载时被用户指定；驱动必须校验范围，不能假设一定是安全值。

pr_info任何上下文都可调用，但高频日志会影响性能。
pr_info(fmt, ...);

参数：fmt：格式串；...：可变参数

返回：无返回值；写入内核日志（KERN_INFO 等级）。

注意：生产驱动应使用 dev_info/dev_err 或 dynamic debug，并避免在热路径打印大量日志。

外部模块 Makefile（示意）

API 逐个解释
obj-mkbuild 构建系统
obj-m += hello.o

参数：hello.o：由 hello.c 编译出的对象文件

返回：无返回值；告诉 kbuild 生成 hello.ko。

注意：模块名与源文件名要对应；多个源文件时用 hello-objs 组合。

M=$(PWD)用户态构建
$(MAKE) -C $(KDIR) M=$(PWD) modules

参数：KDIR：目标内核构建目录；PWD：外部模块源码目录

返回：由 make 决定；失败时返回非 0 退出码。

注意：编译用的内核头文件/配置必须与目标板运行的内核一致。

版本对照卡

6.x 是默认基线，旧版只做定位提示。发行版可能回移植补丁，迁移时请直接看目标内核头文件。

版本对照内核模块 / 加载

模块签名与 taint 策略

6.x 基线

6.x 常见发行版可能启用 CONFIG_MODULE_SIG 与 Secure Boot 策略

旧版对照

旧内核/发行版对未签名模块可能更宽松，但仍可能给内核打上 taint 标记

影响：未签名或树外模块可能被拒绝，或让内核进入 tainted 状态；加载成功不等于环境干净。

边界：是否强制签名取决于内核配置、Secure Boot 与发行版策略，不能一概而论。

步骤 1
modprobe 请求

执行 sudo modprobe gpio_led。modprobe 先解析模块名/别名与依赖，而不是直接调用 module_init。

观察问题：为什么 insmod gpio_led.ko 可能失败，而 modprobe gpio_led 成功？依赖顺序错了，dmesg 会留下什么线索？

结论提示：insmod 只加载指定文件；modprobe 读取 modules.dep 并按依赖顺序加载。Unknown symbol 通常表示符号未导出或依赖未加载。

模块名、路径与符号名为教学示意；真实项目以 modinfo、modules.dep 与内核符号表为准。

常见错误与排查

01

insmod 报 Unknown symbol 或 unknown symbol in module。

常见原因
模块调用了未加载模块导出的符号，或使用了当前内核没有导出的符号。
排查 / 修复
用 modprobe 让依赖先加载；用 modinfo、nm、/proc/kallsyms 检查符号；确认许可证与 EXPORT_SYMBOL_GPL 的匹配。
02

insmod 报 Invalid module format，但编译明明成功。

常见原因
模块与目标内核的 vermagic、架构或关键配置不一致。
排查 / 修复
在目标机上用 /lib/modules/$(uname -r)/build 重编；确认 ARCH/CROSS_COMPILE 与目标板一致。
03

modprobe 找不到模块，或加载顺序不对。

常见原因
模块没有安装到 /lib/modules/$(uname -r)，或 modules.dep 未更新。
排查 / 修复
执行 make modules_install 与 depmod -a；用 modprobe -n -v 查看将要加载的依赖。

TAKE IT WITH YOU

记住这三句话

  1. 01

    模块是共享内核地址空间的代码包，不是独立进程；加载成功只是生命周期开始。

  2. 02

    module_init 返回 0 才算初始化成功，失败要按相反顺序释放已申请资源。

  3. 03

    insmod 只加载一个文件；modprobe 才根据 modules.dep 处理依赖。
