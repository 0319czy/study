中断处理

中断像火警：上半部先灭火，下半部再善后。理解 request_irq、线程化中断、tasklet 与 workqueue 的取舍。

request_irq上半部下半部taskletworkqueuethreaded IRQIRQF_SHARED

学习目标

  • 区分上半部与下半部的执行上下文和限制
  • 能写出带 dev_id 与共享标志的 request_irq 调用
  • 根据“能否睡眠、耗时长短”选择 workqueue 或 threaded IRQ
ONE SENTENCE

中断让 CPU 暂停当前工作先处理硬件事件；驱动把最紧急的部分放在上半部，把耗时善后放到下半部。

生活化比喻

火警响了：先灭火，再写事故报告

上半部是消防员到场先做的“断电、喷水”——必须快，不能睡觉。下半部是事后清理、记录、通知——可以延后。workqueue 像专门的后勤人员，threaded IRQ 像给这个设备配一名专职内核线程，tasklet 像软中断队列里的快速杂活。

为什么重要 / 用在哪里

  • 按键、传感器、DMA 完成都常用中断通知 CPU；不会中断处理，就无法写出真正响应硬件的驱动。
  • 上半部在中断上下文运行，不能睡眠、不能长时间关中断；放错工作会让系统卡顿或直接 BUG。
  • 共享中断、错误返回值和 dev_id 是实际调试中的高频坑。
  • 下半部机制影响延迟、吞吐与代码复杂度，不是“随便选一个”。

核心概念

IRQ number / irq_handler_t

IRQ 与处理函数

request_irq 把一个中断号和回调绑定。回调返回 IRQ_HANDLED 表示处理了，IRQ_NONE 表示不是自己的中断（共享中断时尤其重要）。

top half / hardirq

上半部

硬中断处理函数运行在中断上下文，必须短小快速。不能睡眠、不能调用可能阻塞的函数；尽量只做清中断、记录、调度下半部。

tasklet

tasklet

基于软中断的延迟机制，运行在软中断上下文，仍然不能睡眠。适合很短、无阻塞的善后工作。

workqueue

workqueue

把工作交给内核线程在进程上下文执行，可以睡眠。适合需要 I2C/SPI 传输、分配内存或较长处理的善后。

threaded IRQ

线程化中断

request_threaded_irq 把主要处理放到内核线程，上半部可以只做最小确认。线程化处理可以睡眠，常用于需要总线访问的设备。

shared IRQ

共享中断

多个设备共享同一 IRQ 线时，每个处理函数都要判断“是不是我的中断”，并返回 IRQ_NONE 让其他处理函数继续；dev_id 必须唯一且与 free_irq 一致。

上半部 + workqueue

API 逐个解释
request_irq通常在 probe/进程上下文注册
int request_irq(unsigned int irq, irq_handler_t handler, unsigned long flags, const char *name, void *dev);

参数：irq：中断号；handler：上半部回调；flags：触发方式/共享等；name：/proc/interrupts 中显示的名字；dev：传给回调的唯一标识

返回：成功返回 0；失败返回负 errno（如 -EBUSY、-EINVAL）。

注意：共享中断必须传非 NULL 且唯一的 dev_id；释放时 free_irq(irq, dev_id)。

schedule_work可在中断上下文调用
bool schedule_work(struct work_struct *work);

参数：work：已 INIT_WORK 的工作项

返回：如果工作项之前未排队并成功加入，返回 true；否则 false。

注意：实际回调在进程上下文执行，可以睡眠；但不要重复初始化同一个工作项。

IRQ_HANDLED / IRQ_NONE中断上下文
return IRQ_HANDLED; / return IRQ_NONE;

参数：无参数；作为 irqreturn_t 返回值

返回：告知内核该中断是否由本处理函数处理。

注意：共享中断中，不是自己的中断要返回 IRQ_NONE，否则会影响其他设备。

线程化中断：上半部为空，善后在线程里

API 逐个解释
request_threaded_irq进程上下文注册
int request_threaded_irq(unsigned int irq, irq_handler_t handler, irq_handler_t thread_fn, unsigned long flags, const char *name, void *dev);

参数：handler：可为 NULL 的硬中断部分；thread_fn：内核线程中的处理函数；其余同 request_irq

返回：成功返回 0；失败返回负 errno。

注意：线程化处理降低上半部负担，但调度延迟受系统负载影响；实时性要求高时要单独评估。

IRQF_ONESHOTrequest_threaded_irq
IRQF_ONESHOT

参数：中断标志位

返回：无返回值；作为 flags 的一部分。

注意：当 primary handler 为 NULL 时，常用它避免中断线在 threaded handler 完成前反复触发。

版本对照中断 / 延迟工作

中断下半部的选择

6.x 基线

6.x：tasklet、workqueue、threaded IRQ 都可选，按上下文与延迟目标选择

旧版对照

旧代码常一律使用 tasklet；现代驱动更常用 threaded IRQ 或 workqueue

影响：下半部机制决定能否睡眠、调度延迟与代码复杂度；tasklet 在软中断上下文不能睡眠。

边界：tasklet 仍存在但不应滥用；选择要看内核配置、实时性要求与硬件行为。

步骤 1
设备触发中断

按键/传感器拉低中断线，CPU 暂停当前工作，进入硬中断入口。真实触发方式由设备树与硬件决定。

观察问题：为什么上半部不能睡眠？tasklet、workqueue 与 threaded IRQ 分别运行在什么上下文？

结论提示：上半部在硬中断上下文，不能睡眠；tasklet 在软中断上下文仍不能睡眠；workqueue 和 threaded IRQ 在进程/线程上下文，可以睡眠，但延迟与调度开销不同。

中断号、触发方式与下半部选择都是教学示意；真实设备要结合设备树、硬件手册与实时性要求验证。

常见错误与排查

01

日志出现 BUG: scheduling while atomic，或系统在中断里卡死。

常见原因
在硬中断/软中断上下文调用了可能睡眠的函数（mutex、msleep、copy_to_user、I2C 传输等）。
排查 / 修复
把耗时/可能睡眠的工作移到 workqueue 或 threaded IRQ；上半部只做最小确认与调度。
02

日志出现 irq XX: nobody cared，或中断计数增长但驱动没收到。

常见原因
共享中断处理函数没有正确判断/返回 IRQ_HANDLED，或中断没有清除，或触发方式配置错误。
排查 / 修复
检查 dev_id、返回值和硬件清中断；用 /proc/interrupts 观察计数；确认设备树 interrupts 与触发类型。
03

request_irq 返回 -16（EBUSY）。

常见原因
中断号已被其他驱动占用，或共享中断没有设置 IRQF_SHARED。
排查 / 修复
确认中断号与设备树；需要共享时设置 IRQF_SHARED 并提供唯一 dev_id；不要强行抢中断。
