字符设备

主次设备号、cdev、file_operations 与自动创建设备节点：把一段内核代码变成 /dev 下可 open 的文件。

主设备号次设备号cdevfile_operationsudev设备节点

学习目标

  • 理解主设备号与次设备号分别解决什么问题
  • 用 alloc_chrdev_region + cdev_add + class_create/device_create 注册设备
  • 能解释 open/read/write/release 在什么上下文被调用
ONE SENTENCE

字符设备是内核按字节流暴露给用户空间的设备抽象，用户通过 /dev 节点执行 open/read/write/release。

生活化比喻

字符设备像一条按字节流动的传送带

主设备号是“部门编号”，次设备号是“窗口编号”；/dev 节点是窗口门牌，file_operations 是窗口能办的事项清单。用户递进来一张 read 申请，VFS 按门牌找到窗口，窗口再按清单调用你的函数。

为什么重要 / 用在哪里

  • LED、按键、串口、传感器等大量简单设备，都会先以一个字符设备接口出现。
  • 字符设备是理解 VFS 分派、用户/内核数据拷贝与设备生命周期的最好入口。
  • 主次设备号、cdev、class/device、udev 之间的关系，是面试与真实板级调试的高频问题。
  • 注册顺序与清理顺序一旦写反，轻则残留节点，重则卸载后访问已释放内存。

核心概念

dev_t / major / minor

设备号

dev_t 同时包含主设备号和次设备号。主设备号通常对应一个驱动，次设备号区分同一驱动下的不同设备实例。用 MAJOR()、MINOR()、MKDEV() 拆装。

cdev

字符设备结构

cdev 把设备号与 file_operations 关联起来。cdev_init 初始化，cdev_add 注册，cdev_del 注销。它不是设备节点，也不等于驱动本身。

file_operations

文件操作表

驱动向 VFS 注册的回调集合。open/read/write/release 是最小集合；ioctl、poll、mmap 按需实现。回调签名由内核固定，不能随意改参数。

class / device

设备类与设备

class_create 创建设备类，device_create 创建具体设备并发出 uevent。用户态 udev 收到通知后创建 /dev 节点、设置权限。

__user

用户指针

驱动读回调收到的缓冲区地址属于用户地址空间，必须用 copy_to_user/copy_from_user 访问。直接解引用可能触发 Oops，也可能读到错误数据。

open count / release

打开计数与生命周期

release 在文件对象的最后一个引用释放时调用，不保证等于每次 close 的瞬间。卸载前要确认没有用户仍持有设备，否则模块可能无法安全移除。

API 逐个解释
alloc_chrdev_region模块初始化，进程上下文
int alloc_chrdev_region(dev_t *dev, unsigned baseminor, unsigned count, const char *name);

参数：dev：输出设备号；baseminor：起始次设备号；count：申请数量；name：设备/驱动名

返回：成功返回 0；失败返回负 errno。

注意：动态申请主设备号可以避免与已有设备冲突；失败路径不要继续注册 cdev。

cdev_init / cdev_add模块初始化
void cdev_init(struct cdev *cdev, const struct file_operations *fops);
int cdev_add(struct cdev *cdev, dev_t dev, unsigned count);

参数：cdev：字符设备结构；fops：文件操作表；dev：设备号；count：设备数量

返回：cdev_init 无返回值；cdev_add 成功返回 0，失败返回负 errno。

注意：cdev_add 之后设备才进入内核的字符设备表；注销时对应 cdev_del。

class_create模块初始化
struct class *class_create(const char *name);

参数：name：设备类名，会出现在 /sys/class 下

返回：成功返回 class 指针；失败返回 ERR_PTR，需要 IS_ERR/PTR_ERR 处理。

注意：6.4+ 常见单参数写法；旧内核常见 class_create(THIS_MODULE, name)。以目标头文件为准。

device_create模块初始化
struct device *device_create(const struct class *class, struct device *parent, dev_t devt, void *drvdata, const char *fmt, ...);

参数：class：设备类；parent：父设备，可为 NULL；devt：设备号；drvdata：驱动私有数据；fmt...：设备名

返回：成功返回 device 指针；失败返回 ERR_PTR。

注意：成功后会触发 uevent，udev 据此创建 /dev 节点；看到节点不代表 open/read 一定正确。

file_operationsVFS 分派
static const struct file_operations led_fops = { .owner = THIS_MODULE, .open = ..., .read = ..., .write = ..., .release = ... };

参数：owner：通常为 THIS_MODULE；其余字段：对应的回调函数

返回：结构体本身无返回值；回调按各自签名返回。

注意：open/read/write/release 的签名必须与内核头文件一致；不要自创参数。

copy_from_user进程上下文
unsigned long copy_from_user(void *to, const void __user *from, unsigned long n);

参数：to：内核目标地址；from：用户源地址；n：字节数

返回：返回未复制的字节数；0 表示全部成功。

注意：write 回调里常见用法；失败返回 -EFAULT。不要用 memcpy 直接复制用户地址。

模块加载后执行 led_init。此时还没有设备号、cdev、设备类，也没有 /dev 节点。

常见错误与排查

01

insmod 成功，但 /dev/led_demo 不存在。

常见原因
device_create 失败、uevent 没有送达 udev，或设备类/设备名写错。
排查 / 修复
看 dmesg 与 /sys/class/led_demo/；确认 device_create 返回值；检查 udev 是否运行。也可以临时用 mknod 验证主次设备号。
02

编译报 class_create 参数数量不匹配。

常见原因
代码按旧内核的两参数写法，目标内核已经是 6.4+ 的单参数形式（或反向）。
排查 / 修复
查看目标内核 include/linux/device/class.h；不要靠猜，按当前头文件改。
03

rmmod 报 module is in use，或卸载后进程仍能操作旧节点。

常见原因
仍有进程打开设备，或卸载顺序错误导致节点/结构残留。
排查 / 修复
用 lsof/fuser 找到持有者；先 device_destroy 再 class_destroy、cdev_del、unregister；确保 release 路径完整。
04

read/write 返回 -1，errno 为 EFAULT，或内核直接 Oops。

常见原因
用户指针被直接解引用，或 copy_*_user 返回值未检查。
排查 / 修复
用 copy_to_user/copy_from_user；检查长度与 *ppos；失败返回 -EFAULT。
