并发与同步

竞态条件不是“概率小”，而是“迟早发生”。用自旋锁、互斥锁、信号量、完成量与 RCU 给共享数据排班。

竞态原子操作自旋锁互斥锁信号量完成量RCU

学习目标

  • 识别多核、中断、抢占带来的三类并发来源
  • 根据能否睡眠选择自旋锁或互斥锁
  • 解释“锁保护的是数据，不是代码行”
ONE SENTENCE

并发是多个执行流同时访问共享数据；同步就是用规则保证结果可预测，而不是“碰运气”。

生活化比喻

两个人改同一张表，必须约定谁先动笔

自旋锁像“占着门不睡觉”：拿不到就原地等，适合几行代码的极短操作。互斥锁像“拿钥匙可以睡”：拿不到就先睡，适合可能耗时或需要等待的操作。信号量像停车位，完成量像“我干完了，通知你”。

为什么重要 / 用在哪里

  • 多核、抢占和中断会让“看起来顺序执行”的代码真正并行；竞态不是理论问题。
  • 锁选错不只是变慢：在原子上下文睡眠可能直接触发 BUG，在中断里用错锁可能死锁。
  • 驱动对象有生命周期；锁、引用计数和释放顺序共同决定卸载时是否安全。
  • 面试与实战都爱问“这里为什么不用 mutex”“为什么要 irqsave”，答案取决于上下文。

核心概念

race condition

竞态条件

多个执行流并发访问共享数据，结果依赖执行顺序。即使概率很低，也可能在压力、SMP 或中断下稳定复现。

atomic operations

原子操作

对单个计数器的不可分割操作，例如 atomic_inc/atomic_dec。它只保证这一个操作原子，不自动保护一整段复杂逻辑。

spinlock

自旋锁

忙等锁，持有期间不能睡眠。临界区必须极短；若数据也会被硬中断访问，通常用 spin_lock_irqsave 关闭本地中断。

mutex

互斥锁

可睡眠的互斥锁，适合进程上下文和可能较长的临界区。不能在硬中断/软中断上下文使用；持锁期间避免调用可能睡眠的函数。

semaphore / completion

信号量与完成量

信号量是计数型睡眠锁，历史上常用于生产者-消费者；完成量用于“一边等另一边完成”的一次性/阶段性同步。新代码优先选择更窄语义的原语。

Read-Copy-Update

RCU

读多写少的同步机制：读者在 RCU 读侧临界区中访问旧版本，写者发布新版本并延迟回收旧对象。读侧通常不能睡眠，写者用 synchronize_rcu 等待宽限期。

关键 API 与代码

代码是学习示意，以 Linux 6.x / ARM64 为默认基线。每个 API 都列出参数与返回值；不要只抄代码， 先确认它运行在什么上下文、失败时怎么回滚。

自旋锁：与硬中断共享数据

API 逐个解释
spin_lock_irqsave进程上下文或中断上下文；临界区不能睡眠
void spin_lock_irqsave(spinlock_t *lock, unsigned long flags);

参数：lock：自旋锁；flags：保存本地中断状态

返回：无返回值；获取锁并关闭本地中断。

注意：必须与 spin_unlock_irqrestore 配对，且在同一执行流中使用同一个 flags 变量。

spin_unlock_irqrestore与加锁配对
void spin_unlock_irqrestore(spinlock_t *lock, unsigned long flags);

参数：lock：自旋锁；flags：之前保存的中断状态

返回：无返回值；释放锁并恢复中断状态。

注意：不要用 spin_unlock 替代；恢复错误的中断状态会破坏系统。

互斥锁：进程上下文、可以睡

API 逐个解释
mutex_lock_interruptible进程上下文，可以睡眠
int mutex_lock_interruptible(struct mutex *lock);

参数：lock：互斥锁

返回：成功返回 0；被信号打断返回 -EINTR（调用方通常转 -ERESTARTSYS）。

注意：若不需要被信号打断，可用 mutex_lock；中断上下文禁止使用 mutex。

mutex_unlock与 mutex_lock 配对
void mutex_unlock(struct mutex *lock);

参数：lock：互斥锁

返回：无返回值。

注意：锁必须由持有者释放；不要跨线程“借锁”。

原子计数：只保护单个操作

API 逐个解释
atomic_inc / atomic_dec任何上下文
void atomic_inc(atomic_t *v);
void atomic_dec(atomic_t *v);

参数：v：原子变量指针

返回：无返回值；操作不可分割。

注意：它不保护多个变量之间的一致性，也不替代临界区。

6.x 是默认基线，旧版只做定位提示。发行版可能回移植补丁，迁移时请直接看目标内核头文件。

版本对照并发 / 自旋锁

自旋锁变体与中断

6.x 基线

6.x：与硬中断共享数据时常用 spin_lock_irqsave/spin_unlock_irqrestore

旧版对照

数据不与中断共享、或中断已关闭时，可能只用 spin_lock/spin_unlock

影响：选错变体可能死锁、丢中断或放大中断延迟；锁保护的是数据，不是代码行。

边界：锁的选择取决于上下文与共享对象，不是固定模板。

常见错误与排查

01

日志出现 BUG: sleeping function called from invalid context。

常见原因
在自旋锁临界区、硬中断或软中断上下文调用了可能睡眠的函数（msleep、mutex_lock、copy_to_user 等）。
排查 / 修复
把可能睡眠的工作移到进程上下文（workqueue/threaded IRQ）；重新检查持锁范围；不要在原子上下文调用阻塞 API。
02

系统偶发死锁，或在中断频繁时卡住。

常见原因
进程上下文只用 spin_lock，而同一把锁也被硬中断获取；中断在等锁，进程持锁等中断。
排查 / 修复
与硬中断共享数据时使用 spin_lock_irqsave/spin_unlock_irqrestore；统一锁顺序；用 lockdep 检查。
03

多线程计数偶尔少 1，压力测试才复现。

常见原因
用普通 int 做 ++/--，读-改-写不是原子操作；或保护范围没有覆盖完整逻辑。
排查 / 修复
单计数器使用 atomic_t；复合逻辑使用锁；用 KCSAN/lockdep 辅助定位。

TAKE IT WITH YOU

记住这三句话

  1. 01

    竞态来自并发执行流；锁保护的是共享数据，不是某一行代码。

  2. 02

    不能睡眠的上下文用自旋锁且临界区极短；可能睡眠的进程上下文用互斥锁。

  3. 03

    与硬中断共享数据时，优先考虑 irqsave 变体并统一锁顺序。
