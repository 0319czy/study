设备树

设备树是板级“说明书”：dts/dtsi/dtb 描述硬件，compatible 把设备与驱动牵线。学会读节点、属性与 overlay。

ONE SENTENCE

设备树是板级硬件的“说明书”：dts/dtsi 描述节点与属性，编译成 dtb 交给内核，compatible 把设备与驱动牵线。

生活化比喻

设备树是设备说明书，compatible 是型号标签

板子上有 I2C 控制器、传感器、GPIO、时钟和中断线，但内核不可能为每块板子写死一份代码。设备树把“这块板子上有什么、接在哪、用什么参数”写成树；驱动只看型号标签（compatible）和资源，决定自己能不能接手。

一份可读的说明书
dtsi
可复用的公共章节
dtb
编译后的说明书
node
一个设备/总线节点

节点的参数项

overlay
给说明书打的补丁

为什么重要 / 用在哪里

  • ARM64 板卡大量依赖设备树描述引脚、时钟、电源、中断与总线；不会读 dts 就很难定位驱动为什么不 probe。
  • compatible 是驱动匹配的核心字符串；一个字符不一致，probe 就不会执行。
  • reg、interrupts、clocks、gpios 等属性决定驱动拿到的资源；写错会表现为“驱动加载了但设备不工作”。
  • overlay 让同一份基础 dts 适配不同扩展板，但也带来“补丁没生效”的新问题。

核心概念

device tree source / include / blob

dts / dtsi / dtb

dts 是板级源文件，dtsi 是可复用片段，dtb 是编译后的二进制。内核启动时读取 dtb，展开成设备树并创建设备。

node / property

节点与属性

节点表示设备或总线，属性是键值对。节点名常带 unit address（如 sensor@48），属性值可以是字符串、整数数组、phandle 等。

compatible

compatible

字符串列表，声明设备兼容哪些驱动。驱动侧用 of_match_table 提供同样的字符串；匹配成功后 bus 才会调用 probe。

reg / #address-cells / #size-cells

reg 与地址空间

reg 描述寄存器地址/长度或总线地址。父节点的 #address-cells/#size-cells 决定 reg 的 cell 数量；写错会导致地址解析错误。

interrupts / clocks / gpios

中断与资源

设备树把中断号、触发方式、时钟、GPIO、复位等资源交给驱动。具体 cell 数量取决于中断控制器与绑定文档。

device tree overlay

overlay

在基础 dtb 上追加/修改节点的补丁，常用于扩展板。应用失败时，节点可能完全不存在，驱动自然不会 probe。

API 逐个解释
compatible节点属性
compatible = "acme,th02";

参数：厂商前缀,型号，通常用逗号分隔；也可列多个兼容项

返回：无返回值；作为设备树属性被内核解析。

注意：驱动 of_match_table 中的字符串必须与这里完全一致；大小写和连字符都算。

regI2C/SPI/MMIO 节点
reg = <0x48>;

参数：地址/偏移；长度由父节点 #address-cells/#size-cells 决定

返回：无返回值；提供设备地址。

注意：I2C 常用 7 位地址；SPI 常用片选号；MMIO 常是地址 + 长度两个 cell。

status节点属性
status = "okay";

参数："okay" 启用；"disabled" 禁用

返回：无返回值；内核据此决定是否创建设备。

注意：节点存在但 status 为 disabled 时，驱动通常不会 probe；先查这一项。

overlay：给已有节点打补丁

API 逐个解释
&labeloverlay 源文件
&i2c0 { ... };

参数：label：基础 dts 中定义的节点标签

返回：无返回值；overlay 编译时解析引用。

注意：标签拼写错误会导致 overlay 编译/应用失败；不同 bootloader 的加载方式不同。

版本对照卡

6.x 是默认基线，旧版只做定位提示。发行版可能回移植补丁，迁移时请直接看目标内核头文件。

版本对照设备树 / 驱动匹配

设备树匹配与 match data

6.x 基线

6.x：of_match_table 提供 compatible，驱动用 device_get_match_data 等 helper 取数据

旧版对照

旧代码常先 of_match_device() 再读取 match->data

影响：compatible 是设备树与驱动之间的字符串契约；改错一个字符就可能导致 probe 不执行。

边界：helper 的可用性与签名以目标内核头文件为准；不是所有平台都用设备树。

步骤 1
从根节点开始

设备树从 / 根节点展开。compatible 描述整块板子，model 是给人看的型号。

观察问题：节点存在、reg 也写了，为什么驱动仍可能不 probe？compatible 在匹配中起什么作用？

结论提示：节点存在只是硬件描述；还需要 status 开启、compatible 与 of_match_table 完全一致、驱动已注册，probe 才会执行。

节点名、地址、中断 cells 均为教学示例；真实值必须来自 SoC 手册与板级 dts。

常见错误与排查

01

驱动加载了，但 probe 完全不执行。

常见原因
compatible 与 of_match_table 不一致；节点 status 为 disabled；overlay 未加载；驱动未注册。
排查 / 修复
对照设备树与驱动的字符串；检查 /proc/device-tree 或 /sys/firmware/devicetree；看 dmesg 是否有 deferred probe。
02

驱动 probe 了，但寄存器地址/中断号明显不对。

常见原因
reg 的 cell 数量与父节点 #address-cells/#size-cells 不匹配；中断 cell 数量不符合控制器绑定。
排查 / 修复
查 SoC 手册与 binding 文档；对照父节点 cells；用 /sys/firmware/devicetree 检查解析结果。
03

扩展板节点不存在，基础板功能正常。

常见原因
overlay 没有加载、标签不存在、加载顺序错误，或 bootloader 没有把 overlay 合并进 dtb。
排查 / 修复
确认 bootloader/OS 的 overlay 配置；检查 /proc/device-tree 是否出现节点；先验证基础 dtb。

记住这三句话

  1. 01

    dts/dtsi 是源文件，dtb 是编译结果；overlay 是给基础设备树打的补丁。

  2. 02

    compatible 是设备与驱动的字符串契约；reg/中断/时钟/GPIO 描述资源。

  3. 03

    节点存在不等于 probe 成功：还要匹配、status 开启、驱动注册。
