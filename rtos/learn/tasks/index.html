任务与调度

任务的状态、优先级、抢占、时间片与空闲任务，是读懂任何 RTOS 的第一课

一句话解释

任务是员工，调度器是经理：谁先上 CPU、谁让位、谁能被挂起，由任务状态和优先级共同决定。

学习目标

  • 1说清任务的四种状态（就绪、运行、阻塞、挂起）以及它们之间如何迁移
  • 2解释优先级、抢占、时间片三者的关系，并能配置 configUSE_PREEMPTION 与 configUSE_TIME_SLICING
  • 3用 xTaskCreate 创建任务、用 vTaskDelayUntil 写周期任务，并逐项说明参数含义
  • 4知道空闲任务从哪里来、两种钩子函数在什么上下文执行、什么事绝对不能做

生活化比喻

任务 = 员工，调度器 = 经理

把 CPU 想成餐厅里唯一的一口灶。员工（任务）各自有活要干：掌勺、收银、打扫。经理（调度器）手里有一张排班表：谁的岗位最紧急（优先级），谁就先上灶；掌勺师傅等食材（阻塞）时，灶台就交给收银员；两个岗位一样紧急时，每人干一个时间片再换班（时间片轮转）。被停职（挂起）的员工不会自己回来，必须经理叫他才行。经理还专门安排了一个实习生在没人干活时擦桌子（空闲任务），保证灶台不会空着。

为什么重要 / 用在哪里

裸机的超级循环是“一个人按固定顺序干所有活”，一旦某个环节要等待（等串口、等 ADC 转换、等延时），整条流水线就卡住。把功能拆成多个任务后，等待变成“阻塞”——内核把 CPU 交给别人，而不是原地空转。但多任务也带来新的问题：谁先运行、运行多久、会不会有人一直抢不到 CPU？这些问题的答案就是调度策略。理解状态与优先级，你才能写出“关键任务永远及时、非关键任务不拖后腿”的程序，也才能在出现“低优先级任务完全不动”“周期任务越跑越慢”时迅速定位原因。

工业控制器：故障保护任务必须比采样、显示、通信任务更快拿到 CPU消费电子：按键响应要跟手，屏幕刷新要均匀，后台日志可以慢慢来电机控制：控制环需要严格固定周期，用 vTaskDelayUntil 抵消执行时间抖动低功耗设备：没有任务可跑时进入空闲任务，通过空闲钩子进入睡眠多传感器融合：采集、滤波、上报按不同频率拆成独立任务，互不阻塞

任务到底是什么？

裸机程序只有一条执行路径：从 main 进入 while (1)，被中断打断、处理完再回来。任务（task）则是一条“独立的执行流”：它有自己的栈、自己的程序计数器和自己的局部变量，内核可以在任意时刻把 CPU 从一条执行流切换到另一条。两条执行流彼此看不见对方的局部变量，只能通过内核对象或全局变量交换数据。

每个任务由两块内存组成：一份任务栈，保存局部变量、函数调用返回地址和寄存器现场；一个任务控制块（TCB，Task Control Block），记录任务名、优先级、当前状态、栈顶指针等元信息。FreeRTOS 的 xTaskCreate 会从堆里分配这两块内存，所以“任务栈开多大”直接决定 RAM 够不够用。

  • 任务入口函数是无限循环（for (;;)），返回意味着未定义行为
  • 任务栈深度单位通常是“字”而不是字节，移植层不同可能不同
  • 任务句柄（TaskHandle_t）是内核发给你的“工牌”，删除、挂起、通知都要用它
  • 任务之间是并发而不是并行：单核上同一时刻只有一个任务真正占用 CPU

第一次出现就记住：调度的五个词

任务Task

状态机为教学简化：FreeRTOS 内部还维护多个就绪/延时/挂起链表，并处理优先级继承、删除等路径。

四种状态：任务的一生只有这几个格子

FreeRTOS 的任务可以在四个状态之间迁移：运行（Running）、就绪（Ready）、阻塞（Blocked）、挂起（Suspended）。单核系统里，任何时刻最多只有一个任务处于运行态；所有“能跑但没抢到 CPU”的任务都排队在就绪态；阻塞态的任务有一个明确的“等待条件”（等延时到期、等信号量、等队列数据）；挂起态则是一个没有超时的“冷冻格”。

理解状态的关键，是分清“谁把它移出调度”和“谁能把它放回来”。阻塞是任务自己申请等待，并且条件满足或超时后内核会自动唤醒它；挂起是别人（或自己）用 vTaskSuspend 强制的，只有 vTaskResume 能让它回来。这也是初学者最常混淆的一点。

  • 就绪 → 运行：调度器选中了它（优先级最高且未被抢占）
  • 运行 → 就绪：被更高优先级任务抢占，或时间片用完
  • 运行 → 阻塞：调用 vTaskDelay、等待信号量/队列且未立即满足
  • 运行/就绪 → 挂起：调用 vTaskSuspend，之后不再参与调度
  • 挂起 → 就绪：调用 vTaskResume 或 xTaskResumeFromISR

挂起不是“更长的阻塞”

阻塞（Blocked）一定有一个唤醒条件，比如 100 ms 延时、信号量到来；挂起（Suspended）没有任何超时，任务会一直停在那里，直到有人调用 vTaskResume。把 vTaskSuspend 当成“睡一会儿”来用，最常见的后果就是任务再也不跑了。需要休眠请用 vTaskDelay 或 vTaskDelayUntil。

优先级：谁先上 CPU？

FreeRTOS 的优先级是一个非负整数，数值越大优先级越高，范围是 0 到 configMAX_PRIORITIES - 1。空闲任务固定是 0 号（tskIDLE_PRIORITY），通常是你见过的最低优先级。任何时刻，调度器都倾向于让“就绪任务里优先级最高的那个”运行，这正是实时系统表达“谁更紧急”的方式。

优先级不是越高越好。把某个任务设成最高优先级，等于让它拥有“随时打断所有人”的特权；如果它又长时间不让出 CPU，低优先级任务就会被饿死。合理的做法是先按“截止时间”排序：错过会出安全事故的最紧急，其次是人机交互，最后是日志、上报这类可延迟的工作。

  • 数值大小：FreeRTOS 越大越优先，与 Zephyr / RT-Thread 方向相反
  • configMAX_PRIORITIES 决定优先级层数，设大了多占一点 RAM
  • 每个优先级通常至少留一个任务，铺满所有层级往往说明设计没想清楚
  • 优先级相同的任务之间，靠时间片轮转而不是靠“先创建先运行”

抢占与时间片：两种“换人”方式

抢占（preemption）解决“紧急任务能不能立刻上”的问题。configUSE_PREEMPTION 为 1 时，只要一个比当前任务优先级更高的任务进入就绪态（被延时唤醒、被信号量唤醒、中断里被唤醒），调度器就会立刻切换过去，不等当前任务主动让出。为 0 时系统变成协作式：只有当前任务阻塞、让出或被中断唤醒更高优先级任务时才会换人，行为更可预测，但响应变慢。

时间片（time slicing）解决“优先级相同的任务怎么分 CPU”的问题。configUSE_TIME_SLICING 为 1 时，每个 tick 中断都会检查一次：如果当前优先级的就绪队列里还有别的任务，就轮到下一个。这样两个同优先级任务就能“你一个 tick、我一个 tick”地推进，而不是先创建的一直跑。

两个宏是两件事：抢占管“不同优先级之间”，时间片管“同优先级之间”。工程里最常见的是两个都开；调试时序问题时也常临时关掉时间片，让同优先级任务的执行顺序变得可复现。具体行为受版本与移植层影响的地方，以官方文档和具体版本为准。

  • configUSE_PREEMPTION = 1：高优先级任务就绪即刻抢占，实时性最好
  • configUSE_PREEMPTION = 0：协作式，切换点可预测，但响应变慢
  • configUSE_TIME_SLICING = 1：同优先级任务按 tick 轮转，避免“先来的独占”
  • 关掉时间片后，同优先级任务会一直运行到阻塞或让出，不要依赖“公平”

空闲任务与两种钩子

空闲任务（Idle Task）是调度器启动时自动创建的任务，优先级为 0，只在没有任何其他就绪任务时运行。它不是“没事干”，而是内核的基础设施：被删除任务的栈和 TCB 会在空闲任务里回收，所以哪怕你不开任何钩子，空闲任务也必须存在。它的栈由 configMINIMAL_STACK_SIZE 决定。

钩子函数（hook）是内核在特定时刻回调你的函数。configUSE_IDLE_HOOK 打开后，内核每次运行空闲任务都会调用 vApplicationIdleHook，这是做低功耗休眠、喂看门狗、后台统计的最佳位置；configUSE_TICK_HOOK 打开后，每个 tick 中断都会调用 vApplicationTickHook，可以用来做简单的 tick 级计时，但它运行在中断上下文里，必须极短。

两个钩子的函数名由内核固定，你不能改名，也不能把它们当成任务来创建。空闲钩子里一旦调用 vTaskDelay、等待信号量或做耗时运算，空闲任务就被阻塞，而内核又依赖它回收内存，后果通常是很隐蔽的随机故障。

  • 空闲任务优先级最低，只在系统“闲下来”时运行
  • 空闲钩子适合低功耗、喂狗、统计，不适合阻塞与长计算
  • tick 钩子运行在 tick 中断里，比空闲钩子更“危险”，只能放几个指令级的操作
  • 中断服务程序绝对不能调用会阻塞的 API，也不能调用非 FromISR 版本

栈开多大、优先级怎么排？

栈大小是最容易被低估的参数。任务栈要容纳局部变量、函数调用链（每一层都有自己的局部变量和返回地址），还要容纳中断嵌套时的寄存器现场；如果用了浮点或 printf，栈需求会明显上升。经验做法是先用一个偏大的值跑通，再用 uxTaskGetStackHighWaterMark 看历史最小剩余量，按实测结果收窄，并留出 30% 以上余量。

优先级应当按“紧急程度 + 截止时间”来排，而不是按代码写起来的顺序。设计时先列出每个任务的周期和最坏执行时间，用响应时间分析或简单的 CPU 利用率估算判断是否可调度；再检查有没有“高优先级任务长时间不让出 CPU”的情况。如果两个任务真的同等重要，就给同优先级并让时间片轮转，而不是硬分出高低。

  • 中断优先级与任务优先级是两套体系，别混为一谈
  • 高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断不能调用 FromISR 系列 API
  • 优先级配置错了，RTOS 帮不了你：饿死、抖动、优先反转都会出现
  • 调试期打开 configASSERT 与栈溢出检测，比事后定位随机 HardFault 便宜得多

用实验建立直觉

写两个优先级不同的任务：低优先级任务每 100 ms 翻转一次 LED，高优先级任务里写一个不阻塞的 for 循环。你会看到 LED 完全不闪——这不是 RTOS 坏了，而是低优先级任务永远抢不到 CPU。再把高优先级任务里的循环换成 vTaskDelay(1)，LED 立刻恢复。这个不到 20 行的实验，比读十页调度器文档更能让你记住“阻塞”的意义。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

把 vTaskSuspend 当成“睡一会儿”

症状
任务调用 vTaskSuspend(NULL) 后永远不再运行，系统功能缺失但没有任何报错。
原因
挂起（Suspended）没有超时机制，任务不会自己醒来，只有 vTaskResume 或 xTaskResumeFromISR 能恢复。
修复
需要定时休眠用 vTaskDelay / vTaskDelayUntil；确实要挂起时，必须保存句柄并确保有明确的恢复路径。
02

高优先级任务不让出 CPU，低优先级被饿死

症状
低优先级任务完全不动，LED 不闪、日志不打印；看门狗可能复位，但调试器里一切“正常”。
原因
高优先级任务里写了长循环或忙等（例如 while (!flag)），调度器永远找不到让低优先级运行的机会。
修复
把等待改成阻塞式（等信号量、等队列、vTaskDelay），让 CPU 在等待期间交出去；用运行时统计（如 vTaskGetRunTimeStats）确认各任务的 CPU 占比。
03

按字节估算栈，结果栈溢出

症状
运行一段时间后随机 HardFault，或者在某个函数调用较深时突然跑飞。
原因
FreeRTOS 的 usStackDepth 单位通常是“字”而不是字节，按字节数填会小 4 倍；另外调用深度和中断嵌套也没有算进去。
修复
查清移植层的单位，先把 configCHECK_FOR_STACK_OVERFLOW 设为 2，用 uxTaskGetStackHighWaterMark 实测后再定栈大小并留足余量。

记住这三句话

  1. 1

    任务是带独立栈的执行流；状态决定它能不能被调度，优先级决定它排在哪。

  2. 2

    抢占管不同优先级，时间片管同优先级；两者都由配置宏控制，行为必须写进设计文档。

  3. 3

    空闲任务不是可有可无的装饰，钩子函数必须短且不能阻塞，否则会引出最隐蔽的故障。
