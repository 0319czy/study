中断与时间管理

ISR 只接快递，慢活交给任务：FromISR、临界区、软件定时器与 tick

一句话解释

中断决定系统“反应快不快”，时间管理决定系统“准不准”；两者都靠克制——ISR 越短，系统越稳。

学习目标

  • 1说清 ISR 与任务的区别，记住中断服务程序里“能做什么、绝不能做什么”
  • 2会用 FromISR 系列 API，并正确处理 xHigherPriorityTaskWoken 与 portYIELD_FROM_ISR
  • 3理解延迟处理模式，知道为什么慢活必须搬出中断
  • 4掌握临界区、软件定时器与 timer daemon task、tick 与时间戳的正确用法

生活化比喻

门铃、前台与闹钟

你在写报告（任务），门铃响了（中断），你放下笔去开门，接过快递（ISR），然后回到原位继续写。如果你开门后还顺便拆箱、试用、打电话（长 ISR），报告就迟迟写不完。聪明的做法是把包裹放到传送带（队列）上，让专门的同事（延迟处理任务）去拆。软件定时器则像办公室的闹钟：闹钟本身不会干活，它只是提醒值日生（定时器守护任务）该做什么，值日生忙不过来时，提醒就会被推迟。

为什么重要 / 用在哪里

嵌入式系统几乎所有外部事件都以中断形式到来：串口收字节、按键按下、定时器到期、ADC 转换完成、总线收到报文。中断处理得不好，系统会出现“平时正常、偶发死机”“响应忽快忽慢”“高优先级任务迟迟不跑”这类最难查的问题。反过来，把 ISR 写短、把慢活挪进任务、把时间建立在 tick 与时间戳上，系统的响应时间就变得可分析、可预测。

串口通信：逐字节接收中断 + 队列 + 协议解析任务按键与传感器：外部中断唤醒，任务里做消抖与业务判断电机与电源控制：硬件定时器中断产生固定周期采样与换相低功耗设备：RTC/LPTIM 定时唤醒，其余时间休眠工业总线：CAN/USB 中断把报文交给协议任务处理

中断：内核世界里唯一能“插队”的角色

中断（Interrupt）是 CPU 收到外部或内部事件后，暂停当前执行流、跳去执行中断服务程序（Interrupt Service Routine，ISR），执行完再返回原处的机制。在 RTOS 里，中断的优先级永远高于任何任务：只要中断到来且未被屏蔽，CPU 就必须先处理它。

这个特性让系统能对紧急事件做出快速反应，但也埋下隐患：ISR 执行得越久，所有任务被推迟得越久。很多“RTOS 不实时”的抱怨，根源都是一段写得太长的 ISR，或者一段关中断太久的临界区。

  • ISR 是“公共资源”：它打断任何人，所以必须短、必须可重入
  • 中断优先级决定谁先被响应，内核只在允许的范围内屏蔽中断
  • ISR 不能阻塞，因为中断上下文里没有“任务”可以让出 CPU
  • 慢活（解析、计算、打印、写 Flash）一律搬到任务里做

结论提示（先观察再展开）

中断延迟（硬件入栈 + 内核入口）决定「多快能开始处理」，上下文切换开销（保存 + 恢复现场）决定「进出一次要花多少钱」，ISR 时长决定「别人被冻多久」。ISR 只做救急动作，把软件处理通过通知/队列下移到任务，才能用更长的任务响应延迟换取更短的中断关闭时间——这是实时系统设计的核心取舍。

简化模型：中断延迟、保存/恢复现场、ISR 体均为示意常数，未建模多级中断嵌套、尾链（tail-chaining）与 FPU 惰性压栈；CPU 占用只统计「中断本身」，不含任务与调度器开销。

四个必须分清的概念

中断服务程序ISR
中断到来时执行的处理函数，运行在中断上下文，不能阻塞。
中断优先级Interrupt Priority
决定多个中断同时到来时谁先被 CPU 响应；ARM Cortex-M 上数值越小优先级越高。
延迟处理Deferred Processing
ISR 只做最少的记录与通知，把耗时工作交给任务完成的设计模式。
临界区Critical Section
暂时屏蔽中断或挂起调度器的一小段代码，用于保护共享数据。
从 ISR 调用FromISR API
FreeRTOS 专门提供给中断上下文的 API 版本，名称以 FromISR 结尾。

ISR 的五条铁律

中断服务程序的写法与普通函数完全不同。原则只有一句：在 ISR 里，你借用的是所有人的时间和资源（CPU 时间，以及被打断任务栈上的异常现场），所以必须尽快归还。

  • 只调用以 FromISR 结尾的 FreeRTOS API；普通版本（如 xQueueSend）可能阻塞，禁止在 ISR 中使用
  • 绝不阻塞：不能用 vTaskDelay，不能带超时等待队列或信号量
  • 尽量短：读寄存器、清标志、发通知、置位信号量，然后立刻返回
  • 不用 printf、浮点运算和大局部数组：耗时不可控，还会吃掉被中断任务的栈
  • 中断优先级高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 时，一个 FreeRTOS API 都不能调用

vTaskDelay 出现在 ISR 里，几乎必定炸

中断上下文里没有“当前任务”可以阻塞，内核也无法为它保存现场。在 ISR 中调用非 FromISR API 或任何阻塞 API 都属于未定义行为，常见现象是断言失败、HardFault 或随机死机。开发阶段请打开 configASSERT，并确保中断优先级配置正确，让这类错误尽早暴露。

延迟处理：把慢活从“插队的人”手里拿走

延迟处理（deferred processing）是 RTOS 的核心套路：ISR 只负责把事件“记录”下来并通知任务，真正的组包、校验、计算、显示、写存储由任务完成。这样中断恢复得很快，系统对所有事件的响应都更有保障，而且慢活还能享受调度器的优先级与超时管理。

按传递内容的复杂度，常见有三种载体：队列（要带数据）、任务通知（最轻量，适合点对点）、信号量（只表示“事件发生了”）。

  • 队列：字节流、报文、传感器采样值的标准选择，天然带缓冲
  • 任务通知：只有一个接收者、数据量很小时效率最高，省掉队列控制块
  • 二值信号量：只表达“某件事发生了”，不携带数据，适合按键、DMA 完成
  • 延迟任务的优先级要设计好：高于普通业务以保证及时处理，但不能抢了硬实时任务的 CPU
  • 队列满时要明确策略：丢弃最新、覆盖最旧、还是记一次溢出计数

忘了 portYIELD_FROM_ISR 会怎样？

如果 xHigherPriorityTaskWoken 被置为 pdTRUE，但你没调用 portYIELD_FROM_ISR，被唤醒的高优先级任务要等到下一个 tick 中断才会运行。这会让响应时间凭空多出最多一个 tick，表现为“延迟忽长忽短”。注意宏的参数形式随端口与版本变化：多数 Cortex-M 端口写作 portYIELD_FROM_ISR(x)，个别端口或旧版本没有参数，移植时以 portmacro.h 中的定义为准。

临界区：保护共享数据，但别把系统也锁住

临界区（critical section）用来保护“多个任务或中断都会访问”的共享数据，例如一个被任务读写、被 ISR 修改的计数器。FreeRTOS 提供两套保护手段，代价不同，用途也不同。

  • taskENTER_CRITICAL / taskEXIT_CRITICAL：屏蔽优先级不高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断，可嵌套，必须成对出现
  • taskENTER_CRITICAL_FROM_ISR / taskEXIT_CRITICAL_FROM_ISR：ISR 里可用的版本，后者需要传入前者返回的保存值
  • vTaskSuspendAll / xTaskResumeAll：只挂起调度器、不关中断，适合较长但不希望被切换打断的操作
  • 挂起调度器期间不要调用任何可能阻塞的 API；也不要在其中再嵌套关中断，语义容易混乱
  • 临界区长度经验值：控制在几十微秒内，绝不能在临界区里等外设、读写 Flash 或延时

结论提示（先观察再展开）

软件定时器 = 定时器对象 + 命令队列 + 守护任务（Tmr Svc）。Start/Stop/Reset/ChangePeriod 全都是入队命令，由守护任务串行执行，所以不需要额外的互斥量；回调也运行在守护任务上下文，必须快进快出——回调一阻塞，所有定时器连同队列命令一起迟到。周期定时器到期后自动重装载（到期时间 += 周期），单次定时器触发一次即回休眠。

教学简化：实际的定时器命令通过 configTIMER_QUEUE_LENGTH 配置的队列传递，守护任务还负责在到期时把回调排入自己的“回调处理”流程；本节把队列与到期处理画成一条流水线，便于理解先后顺序。

软件定时器：闹钟由“值日生”执行

FreeRTOS 的软件定时器（software timer）不是硬件定时器，它依靠 tick 计时，回调函数在定时器守护任务（timer daemon task，也叫 timer service task）的上下文里执行。你在任务或中断里调用的 xTimerStart，本质上只是往守护任务的命令队列里塞一条命令，真正执行由守护任务完成。

因此定时器的准时性取决于三件事：守护任务的优先级是否足够高、命令队列是否堵塞、系统里有没有更高优先级的任务长期占用 CPU。

  • configUSE_TIMERS = 1 时，调度器启动会自动创建守护任务
  • 守护任务优先级由 configTIMER_TASK_PRIORITY 决定，命令队列长度由 configTIMER_QUEUE_LENGTH 决定
  • 守护任务栈由 configTIMER_TASK_STACK_DEPTH 决定，回调里用多少栈都算在它头上
  • 回调函数里禁止阻塞，一旦卡住，所有定时器一起停摆
  • 需要硬实时精度的周期动作，请用硬件定时器中断或高优先级周期任务

Tick 与时间戳：系统的心跳

tick 是内核的心跳：硬件定时器（Cortex-M 上通常是 SysTick）周期性产生中断，内核每来一拍就把 tick 计数加一，并检查有没有任务到期。configTICK_RATE_HZ 决定一拍多长，常见配置是 1000，也就是 1 tick 等于 1 ms。

需要“现在几点”时，用 xTaskGetTickCount()；在中断里必须用 xTaskGetTickCountFromISR()。测量一段耗时的正确写法是无符号相减，而不是比较绝对大小。

  • pdMS_TO_TICKS(ms)：把毫秒换算成 tick，避免手写乘法出错
  • 耗时测量：先存 t0 = xTaskGetTickCount()，结束时 (now - t0) * 1000 / configTICK_RATE_HZ 即为毫秒
  • TickType_t 在常见配置下是 32 位，1000 Hz 时约 49.7 天回绕一次；用无符号相减可安全跨越回绕
  • tick 的分辨率就是 1/configTICK_RATE_HZ，不要用它做微秒级测量
  • 小时、天级别的计时请用 RTC 或专门的时间服务，不要靠 tick 累加
  • vApplicationTickHook 在 tick 中断里执行，必须极短，否则会拖垮整个系统

软件定时器不是“硬实时闹钟”

守护任务优先级不够高、命令队列已满、或者有更高优先级任务长期占用 CPU 时，定时器回调都会被推迟。对“到点必须执行”的动作（如电机换相、精确采样），请用硬件定时器中断；软件定时器更适合超时、心跳、延时动作这类对抖动不敏感的场景。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

在 ISR 里调用普通版 API

症状
系统偶发死机、断言失败或 HardFault，仿真器里看到程序停在奇怪的位置。
原因
xQueueSend、xSemaphoreTake 等普通 API 可能在内部阻塞或触发调度，在中断上下文里没有任务可调度，属于未定义行为。
修复
中断里一律使用 FromISR 版本；开启 configASSERT，并检查中断优先级是否允许调用 FreeRTOS API。
02

设置 xHigherPriorityTaskWoken 却忘记触发切换

症状
高优先级任务明明收到了信号，却总要等下一个 tick 才运行，响应时间莫名多出 1 ms 级别。
原因
ISR 末尾漏了 portYIELD_FROM_ISR，内核没有收到“退出中断后立即切换”的请求。
修复
每个可能唤醒任务的 ISR 末尾都调用 portYIELD_FROM_ISR(xHigherPriorityTaskWoken)，变量初值设为 pdFALSE。
03

在 ISR 或定时器回调里 printf / 做浮点计算

症状
系统随机变慢、栈溢出、偶发 HardFault，加了打印之后问题反而更频繁。
原因
C 库打印函数往往不可重入、耗时长且需要较大栈空间；浮点运算还可能触发额外的上下文保存。
修复
ISR 只把数据放进环形缓冲或队列，由低优先级任务负责格式化和打印；回调里同样只做轻量动作。
