同步与通信

信号量、互斥量、队列、事件组与任务通知：让多个任务安全地协作

一句话解释

任务之间既不能互相踩内存，也不能互相干等：同步与通信机制负责“排队、通知、传数据、护资源”。

学习目标

  • 1区分二值信号量、计数信号量、互斥量各自解决的问题，并说清互斥量为什么需要优先级继承
  • 2用队列实现生产者—消费者模型，读懂 xQueueCreate / Send / Receive 的每个参数与返回值
  • 3知道中断服务程序里必须使用 FromISR 版本 API，并会用 portYIELD_FROM_ISR 触发切换
  • 4为“等待多个事件”“传大量数据”“轻量通知”等场景选出合适的机制，并写出防死锁的超时策略

生活化比喻

停车场、卫生间钥匙、传送带与广播

信号量像一个停车位：位子空着（计数为 1）才能停进去，停满了就得等；计数信号量就是有 N 个车位的停车场。互斥量像卫生间的钥匙：同一时刻只允许一个人用，钥匙还挂在门外的钩子上，谁拿谁还，并且优先给“最着急的人”。队列像一条传送带：生产者把零件放上去，消费者从另一头取走，传送带上能积压几个零件就是队列深度。事件组像公告板上的几个指示灯：可以只等某一盏亮，也可以等所有灯都亮再开工。任务通知则像拍肩膀：只叫某一个人，轻便但信息量小。

为什么重要 / 用在哪里

多任务程序里，任务之间总要打交道：一个任务读到的数据要交给另一个任务处理，两个任务要抢同一个串口，一个任务要等中断报告“数据到了”。裸机时代这些问题靠全局变量加标志位“约定”，在单线程里勉强能用；一旦变成多任务，任何一次抢占或时间片轮转都可能让“读—改—写”被打断，产生数据竞争。同步与通信机制把这些约定变成内核管理的对象：等待会阻塞而不是空转，共享资源有明确的进入/退出点，数据传递有确定的缓冲和边界。学会在正确场景选正确对象，是写出稳定多任务程序的关键一步。

串口日志：多个任务都要打印，必须用互斥量保护，避免半行日志互相穿插传感器采集：中断把数据放进队列，处理任务在队列上阻塞等待，天然解耦资源池管理：有限的内存块、DMA 通道用计数信号量表示“还剩几个”事件同步：WiFi 连上 + 传感器校准完成，两个条件都满足才开始上报低功耗唤醒：中断用任务通知轻量唤醒处理任务，比队列省时省内存

多任务为什么需要同步与通信？

多任务带来的第一个新问题是共享资源。两个任务都要往同一个串口写数据，如果任务 A 刚写了一半就被任务 B 抢占，B 又从头写一段，串口上就会出现两段交错的乱码。这类问题的根源是“读—改—写”不是原子操作，必须有一个明确的“进入/退出”协议来保护临界区。

第二个问题是事件通知。中断里检测到按键按下，需要告诉某个任务“该干活了”；任务不应该在 while 里反复查询标志位，因为那样既费电又增加响应延迟。第三个问题是数据传递：一个任务产生数据、另一个任务消费数据，二者速度不匹配时需要缓冲区。RTOS 把这三类需求分别抽象成信号量/互斥量、事件组/任务通知、队列/缓冲区，内核负责阻塞、唤醒与调度，应用层只需表达意图。

  • 共享资源：用互斥量或临界区保证同一时刻只有一个执行流访问
  • 事件通知：用信号量、事件组或任务通知把“事情发生了”传给任务
  • 数据传递：用队列、流缓冲区在生产者和消费者之间排队
  • 核心原则：能阻塞等待就不要忙等；能在内核对象上排队就不要靠全局标志位

先记住这六个词

二值信号量Binary Semaphore
计数只有 0 和 1 的信号量，用于事件通知与简单互斥。
计数信号量Counting Semaphore
计数从 0 到 N，用来表示“还有几个资源可用”。
互斥量Mutex
带所有权和优先级继承的锁，专用于保护共享资源。
优先级继承Priority Inheritance
低优先级持锁时临时提升到等待者的优先级，缩短阻塞时间。
队列Queue
按值拷贝、先进先出的缓冲区，任务与中断都能安全收发。
事件组Event Group
用一组位标志表示多个事件，可以等待“任意一个”或“全部”。

结论提示（先观察再展开）

信号量是“许可的计数器”：take() 申请、release() 归还，拿不到就阻塞排队。二值信号量（容量 1）用于互斥保护唯一资源；计数信号量（容量 N）用于限制并发数量。切换容量可以看到：容量越大，等待队列越短，但并发进入的任务也越多——保护与吞吐需要权衡。

模型简化：任务按固定顺序到达/离开，wait 队列为 FIFO；真实内核的 release 可能唤醒多个等待者（give 语义）或采用优先级排序。

信号量：停车位与通行证

信号量（semaphore）本质上是一个计数器加一个等待队列。任务调用 Take（或 Wait）时，如果计数大于 0 就减 1 并继续执行，否则就阻塞排队；调用 Give（或 Post）时，如果有任务在等就唤醒一个，否则把计数加 1。计数只有 0/1 两种状态的叫二值信号量，可以表示“事件发生过”；计数从 0 到 N 的叫计数信号量，可以表示“还有 N 个资源可用”。

FreeRTOS 里创建二值信号量用 xSemaphoreCreateBinary，它创建出来是“空的”（计数为 0），通常先在初始化时 Give 一次，或由中断在事件发生时 Give。注意二值信号量不是锁：谁都可以 Give，也没有所有权概念，所以它适合做“通知”，不适合保护共享资源。

  • xSemaphoreGive / xSemaphoreTake：任务上下文使用
  • xSemaphoreGiveFromISR：中断上下文中给出信号量
  • 二值信号量初始为 0，忘记 Give 会让等待方永远阻塞
  • 计数信号量的最大值与初始值要在创建时定好，超发会失败

别用二值信号量当锁

二值信号量和互斥量的 API 长得很像（都是 Give/Take），但用途完全不同。互斥量有“所有权”和“优先级继承”：低优先级任务持锁时，如果高优先级任务来等，内核会临时把低优先级任务的优先级抬高，让它尽快跑完释放锁。二值信号量没有这些机制，用它保护共享资源会出现优先级反转，高优先级任务可能被一个与锁无关的中优先级任务拖到超时。

优先级反转与优先级继承

优先级反转（priority inversion）是实时系统里最经典的坑：低优先级任务 L 拿到了锁，高优先级任务 H 来等这把锁，此时一个与锁无关的中优先级任务 M 就绪，把 L 抢占掉。结果 H 明明优先级最高，却要等 M 跑完、L 再跑完才能继续，实际优先级被“反转”成了最低。如果 M 是周期性的长任务，H 的截止时间就彻底没保障。

互斥量用优先级继承（priority inheritance）缓解这个问题：当 H 在等 L 持有的锁时，内核临时把 L 的优先级提升到 H 的水平，M 就无法抢占 L 了；L 释放锁后优先级自动恢复。注意这只是“缓解”：持锁期间如果做耗时操作，继承来的高优先级同样会拖住别人，所以临界区一定要短。FreeRTOS 打开 configUSE_MUTEXES 后互斥量默认带继承；Zephyr 的 k_mutex 默认支持优先级继承，RT-Thread 的 rt_mutex 也支持。具体行为与版本相关，简化说明以官方文档和具体版本为准。

  • 持锁时间越短，优先级反转的窗口越小
  • 不要在持锁期间调用可能阻塞的 API（等队列、等另一个信号量）
  • 多个锁要按固定顺序获取，否则两个任务可能互相等待形成死锁
  • 互斥量只保护“资源”，不要用它做任务间的事件通知

队列解耦了生产者与消费者的速度差：满时生产者阻塞、空时消费者阻塞，数据既不丢也不覆盖。队列越短，阻塞越频繁、实时性抖动越大；队列越长，延迟越大、内存占用越多——长度是“缓冲能力”和“延迟”之间的权衡。

模型简化：队列为 FIFO、数据项一次搬运一条；真实 FreeRTOS 的 xQueueSend 可能带超时，超时后返回失败而不是永久阻塞。

队列：任务之间的传送带

队列（queue）是一个先进先出（FIFO）的环形缓冲区，生产者在尾部放，消费者从头部取。FreeRTOS 的队列是“按值拷贝”的：xQueueSend 会把你要发送的数据复制进队列内部的内存，接收方再把它复制到自己的变量里。所以队列里的数据与发送方的原始变量完全独立，发送方函数返回后数据依然有效——但这也意味着传大结构体会带来拷贝开销，传指针则要注意生命周期。

队列的另一个价值是“解耦速度差”。采集任务每 2 ms 产生一个样本，处理任务可能忙一阵闲一阵，队列把两者隔开：处理任务忙的时候样本先存在队列里，等它空下来再取。队列满时，发送方可以选择阻塞等待（直到有空间或超时），也可以立即返回失败并丢数据——这是产品层面的策略选择，不是技术细节。

  • xQueueSend：从任务上下文发送，队列满时可阻塞到超时
  • xQueueSendFromISR：从中断上下文发送，不能阻塞，通过参数告知是否需要切换
  • xQueueReceive：接收并从队列移除；超时到仍无数据则返回 pdFALSE
  • 队列既能传数据也能当“事件”用：发送一个字节表示有事情发生
  • 深度是设计参数：太小丢数据，太大增加内存和延迟

事件组：等“多件事凑齐”

事件组（event group）用一组位（bit）表示不同事件是否发生。任务可以等待“任意一位置位”或“所有指定位置位”，还可以选择在被唤醒时自动清除这些位。它特别适合“多个条件都满足才继续”的场景：传感器校准完成是一位，网络连接成功是另一位，两个都到位才开始上报。二值信号量只能表达一件事，要等三件事就得拿三把信号量，代码会写得很啰嗦。

FreeRTOS 的事件组通常有 24 个可用位（具体数量与版本、configUSE_16_BIT_TICKS 等历史配置有关，FreeRTOS 11 起已移除 16 位 tick 选项，简化说明以官方文档和具体版本为准）。中断里置位要用 xEventGroupSetBitsFromISR，它实际是把操作交给定时器守护任务执行，因此不能在中断里无限等待。

  • xEventGroupWaitBits：等待位组合，xWaitForAllBits 选择“与”还是“或”语义
  • xClearOnExit：唤醒时是否自动清除等待的位，决定事件是“一次性”还是“电平式”
  • 返回值包含调用时刻的完整位图，可用于判断是否真的等到
  • 事件组适合“状态组合”，不适合传数据，也不适合替代互斥量

任务通知、流缓冲区与消息缓冲区

任务通知（task notification）是 FreeRTOS 里最轻量的事件机制：每个任务自带一个 32 位通知值和一个通知状态，发送方直接“拍”目标任务一下，不需要额外创建队列或信号量。它没有中间缓冲区，一对一时速度最快、内存最省；代价是只能指定单个任务，无法广播，也不能像队列那样缓冲多条消息。常见用法是用 xTaskNotifyGive / ulTaskNotifyTake 模拟二值或计数信号量，或用 xTaskNotify / xTaskNotifyWait 传一个 32 位值。

当数据是连续的字节流（串口、DMA、音频）时，队列按固定大小拷贝的方式就不合适了。流缓冲区（stream buffer）专门处理“字节流 + 单写者单读者”：写入任意长度字节，读取按触发阈值唤醒，适合中断到任务的搬运。消息缓冲区（message buffer）在流缓冲区的基础上给每条消息加了长度前缀，因此可以传变长消息。两者的容量、触发阈值和内存分配方式请以官方文档与具体版本为准。

  • 任务通知：一对一、最轻量，适合中断唤醒任务、简单计数
  • 流缓冲区：字节流、单写者单读者，适合串口/DMA 数据搬运
  • 消息缓冲区：变长消息，接收方一次拿到一条完整消息
  • 所有机制的共同底线：中断里只能用不阻塞的版本，任务里等不到要处理超时

死锁：两个任务互相等对方的锁

死锁最典型的形态是两个任务以相反顺序获取两把锁：任务 A 先拿锁 1 再等锁 2，任务 B 先拿锁 2 再等锁 1，双方都等对方释放，于是永远卡住。如果等待时用了 portMAX_DELAY，系统不会有任何报错，只会表现为“功能整体停摆”。

防死锁的手段很朴素：给所有锁定义全局统一的获取顺序；尽量只持有一把锁；持锁期间不做可能阻塞的操作；除非业务确实需要无限等待，否则给等待设置超时并在超时分支记录日志或计数。超时不是万能药，但它至少能把“静默卡死”变成“可观测的失败”，让你在调试时知道问题出在哪个环节。

  • 统一锁顺序：所有任务按同一编号顺序获取多把锁
  • 缩小临界区：锁里只放必要的读写，耗时计算放到锁外
  • 持锁时不要等队列、等信号量、调用 printf 或写 Flash
  • 用超时 + 计数 + 日志暴露异常，而不是无限等待

中断里绝不能调用会阻塞的 API

中断服务程序运行在“打断一切”的上下文里，它不能睡眠、不能被阻塞，也不能等待调度。因此在 ISR 里调用 vTaskDelay、xSemaphoreTake、xQueueSend（非 FromISR 版本）或任何带超时的函数，轻则触发 configASSERT，重则破坏内核数据结构导致随机死机。中断里只做三件事：读硬件、把数据交给内核对象（FromISR 版本）、必要时请求切换。

先加超时，再优化性能

第一次写多任务程序时，给所有等待都加上有限超时（比如 100 ms 或 1 s），并在超时分支里累加一个计数器。等功能稳定、时序测量清楚之后，再考虑把某些关键路径改成 portMAX_DELAY。这样即使逻辑有漏洞，系统也是“部分功能失效并可观测”，而不是整个卡死、只能靠复位恢复。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

在中断里直接调用 xSemaphoreGive

症状
串口中断一来就触发 configASSERT，或者系统在中断返回后随机跑飞。
原因
xSemaphoreGive 是任务上下文 API，可能触发调度甚至阻塞，中断里调用属于非法使用。
修复
改用 xSemaphoreGiveFromISR(handle, &xHigherPriorityTaskWoken)，并在退出中断前调用 portYIELD_FROM_ISR。
02

用二值信号量保护共享资源

症状
高优先级任务偶尔超时，低优先级任务明明很快却被莫名拖慢。
原因
二值信号量没有所有权与优先级继承。低优先级持锁时被中优先级任务抢占，高优先级任务实际被反转成最低优先级。
修复
保护共享资源一律用互斥量（xSemaphoreCreateMutex），让继承机制缩短阻塞窗口；二值信号量只用于事件通知。
03

队列里传栈上临时变量的地址

症状
接收方拿到的数据时对时错，或者结构体字段变成随机值。
原因
队列的 Send 拷贝的是“指针值”而不是指针指向的内容；发送方函数返回后局部变量失效。
修复
发送结构体本身（按值拷贝），或传堆上/静态变量的指针并明确所有权与释放责任。

  1. 1

    先判断需求是互斥、通知还是数据流，再选对象：锁用互斥量，通知用信号量/任务通知，数据用队列或缓冲区。
