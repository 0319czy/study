低功耗与看门狗

Tickless Idle、唤醒源与 tick 补偿，以及硬件看门狗、喂狗策略与任务卡死检测

一句话解释

低功耗是“该睡就睡、该醒必醒”，看门狗是“醒着就必须证明自己还活着”；两者一个省电，一个保命。

学习目标

  • 1说清空闲任务、idle hook 与 Tickless Idle 的区别，知道 tickless 为什么能显著省电
  • 2理解 configUSE_TICKLESS_IDLE 的取值含义、休眠时长如何计算、唤醒后如何做 tick 补偿
  • 3区分硬件看门狗、软件定时器与任务监控，知道为什么软件定时器不能替代硬件看门狗
  • 4设计一套“所有关键任务报到后才喂狗”的策略，并用它检测任务卡死

生活化比喻

夜班保安与巡视打卡

低功耗像夜班保安：没人来的时候打盹（休眠），门铃一响必须立刻清醒（唤醒源），而且醒来后要知道自己睡了多久（tick 补偿），否则值班记录就乱了。看门狗像总部的巡视打卡制度：保安必须每半小时按一次打卡机（喂狗），超时就自动报警换人（复位）。如果保安把打卡机搬到门铃旁边，让门铃替他打卡（在中断里喂狗），那么他就算睡死过去，总部也发现不了。

为什么重要 / 用在哪里

电池供电的产品，待机电流常常比运行电流更能决定销量：一颗 2000 mAh 的电池，平均电流从 10 mA 降到 100 µA，寿命就从 8 天变成两年多。但低功耗与可靠性是一对矛盾：为了省电关掉时钟、进入休眠，任何配置错误都会让设备“睡过去再也醒不来”；而为了保命加的看门狗，如果喂法不对，又会把真正的死机掩盖成“偶尔重启”。掌握 tickless idle、唤醒源、tick 补偿和集中喂狗策略，才能同时做到省电与可信。

电池供电的传感器节点：每 10 分钟唤醒采样，其余时间深度休眠可穿戴设备：屏幕与传感器间歇工作，追求微安级待机远程抄表与追踪器：多数时间休眠，靠 RTC 或外部事件唤醒工业设备：看门狗必须在程序跑飞时可靠复位，并留下复位原因汽车与医疗：要求可证明的失效安全行为，不能被喂狗掩盖

低功耗的第一课：先搞清楚“谁在耗电”

MCU 的功耗大致由三部分组成：运行电流（CPU 与总线）、外设与时钟（尤其是高频时钟和模拟外设）、以及睡眠时的漏电流。常见的省电顺序是：先关掉不需要的外设时钟，再降低主频与电压，最后才考虑进入更深的休眠模式。

对 RTOS 系统来说，还有一个隐形的大头：tick。只要 tick 还在跑，CPU 每隔 1/configTICK_RATE_HZ 秒就会被 SysTick 中断叫醒一次。1000 Hz 的节拍意味着每秒 1000 次“醒来—保存现场—判断有没有任务到期—再睡回去”，这在高待机要求下是不可接受的。

  • 运行态优化：降主频、关外设时钟、DMA 代替 CPU 搬运
  • 空闲态优化：让 CPU 在空闲时真正停下来（WFI/WFE），而不是空转
  • 睡眠态优化：关闭 tick、进入低功耗模式，靠事件或定时器唤醒
  • 外设态优化：GPIO 配置为确定电平、模拟外设断电、避免悬空输入漏电

结论提示（先观察再展开）

Tickless 的本质是「把周期性唤醒改成事件驱动唤醒」：空闲时关闭 tick、设好低功耗定时器再深睡，醒来后用 tick 补偿把睡眠时间补回去。tick 模式不仅每秒被叫醒上千次，还因为 tick 时钟必须运行而无法进入深睡——这两点叠加才是节能的来源。它用更大的唤醒延迟（时钟起振）换取数量级更少的唤醒；空闲窗口越长、唤醒越少，节能越明显。对唤醒延迟敏感的场景，要么保留 tick，要么用硬件定时器直接唤醒。

简化模型：假设 STOP2 下 CPU 与主时钟停止、RAM 保持，未建模外设漏电、唤醒源抖动与电源管理分级；tick 补偿次数按睡眠时长 / tick 周期估算，实际由内核在恢复 tick 时计算。

从 WFI 到 Tickless：三个层次的“睡”

很多教程告诉你“在空闲钩子里执行 WFI 就能省电”，这只对了一半。WFI 让 CPU 停下，但 tick 中断照样每毫秒把 CPU 叫醒。要真正省电，需要让内核知道“接下来一段时间没有任务要做”，从而把 tick 一起关掉——这就是 Tickless Idle。

FreeRTOS 在空闲任务里判断：如果所有任务都在阻塞，且最近的到期时间还很远，就调用端口的 portSUPPRESS_TICKS_AND_SLEEP（Cortex-M 端口里通常是 vPortSuppressTicksAndSleep），关闭 tick、进入低功耗，睡到下一个到期时刻或外部中断唤醒。

  • 层次一：vApplicationIdleHook 里执行 WFI，只能到达浅睡眠，tick 仍在运行
  • 层次二：Tickless Idle 关闭 tick，睡到下一个任务到期时刻，省掉大量无用唤醒
  • 层次三：深度休眠 + 关外设时钟 + 配置唤醒源，需要按芯片手册逐项处理
  • 进入深睡前要保存必要状态，唤醒后重新初始化被断电的外设
  • 调试器、看门狗、欠压检测等也会影响最低功耗，别只看数据手册的典型值

关掉 tick 不代表任务延时失效，但你自己的计数会出错

Tickless 由内核负责在唤醒后补齐 tick 计数，所以 vTaskDelay、超时、软件定时器的语义仍然正确。但如果你在 tick 中断里自己数数（例如每来一拍给变量加一），休眠期间就会少算。需要真实时间请读 xTaskGetTickCount，或者用 RTC 作为时间基准。

tick 补偿：醒来以后把时间“补上”

睡之前，内核算出还能安全睡多久（xExpectedIdleTime）；醒来后，实际睡过的节拍数往往与预期略有差异，内核通过 vTaskStepTick 把这段时间补进 tick 计数，让任务延时、超时、软件定时器保持一致。

补偿的精度取决于唤醒时钟的分辨率：用 RTC 秒级闹钟做唤醒，误差可能是毫秒到几十毫秒；用低功耗定时器（LPTIM 一类）则可以做到更细。长期运行还会因晶振偏差漂移，必要时周期性用 RTC 校准。

  • 休眠时长 ≈ min(下一个任务到期时刻 - 当前 tick, 定时器/睡眠模式允许的最大时长) - 进出睡眠的固定开销
  • 自定义实现里要正确处理 eTaskConfirmSleepModeStatus 的返回值：eAbortSleep 表示别睡，eStandardSleep 表示可以睡到下一个到期时刻，eNoTasksWaitingTimeout 表示没有任何超时在等，可以睡到外部事件唤醒
  • 唤醒后先恢复时钟与外设，再继续调度，顺序错了会出现“唤醒即 HardFault”
  • 把唤醒次数与每次睡眠时长记录下来，是优化功耗最有用的数据

休眠不是“什么都不做”

进入 Stop、Standby 一类深睡模式前，芯片会关掉大部分时钟甚至电源域，唤醒后很多外设需要重新初始化。低功耗调试里最典型的事故是：设备睡下去就再也没醒，因为唤醒源没使能，或者唤醒后没恢复时钟就访问了外设。

  • 进睡前：保存需要保留的状态、关闭不需要的时钟、配置唤醒源与唤醒引脚
  • 唤醒后：先恢复时钟系统，再初始化外设，最后才允许任务访问它们
  • GPIO 处理：未使用的引脚配置为模拟输入或确定电平，输出引脚避免悬空
  • 调试影响：调试器连接、日志串口、看门狗都会抬高电流，测功耗时要断开
  • 先用浅睡模式验证唤醒链路，再逐步进入深睡，出问题时更容易定位

硬件看门狗 vs 软件定时器

硬件看门狗是芯片内部（很多型号用独立时钟源）的计时器，程序只要在超时前喂一次就继续，超时则直接复位芯片。它不依赖 CPU 是否正常，所以能救回跑飞的程序。软件定时器则是 FreeRTOS 内核对象，靠 tick 计时、在定时器守护任务里回调；它只能证明“调度器还在转”，无法让系统从死锁里恢复。

两者不是替代关系：软件定时器适合做超时、心跳、延时动作；硬件看门狗负责最后一道防线。真正的“任务卡死检测”则是第三件事——用软件手段判断某个具体任务是否还活着。

  • FreeRTOS 本身不提供看门狗 API，喂狗是芯片驱动/HAL 的事
  • 软件定时器依赖 tick 与守护任务：调度器停摆或高优先级任务霸占 CPU 时，它既不准时，也救不了系统
  • 硬件看门狗只能告诉你“该复位了”，不能告诉你“是谁卡住了”，需要配合复位原因记录
  • 窗口看门狗（WWDG 一类）要求在规定时间窗内喂狗，喂太早也会复位，能检测“跑得太快”的异常
  • 量产设备应在启动早期就开启看门狗，避免初始化阶段卡死无人管

喂狗策略：集中喂、晚点喂、别乱喂

看门狗最怕的不是“没喂”，而是“喂了但系统已经死了”。喂狗的位置决定了看门狗到底在监控什么：如果每个任务都自己喂，任何一个任务活着就能拖住不复位；如果中断里喂，那么任务全部死锁也不会复位；只有让“最不可能撒谎的一方”来喂，看门狗才有意义。

  • 集中策略：只在一个地方喂狗，通常是低优先级的监控任务
  • 条件喂狗：所有关键任务都报到后才喂，任一个失联就不喂
  • 时间余量：喂狗周期 ≤ 看门狗超时的 1/3，给调度抖动留空间
  • 窗口看门狗：既不能太晚，也不能太早；初始化时要在窗口内完成第一次喂
  • 记录现场：复位原因、上次卡住的任务名写入备份寄存器或 Flash，方便事后分析
  • 调试阶段：先关闭看门狗或使用调试冻结功能，否则频繁复位看不到现场

在中断里喂狗，等于给病人打麻药

中断优先级高于所有任务，哪怕业务任务全部死锁，中断照样按时到来。如果在中断里喂狗，硬件看门狗就彻底失效了，系统会以“看起来正常运行”的方式慢慢烂掉。喂狗必须由能证明业务健康的地方执行。

结论提示（先观察再展开）

看门狗是独立于 CPU 的硬件计时器：软件只能在超时前「清零」来证明自己还活着，一旦某次没喂到，硬件复位就是最后的防线。喂狗必须由真正健康、能拿到 CPU 的任务完成（优先级不能过低），周期要明显小于超时阈值；复位后务必读取复位原因、修复根因，否则会陷入「复位—再卡死—再复位」的循环。

简化模型：真实 IWDG 由独立 LSI 时钟（约 32.768 kHz）驱动，超时时间 = 重载值 × 分频 / 时钟；这里用「拍」抽象计数，复位脉冲宽度与启动耗时为示意值，未建模窗口看门狗（WWDT）与外部看门狗芯片。

调试低功耗系统的土办法

低功耗 bug 的特点是“一带调试器就正常，一拔就出问题”。原因往往是调试器连着时时钟、低功耗模式、看门狗冻结等行为都变了。所以测量与验证方式本身需要设计。

  • 用 GPIO 翻转加示波器打点，代替串口打印观察唤醒时序
  • 用功耗分析仪看平均电流与电流波形，比万用表更能发现尖峰与泄漏
  • 记录唤醒原因（唤醒/复位状态寄存器），确认是不是被意外中断叫醒
  • 常见漏电原因：外设时钟没关、GPIO 悬空、上拉电阻常开、调试器还连着
  • 把每次唤醒的时长与原因统计出来，才知道该优先优化哪里

先测量，再优化

不要凭直觉改配置。先用功耗分析仪测出运行态电流、待机电流与占空比，算出平均电流，再决定是降低唤醒频率、缩短唤醒时长，还是进入更深的休眠模式。盲目把 sleep 塞进主循环，往往只是把一个 bug 变成更难查的 bug。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

开了 tickless 却仍自己数 tick

症状
设备运行越久时间越偏，定时任务间隔变长，软件定时器明显不准。
原因
休眠期间 tick 被跳过，内核会在唤醒后补偿，但应用里“每来一次 tick 中断就加一”的计数器不会补偿。
修复
统一用 xTaskGetTickCount 获取时间；需要长期真实时间时以 RTC 为基准，并周期性校准。
02

在中断里喂狗

症状
业务任务已经死锁，系统却一直不复位，直到看门狗被人为关闭或出现其他故障。
原因
中断独立于任务调度，即使任务全部卡死，高优先级中断仍会按时执行喂狗。
修复
改由低优先级监控任务在所有关键任务报到后集中喂狗；中断只负责记录事件。
03

直接进深睡但没配唤醒源、没恢复时钟

症状
设备休眠后彻底失联，只能重新上电；或者唤醒瞬间 HardFault。
原因
唤醒源未使能，或唤醒后时钟/外设尚未恢复就被访问。
修复
明确配置唤醒源与唤醒引脚，唤醒后先恢复时钟再初始化外设；先在浅睡模式验证整条唤醒链路。

记住这三句话

  1. 1

    Tickless Idle 的价值在于取消无用的周期唤醒；是否生效取决于端口与唤醒源配置。

  2. 2

    休眠后的 tick 由内核补偿，应用自己数的节拍不会补偿，时间基准要统一到 tick 或 RTC。

  3. 3

    硬件看门狗负责“复位救命”，软件定时器只证明调度器还在跑，任务监控才回答“是谁卡住了”。
