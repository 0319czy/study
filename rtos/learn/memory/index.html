内存管理

任务栈、TCB 与队列缓冲从哪来：heap_1 到 heap_5、碎片、栈溢出与内存池

一句话解释

RTOS 里每一块内存都有主人：说清谁分配、谁释放、什么时候分配，系统才能稳定运行几年而不是随机死机。

学习目标

  • 1说清任务、队列、信号量背后的内存开销，会做静态内存预算
  • 2区分静态分配、FreeRTOS 堆与 C 库堆，并解释 heap_1 到 heap_5 的差异
  • 3理解内外部碎片，能用固定块内存池替代运行期变长分配
  • 4会用 configCHECK_FOR_STACK_OVERFLOW 与 uxTaskGetStackHighWaterMark 定量确定栈大小

生活化比喻

仓库管理员与五种货架

静态分配像给每个工人提前划好固定工位：地方不大但绝不会抢，谁也不会被临时赶走。FreeRTOS 堆像一间公共仓库，由管理员按需切块，切法（heap_1 到 heap_5）决定了好不好用、会不会碎。C 库堆则像向市政租的仓库，规则由工具链决定。内存池则把仓库改成一排同样大小的标准货位：永远不会有“空间够但塞不进去”的尴尬。

为什么重要 / 用在哪里

MCU 的 RAM 通常只有几十到几百 KB，而每个任务都要独立的栈、每个队列都要缓冲、每个内核对象都要控制块。默认的 xTaskCreate 会在运行期从 FreeRTOS 堆里切内存，一旦切不出来，任务创建就失败；一旦栈给少了，程序会在某个深夜随机 HardFault。理解内存来源、碎片与水位监测，是把“能跑”变成“敢量产”的关键一步。

长时间运行的设备：运行几天后任务创建失败、通信中断安全关键场景：要求内存分配在编译期确定，不允许运行期失败多任务产品：任务栈大小需要量化依据，而不是凭感觉给 128带外部 SRAM 的板子：内存分散在多段，需要 heap_5 管理协议与文件系统：需要大量变长缓冲，必须有碎片对策

谁在吃你的 RAM？

写 RTOS 程序时最容易忽略的一件事：创建任务的代价不只是几行代码。一个 xTaskCreate 背后至少有任务栈和控制块（TCB）两块内存；一个队列背后是“元素大小 × 长度”的缓冲再加控制块；信号量、事件组、软件定时器也都有各自的控制结构。

这些东西默认都从 FreeRTOS 堆里切，而堆本身只是 RAM 里的一段固定数组。所以“创建任务失败”“跑着跑着不够用”，本质上都是同一件事：仓库规划没做好。

  • 任务栈：局部变量、函数调用栈帧、上下文保存的寄存器，都由它承担
  • 任务控制块 TCB：内核记录任务状态、优先级、链表节点的结构体
  • 队列：缓冲区大小 = 队列长度 × 单个元素大小，另加控制块
  • 定时器、事件组、信号量：各自的控制块，通常几十字节到一百多字节
  • FreeRTOS 堆：由 configTOTAL_HEAP_SIZE 决定，实现方式由 heap_x.c 选择

结论提示（先观察再展开）

外部碎片 = 总空闲够、连续块不够，它是分配与释放历史留下的空洞，而不是「内存用完了」。首次适配 + 释放时合并相邻空闲块能缓解碎片；固定内存池用块粒度彻底消灭外部碎片、换取可预测的分配时间，代价是内部浪费与容量刚性。无论哪种方案，都要在运行期监控最大连续块，而不是只看空闲总量。

简化模型：只看单线程的字节布局，忽略分配器元数据（块头、对齐填充）、多线程锁竞争与真实 malloc 实现；固定池按 64 B 块对齐仅是示意。

先分清这五个词

堆Heap
一块由分配器切分的内存区域，分配顺序与大小在运行期才确定。
栈Stack
每个任务独立的函数调用与局部变量区域，向下增长（多数架构）。
静态分配Static Allocation
内存对象在编译/链接期确定，运行期不需要分配器。
内存碎片Fragmentation
空闲总量足够，但缺少足够大的连续块（外部碎片），或分配粒度造成浪费（内部碎片）。
内存池Memory Pool
预先切成固定大小块的分配方案，分配与释放都是常数时间且不产生外部碎片。

三条内存来路：静态、FreeRTOS 堆、C 库堆

FreeRTOS 允许三种内存来源共存，关键是每一块内存的“主人”必须清楚，不要跨来源释放。比如从 FreeRTOS 堆里 pvPortMalloc 出来的内存，绝不能交给 free() 释放。

  • 静态分配：由 configSUPPORT_STATIC_ALLOCATION 打开，创建对象时传入预制缓冲区和控制块，运行期不会分配失败
  • FreeRTOS 堆：由 configSUPPORT_DYNAMIC_ALLOCATION 打开，内存来自 heap_1 到 heap_5 中的一种实现，大小由 configTOTAL_HEAP_SIZE 决定
  • C 库堆：由 heap_3 包装标准 malloc/free 使用，大小由启动文件或链接脚本里的 heap 段决定
  • 三种可以混用，但“谁分配谁释放”必须统一，否则会破坏堆结构
  • 安全关键项目优先静态分配；通用产品常用 heap_4；带外部 SRAM 的板子考虑 heap_5

碎片：仓库里的“鸡零狗碎”

外部碎片指空闲总量够、但没有一块连续空间足够大：仓库还有 8 KB 空地，却被切成 20 个放不下 2 KB 箱子的小缝。内部碎片指分配粒度带来的浪费：你要 30 字节，对齐和块头让它实际占用了 40 字节。

FreeRTOS 的堆没有“压缩整理”能力：已分配的数据不能搬动，因为任务手里握着指针。所以碎片一旦产生，只能靠设计避免，不能靠算法消除。

  • heap_4 会合并相邻的空闲块，缓解但不消灭碎片
  • 大小混杂的反复分配/释放是碎片的最佳配方，尤其是运行期分配变长缓冲
  • 固定块内存池没有外部碎片问题，只有“池子够不够大”的问题
  • 用队列传指针、启动期预分配大对象，比运行期多次 malloc 更安全
  • 观察趋势：xPortGetFreeHeapSize 看当前余量，xPortGetMinimumEverFreeHeapSize 看历史最低点（可用性视所选 heap 方案而定）

运行期反复 malloc/free 是碎片的最佳配方

即使使用 heap_4，大小不一的反复分配仍会把仓库切成一堆“只能放下小箱子”的空洞。稳妥做法是：启动阶段一次性分配好所有对象（任务、队列、缓冲），运行期只使用固定大小块；确实需要变长数据时，用固定块池加“多档块大小”来兜底。

内存池：把仓库改成一排标准货位

固定块内存池在初始化时把一大块内存切成一排同样大小的格子，分配就是取走一个空位，释放就是还回去。它是常数时间操作，也永远不会产生外部碎片，非常适合运行期反复使用的报文、采样、网络包缓冲。

FreeRTOS 本身没有类似 Zephyr k_mem_slab 的固定块池 API，工程上常见的实现方式是“用队列存空闲块指针”或“静态数组 + 位图/自由链表”，几十行代码就能完成。

  • 变长需求可以准备多档块大小（例如 16 / 32 / 64 / 128 字节），按需选档
  • 池耗尽时必须有明确策略：丢包、阻塞等待、还是计数告警
  • 池的大小按“峰值同时在用的块数”设计，可通过计数器统计峰值
  • 释放后记得清空状态，避免出现“同一块被两个任务同时持有”的双重释放 bug

栈溢出检测：在最危险的地方装报警器

栈溢出是嵌入式最隐蔽的崩溃来源之一：局部大数组、深层递归、printf 格式化、中断嵌套，都可能悄悄吃掉栈。溢出往往不会立刻崩溃，而是先破坏别的变量，再在别处 HardFault，让人误以为是别的问题。

FreeRTOS 提供两级检测，都通过 configCHECK_FOR_STACK_OVERFLOW 打开。检测到溢出后调用 vApplicationStackOverflowHook，此时系统已经不安全，钩子里要做的是“记录现场并复位”，而不是继续优雅运行。

  • 等级 1：上下文切换时检查栈指针是否越过栈边界，速度快，但可能漏掉“越界后又被写回”的情况
  • 等级 2：创建任务时用已知图案填充栈，切换时检查栈末尾若干字节是否被改写，更容易发现早期溢出，开销略大
  • 钩子签名固定：void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)
  • 钩子里不要调用 printf、不要动态分配；把任务名存到备份寄存器或 Flash 后复位
  • 在 Cortex-M 上，异常入栈的现场（R0-R3、返回地址等）会压在被打断任务的栈上，ISR 自身的局部变量则用主栈 MSP；所以任务栈要为一次中断现场留余量，而 ISR 调用链深度受链接脚本里的主栈大小限制

栈要多大：先给保守值，再用高水位收敛

没有公式能精确算出栈需求：编译器优化、库函数实现、中断嵌套层数、是否使用浮点都会改变结果。工程做法是“先给保守值跑通，再读水位收敛”，而不是一开始就抠到最小。

uxTaskGetStackHighWaterMark 返回任务创建以来出现过的最小剩余栈空间，单位是栈字（Cortex-M 上通常 4 字节）。返回值接近 0，说明已经非常危险。

  • 起步参考：极小任务用 configMINIMAL_STACK_SIZE 起步（常见 128 字），普通业务任务 256 字起步
  • 用到 printf、浮点、较大局部缓冲时，栈需求可能翻倍甚至更多
  • 收敛目标：跑遍所有分支与最坏场景后，保留 20%～30% 的余量
  • 查询其他任务需要保存创建时的句柄；传 NULL 表示查询当前任务
  • 需要精确宽度时用 uxTaskGetStackHighWaterMark2，返回 configSTACK_DEPTH_TYPE 类型

把内存预算写成一张表

项目启动时列出：每个任务的栈与 TCB、每个队列的缓冲与控制块、定时器与事件组、协议缓冲、堆预留……加起来必须小于 RAM，还要给启动栈、中断嵌套、C 库留出余量。这张表比事后通宵查“为什么创建任务失败”便宜得多。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

把 configTOTAL_HEAP_SIZE 当成“系统总内存”

症状
调大或调小这个宏，程序行为毫无变化，或者改了之后直接链接失败。
原因
如果选用 heap_3，内存来自 C 库的 malloc，堆大小由链接脚本/启动文件决定，configTOTAL_HEAP_SIZE 不生效。
修复
先确认工程实际编译的是哪个 heap_x.c，再按该方案配置对应大小；用 xPortGetFreeHeapSize 观察真实余量。
02

把栈高水位返回值当成字节数

症状
以为任务还剩 200 字节栈空间，实际只剩 50 字节，运行一会儿就栈溢出。
原因
uxTaskGetStackHighWaterMark 返回的单位是栈字（StackType_t），Cortex-M 上 1 字 = 4 字节。
修复
需要字节数时乘以 sizeof(StackType_t)，并在估算栈大小时统一单位。
03

运行期反复分配释放变长对象

症状
设备连续跑几天后 pvPortMalloc 返回 NULL，或者 xQueueCreate 失败，重启即恢复。
原因
大小混杂的反复分配产生外部碎片，空闲总量够但没有足够大的连续块。
修复
启动期预分配、运行期只用固定块内存池或静态对象；必须动态分配时统一块大小并监控碎片趋势。
