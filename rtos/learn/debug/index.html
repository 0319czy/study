调试与性能

栈、CPU 利用率、运行时统计与死机定位：让系统从“黑盒”变成“仪表盘”

一句话解释

调试 RTOS 的核心不是猜，而是把栈、CPU 时间、任务状态和调用轨迹变成可读的数据，再用数据缩小范围。

学习目标

  • 1用栈高水位和溢出检测判断任务栈是否够用，并解释为什么空载数据不可信
  • 2配置运行时统计，读懂任务列表和 CPU 占比，定位忙等与资源争用
  • 3按“保留现场→读故障寄存器→回溯调用栈→二分复现”的顺序排查 HardFault
  • 4识别优先级配置、栈溢出、堆耗尽和死锁四类系统级问题的典型症状与对策
本章测验3 题
去测验中心专项练习
生活化比喻

给城市装监控，而不是满城找嫌疑人

裸机调试常常靠 printf 和“注释一半代码”，像在没有监控的城市里靠目击者描述破案。RTOS 调试要先把仪表装起来：栈高水位告诉你“离墙还有多远”，CPU 统计告诉你“谁在占道”，任务列表告诉你“谁堵在路上”，Trace 则像行车记录仪，把切换顺序完整录下来。先有数据，再谈定位。

为什么重要 / 用在哪里

多任务系统的问题往往不是“必现”的：偶发死机、周期抖动、某个任务越来越慢、内存越跑越少。这些现象在单步调试时经常消失，因为时序被改变了。可靠的调试方法是“可观测性 + 压力测试 + 现场保留”：让固件自己记录证据，在真实负载下暴露问题。

产品小批量试产时偶发死机，实验室无法复现电机控制周期偶尔抖动，需要确认是否被高优先级任务抢占设备运行几天后创建队列失败，怀疑堆耗尽或泄漏任务明明在运行，但响应越来越慢，怀疑优先级或锁竞争优化功耗前，先确认 CPU 到底有多少时间在空转

先让系统“会说话”

调试 RTOS 最容易犯的错误，是直接盯着某个函数找 Bug。多任务系统里，一个现象可能由另一个任务、一次中断、甚至一次内存越界引起。正确的顺序是先把系统的运行状态变成可读的数字，再顺着数字找代码。

四类最值得先接上的“仪表”：栈余量（会不会撞墙）、CPU 占比（谁在吃时间）、任务状态（谁在等、谁在跑）、事件时间线（切换与中断的顺序）。它们分别回答“空间够不够、时间花在哪、卡在哪、顺序对不对”。

  • 栈：uxTaskGetStackHighWaterMark + 栈溢出钩子
  • CPU：configGENERATE_RUN_TIME_STATS + vTaskGetRunTimeStats
  • 任务状态：vTaskList / uxTaskGetSystemState
  • 时间线：Percepio Tracealyzer、SEGGER SystemView 等 Trace 工具
  • 现场：HardFault 故障寄存器 + 复位原因 + 故障日志

调试常用术语

栈高水位Stack High Water Mark
任务运行以来栈剩余空间的历史最小值，用来判断栈是否够用。
CPU 利用率CPU Utilization
单位时间内 CPU 忙于执行任务的比例；空闲任务占比高说明还有余量。
运行时统计Run-Time Statistics
记录每个任务累计消耗的 CPU 时间，并换算成占比。
TraceExecution Trace
按时间顺序记录任务切换、中断、队列等事件，用于还原真实时序。
HardFaultHard Fault
Cortex-M 的兜底异常，非法访问、未定义指令、栈破坏等最终都可能落到这里。
死锁Deadlock
多个任务互相等待对方持有的资源，谁都无法继续执行。

栈与高水位：每个任务都有自己的“鞋柜”

每个任务都有独立栈，动态创建时从 FreeRTOS 堆里分配。栈里放局部变量、函数调用返回地址、中断/切换时的寄存器现场，以及 printf、浮点运算这类“隐形大户”的临时数据。栈不够时不会立刻报错，而是悄悄改写相邻内存——可能破坏 TCB、其他任务栈或全局变量，表现为完全随机的死机。

uxTaskGetStackHighWaterMark() 返回任务历史上剩余的最小栈空间，单位是字（Cortex-M 上 1 字 = 4 字节）。返回值越接近 0 越危险；返回 0 说明可能已经贴底甚至溢出。注意它是“历史最小值”，所以必须在最坏负载下跑过之后再看，空载时的数字没有参考价值。

  • configCHECK_FOR_STACK_OVERFLOW = 1 或 2，2 会在栈末尾填 pattern 并检查，能更早发现越界
  • 溢出时内核调用 vApplicationStackOverflowHook，适合记录任务名后停机或复位
  • 工程经验：压力测试后仍保留约 20%~30% 余量比较稳妥（经验值，不是标准要求）
  • 把 printf、大局部数组、深递归、浮点运算列为“栈大户”单独评估
  • 任务栈单位是字，configMINIMAL_STACK_SIZE = 128 表示 512 字节，不是 128 字节

  • 溢出/危险

观察问题
  • · 日志任务为什么最容易溢出？printf、浮点和大局部数组分别占多少？
  • · 关闭压测后余量变大，能否直接说明栈安全？
  • · 高水位为 0 时一定已经溢出吗？还可能是什么情况？
结论提示（先观察再展开）

栈够不够不能靠“感觉”。用高水位观察历史最小值，在最坏路径上压测并留 20%~30% 余量；开启栈溢出检测只是兜底，不是替代估算。

简化模型：用字节展示，实际 uxTaskGetStackHighWaterMark 返回栈字（Cortex-M 通常 4 字节/字）；不同编译器的栈消耗差异很大。

CPU 利用率与运行时统计：时间到底花在哪

单核系统里，CPU 利用率可以粗略理解为“1 减去空闲任务占比”。FreeRTOS 提供运行时统计：内核在任务切换时记录时间戳，累计每个任务的运行时间，再换算成百分比。它不能告诉你“为什么慢”，但能迅速指出“谁在占 CPU”。

启用它需要三件事：configGENERATE_RUN_TIME_STATS = 1；提供 portCONFIGURE_TIMER_FOR_RUN_TIME_STATS() 和 portGET_RUN_TIME_COUNTER_VALUE() 两个宏；以及一个频率远高于 tick 的计时源。计数值只要求单调递增，单位由你自己定义。

  • 计时源通常用 1 个硬件定时器，频率取 tick 的 10 倍以上（分辨率越高越准，开销也越大，具体建议以官方文档为准）
  • 读取统计的 vTaskGetRunTimeStats 需要 configUSE_STATS_FORMATTING_FUNCTIONS = 1
  • 输出一般包含任务名、绝对时间和百分比；百分比是统计窗口内的平均值
  • 统计本身有开销，量产固件可以关闭；需要现场诊断时再打开
  • 经验上，空闲任务占比长期低于 10%~20% 时，系统已接近饱和，新增负载容易造成超时

vTaskList：一眼看清谁在跑、谁在等

运行时统计回答“花了多少时间”，任务列表回答“现在是什么状态”。打开 configUSE_TRACE_FACILITY = 1 和 configUSE_STATS_FORMATTING_FUNCTIONS = 1 后，vTaskList() 会输出每个任务的名字、状态、优先级、栈高水位和任务编号。

状态列用字母表示：B（Blocked，阻塞）、R（Ready，就绪）、D（Deleted，已删除）、S（Suspended，挂起）。如果某个高优先级任务长期是 R 却几乎不产生业务输出，通常意味着它在忙等或轮询；如果多个任务都是 B，系统可能正卡在某个信号量或队列上。

  • vTaskList 会短暂挂起调度器遍历所有任务，不要在高速循环或中断里调用
  • 输出缓冲区按“每任务约 40 字节”估算只是官方示例口径，任务名长时要加大
  • uxTaskGetSystemState 是它的结构化版本，适合程序自己解析和上报
  • 任务编号变化、状态频繁跳变，往往比单次快照更有诊断价值

Trace：把“顺序”也录下来

统计和任务列表都是“某一时刻的截面”，而很多问题出在顺序上：中断为什么在这个任务刚拿锁时打断它？两个任务为什么交替得如此频繁？Trace 工具把任务切换、ISR 进入/退出、队列收发、信号量操作按时间轴记录下来，像行车记录仪一样还原现场。

常见工具示例：Percepio Tracealyzer 配合 FreeRTOS 的 trace recorder 记录事件并做可视化分析；SEGGER SystemView 通过 RTT 实时采集，适合 J-Link 环境。两者都有不同的版本与授权方式，功能和版本支持范围以官方信息为准。

  • Trace 记录通常通过内核的 trace 宏（如 traceTASK_SWITCHED_IN）挂接，需要把 recorder 集成进工程
  • 记录方式分 RAM 缓冲快照和流式输出；RAM 缓冲会占用可观内存，流式对调试链路带宽有要求
  • Trace 适合分析“偶发时序问题”，不适合长期开在生产固件里
  • 先录最短的可复现片段，再放大看上下文切换和 ISR 时序，避免被海量事件淹没

HardFault 与死机：先保留现场，再找第一现场

HardFault 是 Cortex-M 的“兜底异常”：总线错误、非法访问、未对齐访问、执行非法指令、栈溢出破坏返回地址，最终都可能落到这里。它不是原因，而是结果。急着重新烧录会丢掉最有价值的现场。

排查顺序：① 确认复位原因（看门狗、欠压、软件复位还是上电）；② 读 SCB->CFSR、HFSR，必要时读 MMFAR、BFAR；③ 从异常栈帧取出出错时的 PC 和 LR；④ 用 addr2line 或 IDE 反汇编定位到函数与行；⑤ 结合最近改动和内存布局判断根因；⑥ 修复后补断言和压力测试。

  • CFSR 包含 MMFSR/BFSR/UFSR 三类子状态，先看哪一位被置起，能快速区分“访问非法地址”还是“指令非法”
  • 任务使用 PSP，异常/中断使用 MSP；取栈帧前先根据 EXC_RETURN 判断用的是哪个栈
  • HardFault 处理函数里不要调用 printf 等可能阻塞或重入的函数，先把关键寄存器存到不覆盖的区域
  • 开启 configASSERT 和栈溢出检测，能让很多问题在“第一次越界”时暴露，而不是几天后随机死机

优先级配置错误：不报错，只“偶发”

最常见的三种：把 FreeRTOS 优先级方向记反（数值越大越高）；两个任务以相反顺序获取两把锁；在优先级高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断里调用 FromISR API。它们都不会编译报错，却会在压力下表现为偶发死机、任务饿死或数据错乱。改优先级前先画出“任务-优先级-资源”表。

栈溢出与堆耗尽：两个伪装成“随机死机”的问题

栈溢出会改写相邻内存（TCB、其他任务栈、全局变量），现象毫无规律；堆耗尽则表现为 xTaskCreate 返回 pdFAIL、xQueueCreate 返回 NULL，或者运行一段时间后创建失败。两者都不一定立刻崩溃，所以必须靠主动检测。

排查栈：打开 configCHECK_FOR_STACK_OVERFLOW = 2，跑最坏场景，读高水位；把 printf/浮点/大局部数组这些“栈大户”移出任务或在启动时预留。排查堆：打开 configUSE_MALLOC_FAILED_HOOK，记录失败点；用 xPortGetFreeHeapSize 和 xPortGetMinimumEverFreeHeapSize 观察趋势。

  • 高水位应在“最坏输入 + 最长调用链”压力测试后采样，空载数据没有意义
  • 动态创建失败先看堆余量，再看是否泄漏（创建后忘记删除、反复创建队列）
  • 能静态分配就静态分配：xTaskCreateStatic / xQueueCreateStatic 把不确定性移到编译期
  • heap_4/heap_5 会合并空闲块，但长期频繁分配仍可能碎片化

死锁：大家都在等对方手里的东西

死锁的四个必要条件同时成立才会发生：互斥、持有并等待、不可剥夺、循环等待。RTOS 里最典型的是两个任务以相反顺序拿两把互斥量：任务 A 拿锁 1 等锁 2，任务 B 拿锁 2 等锁 1，双方永远等下去。

处理思路：统一锁顺序（给锁编号，永远从小到大获取）；缩小锁范围，持锁期间不做阻塞操作；用带超时的 xSemaphoreTake 让系统能退出来；能用一个锁解决就不要用两个。注意：互斥量的优先级继承只缓解优先级反转，不能预防死锁。

  • 症状：相关任务全部阻塞，CPU 利用率很低，最后被看门狗复位
  • 用 Trace 看“谁持锁、谁在等”，比在代码里猜快得多
  • 中断里不能获取互斥量；ISR 与任务共享数据用队列、任务通知或临界区
  • 递归互斥量只能同一任务重复获取，不能跨任务传递

排障顺序：先保现场，再二分

遇到死机，先记录复位原因、故障寄存器和当时的任务状态，再复位。然后问三个问题：最近改了什么？能否稳定复现？哪条时间线对不上？能稳定复现的问题，用二分法（注释一半功能、缩短周期、换输入）通常比盯着代码看更快。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

只看平均 CPU 占用，不看最坏情况

症状
平均占用只有 30%，但现场偶发超时和丢包。
原因
运行时统计是统计窗口内的平均值，短时突发、高优先级抢占和关中断带来的延迟被平均掉了。
修复
结合 Trace 看最坏响应时间，用 GPIO 翻转或高精度计时测量关键路径的 worst case，而不是只看平均值。
02

用空载时的高水位判断栈够不够

症状
实验室测试一切正常，现场运行几天后偶发死机。
原因
空载时没有走最坏分支，高水位偏乐观；printf、浮点、深调用链会在特定输入下临时吃掉大量栈。
修复
在最大输入、最长调用链下做压力测试后再采样，并保留 20%~30% 余量；同时打开栈溢出检测和钩子。
03

在中断里调用非 FromISR API

症状
偶发卡死、断言失败，或任务状态莫名其妙。
原因
非 FromISR API 可能阻塞或直接操作就绪表，在中断上下文调用会破坏内核状态。
修复
ISR 中只用 FromISR 版本，并用 portYIELD_FROM_ISR 请求切换；同时确认该中断优先级不高于 configMAX_SYSCALL_INTERRUPT_PRIORITY。
