安全与认证

安全边界、防御性编程、功能安全标准与“认证”的正确理解

一句话解释

安全不是某个中间件，而是一组边界、检查与证据：谁能访问什么、输入是否可信、出错时系统是否可控。

学习目标

  • 1说清 TrustZone/MPU 解决的是“访问边界”，而不是“自动防黑客”
  • 2用看门狗、断言和输入校验把故障限制在可控范围，并区分断言与错误处理
  • 3理解最小权限与安全启动的基本思路，能列出产品的信任边界
  • 4正确理解 MISRA C 与功能安全/安全认证的关系，避免“用了 RTOS 就自动认证”的误区

生活化比喻

小区安保：围墙、门禁、监控与验收

安全边界像小区围墙和门禁：不是所有人都能进所有楼栋（TrustZone/MPU）；看门狗像保安巡逻，发现异常就拉闸（复位）；输入校验像访客登记，先核对身份再放行；MISRA C 像施工规范，让房子经得起检查；认证则像消防验收——它验收的是“这一栋按这套图纸和材料建成的房子”，不是“你用了某个品牌的砖”。

为什么重要 / 用在哪里

联网设备一旦被攻破，损失不只是数据：门锁可能被远程打开，电机可能被恶意指令驱动，OTA 通道可能被用来植入固件。功能安全则是另一条线：系统失效时必须进入可预期的安全状态。两者都要求“默认不信任”和“证据可追溯”，而这恰恰是很多裸机项目最薄弱的部分。

物联网终端需要通过客户或行业的安全评估工业控制器要做功能安全，客户要求提供标准和证据说明汽车电子项目需要理解 ASIL 与软件组件的责任边界产品带 OTA，需要防止固件被替换或降级团队想把“出了事再查”变成“设计时就防住”

安全从威胁模型开始，而不是从加密算法开始

讨论安全前先问：要防谁、防什么、防到什么程度？是防远程攻击者刷入恶意固件，还是防现场误操作导致执行器误动，还是满足某个行业标准的合规要求？不同威胁模型对应完全不同的措施，先选算法往往是在解决错误的问题。

嵌入式安全通常关注三个目标：机密性（密钥、用户数据不泄露）、完整性（固件和配置不被篡改）、可用性（被攻击或故障后系统仍能安全停机）。对功能安全同样重要的还有可控性：出错时进入已知的安全状态，而不是随机跑飞。

  • 资产：密钥、校准参数、固件、用户隐私数据
  • 入口：调试口、通信接口、OTA、可移动介质、传感器输入
  • 边界：安全/非安全世界、特权/非特权、内核/应用、可信/不可信输入
  • 安全状态：切断执行器、进入安全模式、记录故障并复位
  • 证据：需求、设计、测试记录和工具链信息，认证时要能追溯

安全边界：TrustZone 与 MPU 各管一段

MPU（内存保护单元）在不少 Cortex-M 内核上提供（M3/M4 上通常是可选组件，M7、M33 等内核通常集成，具体以芯片数据手册为准）：它把地址空间划分成若干区域，规定某个区域是只读、可读写还是不可访问，以及是否允许执行。配合非特权模式，可以让通信任务无法改写控制任务的内存，也可以让任务代码区不可写、数据区不可执行。

TrustZone 是 Armv8-M（Cortex-M23/M33 等）的硬件隔离：系统被划分为安全世界和非安全世界，由 SAU/IDAU 决定每块地址属于哪个世界，跨世界调用必须经过受控入口。典型用法是安全世界管理密钥、安全启动和关键外设，非安全世界跑应用和 RTOS。

  • MPU 是“同一世界内的权限分区”，TrustZone 是“两个世界的硬件隔离”，两者可以叠加使用
  • 区域配置错误（重叠、给了 RWX、把栈区设成可执行）会制造新的漏洞，必须配合链接脚本一起设计
  • 任务进入非特权模式后，访问未授权区域会触发 MemManage 异常，这正是隔离生效的表现
  • FreeRTOS 的部分端口支持 MPU 与 Armv8-M 安全/非安全上下文，具体端口和配置项以所用版本官方文档为准
  • 隔离的目标是“缩小攻击面、限制故障影响”，不是让系统自动变安全

结论提示（先观察再展开）

默认拒绝、最小权限、在边界处校验不可信输入，是安全设计的基本盘。MPU/TrustZone 让越权“撞墙”，但墙怎么砌、门怎么开，仍由系统设计决定。

TrustZone/MPU 的具体寄存器、区域数量与异常行为随内核型号变化；本实验室只表达访问控制与校验思路，不构成安全认证或渗透测试结论。

看门狗与断言：一个负责“拉回正轨”，一个负责“抓住 Bug”

独立看门狗通常由独立时钟源驱动，即使主时钟跑飞也能复位系统。窗口看门狗还能检测“喂得太早”，防止程序在错误的位置空转却仍然按期喂狗。它的价值在于：当软件已经不可信时，硬件强制把系统拉回确定的初始状态。

断言则完全不同：它捕获的是“程序员认为绝不应该发生”的内部错误，比如任务创建失败、队列句柄为空、状态机进入非法状态。断言失败意味着代码有 Bug，应该停机让调试器接管，而不是继续运行。用断言去校验外部输入，会把“用户发了错包”变成“整机停机”，这是典型的误用。

  • 喂狗点要能代表系统健康：放在监控任务里，检查各关键任务心跳后再喂，而不是在主循环里无脑喂
  • 调试时用调试器冻结看门狗（如 STM32 的 DBGMCU 配置），否则断点一停就被复位
  • configASSERT 默认是空宏，等于关闭；开发期务必打开，量产可改为“记录 + 复位”但不要静默忽略
  • 断言失败处理函数里避免 printf 和阻塞调用，先把文件和行号存到保留内存
  • 外部输入用返回错误码 + 丢弃/安全状态处理，不要用断言

输入校验：所有来自芯片外部的数据都不可信

通信帧、传感器读数、OTA 包、文件系统内容、调试命令，全都跨过了信任边界。攻击者或干扰可能让长度字段撒谎、让 CRC 碰撞、让状态机收到乱序报文。防御性编程的第一步，是在边界处把数据当成“敌意输入”处理。

校验顺序建议固定为：长度 → 范围 → 格式/CRC → 状态机合法性 → 业务约束。任何一步失败都丢弃整包并记录，不要把半包数据继续往下传。涉及内存拷贝时，先检查长度再 memcpy；涉及整数运算时，检查溢出和除零。

  • 长度字段必须与缓冲区实际大小比较，不能直接信任报文里的长度
  • 解析前先确认状态机处于允许接收该类型报文的状态
  • 失败要有计数和日志，方便发现“正在被扫描/干扰”，而不是静默丢弃
  • 安全相关参数（标定值、限值）加 CRC 或签名，并做范围检查
  • 重试要有上限和超时，避免被一个坏包拖死整个任务

最小权限：默认拒绝，而不是默认允许

最小权限不只是“少给 root”，在 MCU 上同样具体：任务只使能自己需要的外设时钟和中断；通信任务通过 MPU 无法写控制任务的内存；不需要的调试接口在生产固件里关闭或加认证；密钥不放在普通 Flash，而是安全存储、OTP 或安全元件。

时间维度上也适用：阻塞操作一律带超时，等待资源有上限，中断里不做长耗时操作。权限给得越少，出问题时的影响面越小，排查也越容易。

  • 按任务划分权限：控制、通信、日志、诊断各管一块，跨块访问走明确定义的接口
  • 默认拒绝：白名单式开放地址、外设和命令，而不是列黑名单
  • 生产固件锁定调试口（读保护/调试认证），但保留可恢复的合法升级路径
  • 密钥与证书放安全存储，启动时校验，不在日志里打印
  • 给每个阻塞调用设置超时，避免“一个任务卡死拖垮全系统”

MISRA C：让代码“可检查”，而不是“看起来没 Bug”

MISRA C 是一套面向安全相关 C 代码的编码指南（如 MISRA C:2012），分为指令（directives）和规则（rules），并按强制程度分类。它的目标是限制未定义行为、未指定行为和实现相关行为，让代码更容易被静态分析、评审和验证。

合规不是“一条都不能违反”，而是“违反要有记录、有理由、有审批”，这叫偏离（deviation）。用静态分析工具扫描时，要配置正确的规则集和编译器模型，工具会有误报和漏报，仍需要人工评审。MISRA C 合规只是安全证据的一部分，不等于功能安全认证。

  • 常见约束：禁止隐式类型转换、限制指针运算、要求所有 switch 有 default、禁止动态内存等
  • 规则编号和分类随版本变化，具体条文以 MISRA 官方文档为准
  • 把静态分析接入 CI，新增违规就阻断合并，比事后集中整改便宜得多
  • 第三方代码（RTOS、协议栈）也要确认其合规声明和已知偏离

“用了某 RTOS 就自动认证”是常见误区

认证针对具体版本、配置、工具链与证据包，以官方最新信息为准。换一个编译器、打开一个调试宏、改一行配置，都可能让原有证据失效。应用代码、驱动、启动文件、链接脚本和测试用例同样在评估范围内；RTOS 厂商提供的证书通常只覆盖其内核在特定条件下的表现，不能自动覆盖你的产品。

安全启动与 OTA：让固件“换得掉，也换不坏”

安全启动是一条信任链：BootROM 验证一级引导，一级引导验证应用，每一级只信任上一级提供的公钥或哈希。任何一级验证失败都应停在安全状态，而不是“跳过校验继续启动”。

OTA 则要同时解决完整性、真实性和可恢复性：镜像签名验证、版本防回滚（单调计数器）、A/B 分区与失败回滚、升级过程掉电保护、升级后自检再切换。只做 CRC 不做签名，只能防传输错误，防不了恶意替换。

  • 签名验证（如 ECDSA）+ 哈希，根公钥放不可改区域
  • 防回滚：拒绝低于当前版本的镜像，避免攻击者利用已知漏洞的旧固件
  • A/B 分区：新镜像启动失败可回滚到旧版本
  • 升级包解析同样要长度校验、状态机校验和超时
  • 密钥生命周期要设计：生成、注入、轮换、吊销
RTOS 对照卡

三套 RTOS 的安全相关能力（概念对照）

三者都能作为安全相关系统的基础组件，但隔离机制、配套生态和认证路径不同。

维度FreeRTOSZephyrRT-Thread
内存隔离部分端口提供 MPU 支持；Armv8-M 有安全/非安全移植用户模式线程 + MPU/MMU 支持，线程隔离是核心设计之一提供线程/内存保护相关组件，能力随版本与配置不同

认证路径生态中存在功能安全/安全认证版本与服务，范围以官方为准有公开的安全响应流程；认证相关信息以官方为准认证与合规信息以官方公告为准

此表只帮助建立概念对应，不构成任何认证结论；涉及认证必须查官方最新文档与证书范围。

落地清单：从“能跑”到“可信”

安全与合规不是最后补的材料，而是贯穿设计、编码、测试和发布的活动。下面这份清单可以直接当作项目自查表。

  • 画出信任边界和数据流：哪些数据来自外部、谁校验、校验失败怎么办
  • 关键任务和内核对象优先静态分配，避免运行期内存失败
  • 打开 configASSERT、栈溢出检测和 malloc 失败钩子，并接入故障日志
  • 看门狗由健康监控任务统一喂，喂狗前检查各任务心跳
  • 通信/OTA 输入先长度后内容，校验 CRC/签名，限制重试次数
  • 生产固件关闭或保护调试口，密钥不落普通 Flash
  • 用静态分析跑 MISRA 规则集，记录偏离，并纳入发布门禁
  • 认证项目尽早确认标准、等级、工具链和证据清单，不要最后补材料

关于认证事实的边界

本文只介绍概念，不给出任何证书等级或“已认证”结论。认证针对具体版本、配置、工具链与证据包，以官方最新信息为准。做合规选型时，直接向芯片厂商、RTOS 厂商和认证机构索取证书范围与证据清单。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

用 configASSERT 校验外部输入

症状
现场收到一帧异常报文，整机就停机或反复复位。
原因
断言用于捕获程序内部错误；外部输入非法是正常情况，不应触发“绝不应该发生”的停机路径。
修复
外部输入用返回错误码 + 丢弃/进入安全状态处理；断言只用于内部不变量，如“任务创建必须成功”。
02

看门狗在主循环里无脑喂

症状
某个任务已经死锁，系统却一直不复位，业务完全停摆。
原因
喂狗点没有反映系统健康，只要主循环还能转到就喂，看门狗形同虚设。
修复
把喂狗放到健康监控任务，确认各关键任务心跳/进度都正常后再喂；调试时用调试器冻结看门狗。
03

认为选了“安全版 RTOS”就完成了认证

症状
项目后期发现证据缺失、工具链不匹配，认证进度严重拖延。
原因
证书覆盖的是特定版本、配置、工具链和证据包，应用代码与集成方式不在默认范围内。
修复
立项时确认认证范围、所需证据和工具链，按标准流程做需求、设计、测试与评审记录。

记住这三句话

  1. 1

    先画信任边界，再谈加密：不知道谁能输入什么，任何安全机制都是盲人摸象。

  2. 2

    看门狗、断言、输入校验和最小权限，是成本最低、收益最高的四道防线。

  3. 3

    标准与认证是“证据工程”：版本、配置、工具链、文档缺一不可，不能靠一句“用了 RTOS”交差。
