启动与移植

把 FreeRTOS 装进一颗陌生芯片：启动链路、向量表、端口层与移植清单

一句话解释

移植 FreeRTOS 不是复制几个文件，而是把“复位→启动文件→SystemInit→main→创建任务→启动调度器”这条链路和芯片的中断系统对齐。

学习目标

  • 1按顺序说出 Cortex-M 从上电复位到第一个任务运行的完整启动链路
  • 2看懂启动文件的向量表，并解释 SVC、PendSV、SysTick 在 FreeRTOS 中各自负责什么
  • 3读懂 FreeRTOSConfig.h 中时钟、tick、优先级、堆和异常映射这几组关键配置
  • 4对照检查清单完成一次移植，并能用最小实验验证 tick 与上下文切换是否正常

生活化比喻

给新公司搭一套管理层

启动文件像公司开门的人：先打开水电（时钟）、把桌椅摆好（内存初始化），再把钥匙交给总经理（main）。FreeRTOS 像一套管理制度：招聘员工（创建任务）、任命经理（调度器）、规定火警流程（中断与异常）。移植就是让这套制度适配这栋楼的门禁、消防和电力系统——制度通用，接口必须一栋楼一栋楼地接。

为什么重要 / 用在哪里

同一份 FreeRTOS 源码可以跑在几十种内核上，靠的是“内核 + 端口层 + 配置”三层分离。真正让初学者卡住的往往不是 API，而是芯片特有的启动细节：向量表放在哪、SysTick 用哪个时钟、中断优先级怎么分组、port.c 里的三个异常有没有接管、堆从哪里来。把这些一次性理顺，后面写业务才有稳定地基。

把官方 Demo 从评估板搬到自己的 PCB从裸机工程升级为 RTOS 工程，同时保留原有驱动更换编译器（GCC / IAR / Keil AC6）或更换内核型号为 Bootloader + 应用程序做向量表重定位排查“调度器一启动就 HardFault”的移植问题

一次上电，芯片到底做了什么？

很多人把 FreeRTOS 移植理解成“把内核源码拖进工程”。但内核只是乘客，真正决定能不能跑起来的是芯片的启动链路：复位向量、启动文件、时钟初始化、C 运行库、main，最后才轮到调度器。

以 Cortex-M + GCC 为例，上电后的顺序是：硬件从向量表取出初始 MSP 和 Reset_Handler 地址 → Reset_Handler 设置栈、调用 SystemInit → C 运行库清 .bss、拷 .data、调用全局构造函数 → 进入 main → 初始化外设 → 创建任务和内核对象 → vTaskStartScheduler() 接管 CPU。

  • 复位（Reset）：PC 跳到 Reset_Handler，此时还没有任何 C 变量可用
  • 启动文件（startup_xxx.s）：定义向量表、栈顶、Reset_Handler 和默认中断处理函数
  • SystemInit：配置时钟树、FPU、向量表偏移（VTOR）等芯片级初始化
  • C 运行库：初始化 .data/.bss，保证全局变量和静态变量是有效值
  • main：外设初始化、创建任务/队列/信号量、启动调度器
  • 调度器：创建空闲任务（和定时器任务），用 SVC 启动第一个任务，之后靠 SysTick + PendSV 维持调度

结论提示（先观察再展开）

启动是一条单向链：硬件取向量 → 启动文件 → SystemInit → C 运行库 → main → 创建任务 → vTaskStartScheduler。移植失败时按这条链逐段检查，比盲改内核源码有效得多。

不同厂商的启动文件、SystemInit 名称与初始化顺序略有差异；以具体芯片的启动文件、链接脚本和官方移植示例为准。

SystemInit 到 main：别让时钟和 FPU 成为暗坑

SystemInit 通常由芯片厂商提供，负责把系统时钟从内部 RC 切到 PLL、设置 Flash 等待周期、使能 FPU、设置向量表偏移。它跑在 main 之前，所以任何“依赖正确主频”的代码都必须放在它之后。

两个最常见的暗坑：第一，没使能 FPU 却编译了浮点任务，第一次执行浮点指令就进 HardFault；第二，Bootloader 跳转后没重定位 VTOR，应用的中断全部落到 Bootloader 的处理函数里。

  • 主频变了，configCPU_CLOCK_HZ 必须同步修改，否则 tick 周期和超时全部不准
  • Cortex-M4F/M7 要使用带 FPU 的 port（如 ARM_CM4F），任务上下文才会保存浮点寄存器
  • 向量表偏移用 SCB->VTOR 设置，地址必须按向量表大小对齐
  • 启动文件里的栈顶符号与链接脚本必须一致，栈落在无效内存会立刻 HardFault

移植层文件：名字先对上号

端口宏 portmacro.hPort Macros
定义 StackType_t/BaseType_t 等类型、栈增长方向、临界区宏与端口相关内联函数。
配置文件FreeRTOSConfig.h
由应用提供的“配置总开关”，决定调度策略、内存、中断优先级和钩子函数。
内存实现heap_x.c
内核堆的实现（heap_1~heap_5），一个工程只能编译其中一个。
启动文件Startup File
定义向量表和复位入口；FreeRTOS 的三个异常处理函数最终要落到这里。
空闲任务Idle Task
调度器自动创建的最低优先级任务，负责回收被删除任务的内存等杂务。

SVC、PendSV、SysTick：调度器的三条腿

FreeRTOS 在 Cortex-M 上把三件事拆给三个异常：SVC 负责启动第一个任务，PendSV 负责真正的上下文切换，SysTick 负责产生周期 tick。这种拆分让内核的切换点集中、可预测。

为什么切换要放在 PendSV？因为 PendSV 可以被“挂起”而不是立刻执行，并且 port 会把它设为最低优先级：当高优先级中断还在处理时，PendSV 一直排队，等所有中断退出后才做上下文切换，从而避免在中断中途换任务。

  • SVC：prvStartFirstTask 执行 SVC 0，异常入口 vPortSVCHandler 恢复第一个任务的栈和寄存器
  • PendSV：任务阻塞/唤醒或 tick 需要切换时，portYIELD 挂起 PendSV，退出中断时完成切换
  • SysTick：每个 tick 进 xPortSysTickHandler → xTaskIncrementTick → 需要切换则挂起 PendSV
  • 临界区：portENTER_CRITICAL 通过 BASEPRI 屏蔽不高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断

中断向量表与 NVIC 优先级：两件容易混的事

向量表决定“中断来了跳到哪里”，NVIC 优先级决定“谁先执行、能不能打断”。FreeRTOS 对两者都有要求：三个异常必须正确映射；中断优先级分组必须是“全部位用于抢占优先级”，否则 configMAX_SYSCALL_INTERRUPT_PRIORITY 的判断会失效。

Cortex-M 的优先级数值越小越高。FreeRTOS 用 BASEPRI 实现临界区：只有优先级数值大于等于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断会被屏蔽。因此，优先级比它更高的中断（数值更小）不能调用任何 FreeRTOS API，包括 FromISR 版本。

  • STM32 HAL 用 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4)，即 4 位全部作为抢占优先级
  • configPRIO_BITS 要与芯片实际实现的优先级位数一致（STM32 常见为 4）
  • configKERNEL_INTERRUPT_PRIORITY 通常是“最低优先级”，保证 PendSV/SysTick 不打断其他中断
  • 在 ISR 中只能调用以 FromISR 结尾的 API，并在退出时用 portYIELD_FROM_ISR 请求切换

配置不是越多越好：先想清楚三个问题

FreeRTOSConfig.h 有上百个宏，但移植阶段真正影响“能不能跑”的只有几组：时钟与 tick、优先级范围、内存、异常映射。其余宏可以先用默认值，等业务需要再打开。

第一，tick 多快？tick 越快，延时分辨率越高，但中断开销越大，1 kHz 是常见折中。第二，优先级要几级？configMAX_PRIORITIES 越大，每个任务占用的就绪表内存越多。第三，堆多大？要按“任务栈 + TCB + 队列/信号量 + 定时器”估算，并留出余量。

  • configCPU_CLOCK_HZ 必须是 SysTick 实际输入频率，而不是“芯片标称主频”
  • configTICK_RATE_HZ 决定 pdMS_TO_TICKS 的换算精度和 tick 中断频率
  • configMAX_PRIORITIES 是档位数，任务优先级取值 0 ~ configMAX_PRIORITIES-1
  • configMINIMAL_STACK_SIZE 的单位是字（Cortex-M 上 1 字 = 4 字节），不是字节

堆从哪里来：heap_1 到 heap_5

FreeRTOS 的动态创建 API（xTaskCreate、xQueueCreate 等）都从内核堆里取内存。内核不直接调用 malloc，而是让你在 portable/MemMang 下选一个 heap_x.c，只编译其中一个。

选型的关键不是“哪个高级”，而是“系统是否需要释放”。如果所有任务和对象在启动时一次性创建、之后永不删除，heap_1 最简单也最确定；需要频繁创建销毁，选 heap_4；内存分散在多块不连续区域（例如内部 SRAM + 外部 SDRAM），选 heap_5。

  • heap_1：只分配不释放，无碎片，执行时间确定，适合“启动时建好一切”
  • heap_2：最佳匹配但不合并相邻空闲块，已不推荐用于新设计
  • heap_3：包装标准库 malloc/free，需要链接器堆，且要保证线程安全
  • heap_4：首次适配 + 合并相邻空闲块，通用性最好，最常用
  • heap_5：在 heap_4 基础上支持多个不连续内存区域，需先调用 vPortDefineHeapRegions
  • 静态分配：configSUPPORT_STATIC_ALLOCATION=1，用 xTaskCreateStatic 等完全绕开堆

移植检查清单：照着打勾，少走三天弯路

下面这份清单按“从底层到上层”排序。每完成一项就做一次最小验证，比全部改完再一起调试高效得多。

  • 选对 port 目录：内核架构（M3/M4F/M7/M33）、编译器（GCC/IAR/Keil）、是否带 FPU/MPU
  • 实现 FreeRTOSConfig.h：至少包含时钟、tick、优先级、最小栈、堆大小、三个异常宏
  • 设置 NVIC 优先级分组为 4 位抢占，并核对 configPRIO_BITS
  • 确认启动文件里的 SVC/PendSV/SysTick 符号能被 port.c 覆盖（无重复定义）
  • 确认 SysTick 时钟源与 configCPU_CLOCK_HZ 一致；用 GPIO 翻转或计数验证 1 秒约 1000 tick
  • 只编译一个 heap_x.c，确认 configTOTAL_HEAP_SIZE 足够
  • 检查 ISR：只调用 FromISR API，优先级不高于 configMAX_SYSCALL_INTERRUPT_PRIORITY
  • 检查任务栈单位与大小，打开 configCHECK_FOR_STACK_OVERFLOW 做压力测试
  • 若使用浮点，确认 port 支持 FPU 上下文保存，并评估 lazy stacking 的影响
  • 若使用 Bootloader，确认应用启动后重设 VTOR

最小验证：两个任务 + 一个中断

移植完成后不要直接上业务。先建两个不同优先级的任务：高优先级任务延时 100 ms 打印一次，低优先级任务持续翻转 GPIO；再用一个定时器中断以 FromISR 方式发送通知。观察：低优先级任务是否被正确抢占、串口时间戳是否稳定、连续运行 30 分钟是否死机。这三项通过，说明 tick、上下文切换和中断协作都是通的。

启动调度器后 HAL_Delay 可能永远不返回

STM32 HAL 依赖 SysTick 中断累加 uwTick。FreeRTOS 接管 SysTick 后，HAL 的 SysTick_Handler 不再被调用，HAL_Delay 就会卡死。常见解法：把 HAL 时基改成 TIM（CubeMX 中 Timebase Source 选 TIMx），或在 vApplicationTickHook 中调用 HAL_IncTick()，或干脆在任务里改用 vTaskDelay。

常见错误与排查

看到症状，先按“原因”定位，再按“修复”验证。

01

只复制内核源码，忘了选 port 和 heap

症状
编译报 vPortSVCHandler、pvPortMalloc 等未定义，或链接后一启动就 HardFault。
原因
FreeRTOS 内核不包含具体芯片的端口层和内存管理实现，必须显式加入对应 port 目录与一个 heap_x.c。
修复
按“内核 + port/编译器/内核型号 + MemMang/heap_x.c”三部分组织工程，并在构建系统中只保留一个 heap 实现。
02

向量表里的 SysTick/SVC/PendSV 没有交给 FreeRTOS

症状
任务能创建，但调度器一启动就停在默认死循环，或 tick 不前进、任务永不切换。
原因
port.c 的异常函数没有被映射成启动文件里的符号，异常落到了启动文件的 Default_Handler。
修复
在 FreeRTOSConfig.h 中添加三个 handler 宏，检查链接 map 文件确认符号来自 port.o 而不是 startup.o。
03

configCPU_CLOCK_HZ 与实际主频不一致

症状
vTaskDelay(1000) 实际延时不是 1 秒，超时、心跳、通信周期全部偏移。
原因
SysTick 的重装载值按错误主频计算，或 SystemInit 改了时钟但配置没有同步。
修复
用示波器或 GPIO 翻转测量实际 tick，按实际 SysTick 输入频率修正 configCPU_CLOCK_HZ。

记住这三句话

  1. 1

    启动链路是“向量表→启动文件→SystemInit→C 运行库→main→调度器”，任何一环与芯片不匹配都会表现为“一启动就死”。

  2. 2

    SVC 启动首任务、PendSV 做切换、SysTick 产生 tick，这三个异常必须正确映射，否则内核根本无法运转。

  3. 3

    移植的成功标准不是“编译通过”，而是“tick 准确、任务可抢占、ISR 能安全通知任务”三件事同时成立。
