DMADirect Memory Access

DMA 是芯片里的专职搬运工：CPU 只说清"从哪搬到哪、搬多少"，它就自己干完，只在搬了一半点个卯、全搬完再叫你。

1 个交互实验 3 道小测验默认 STM32F407 / STM32G474（Cortex‑M4F）

学习目标

  • ·能算出"逐字节用 CPU 搬 1 KB"大概要消耗多少开销，并说清 DMA 到底省了什么
  • ·会按请求映射表给一个外设挑 stream / 通道，并配好方向、地址自增、数据位宽
  • ·分得清单次（Normal）与循环（Circular），会用半传输（HT）与完成（TC）中断做双缓冲
  • ·能用 __HAL_LINKDMA + HAL_UART_Transmit_DMA 写出可用的串口 DMA 收发，并在回调里正确收尾

一句话解释

DMA 是芯片里的专职搬运工：CPU 只说清"从哪搬到哪、搬多少"，它就自己干完，只在搬了一半点个卯、全搬完再叫你。

生活化比喻

DMA 像仓库里的专职搬运工

老板（CPU）要发货，最笨的办法是自己跑一趟趟仓库，一件件搬到货车上——搬的时候什么正事都干不了，而且大部分时间花在"等对方把货递过来"（等外设状态）。请了搬运工（DMA）之后，老板只需要递一张单子：从 A 货架搬到 B 货架、一共多少件、几件一组。搬运工自己跑，每搬一组还会在小本子上把剩余数量减一，搬到一半通知你一声"前半车装好了"（HT），全部装完再通知一次"可以发车了"（TC）。老板在整段时间里可以继续谈生意——这就是 DMA 的意义。

为什么重要 / 用在哪里

  • 01串口、ADC、SPI 这类"大量小数据"场景，搬运开销往往比处理本身还大：CPU 忙着读状态位、读数据寄存器、写内存，真正的算法被挤得没有时间。
  • 02实时性的关键杠杆：同样一颗 168 MHz 的 M4，用 DMA 之后 CPU 可以把时间花在滤波、协议解析和 UI 刷新上，而不是当搬运工。
  • 03降低响应抖动：轮询的延迟取决于循环转多快，DMA 只在 HT/TC 两点打断你，延迟可预测，更适合控制和采样。
  • 04几乎所有"连续"功能都靠它：ADC 多通道扫描、串口不定长接收、DAC 输出波形、SPI 刷屏、定时器触发采样，背后都是 DMA 在搬。

为什么需要 DMA

先算一笔账：不搬这一 KB，CPU 到底忙在哪。

轮询和中断解决的是"什么时候有数据"，但没解决"把数据从一个地方搬到另一个地方要花多少次读写"。以串口为例：115200 波特率下收 1 KB，光在线上就要 约 89 ms（示意计算：1024 字节 × 10 位 ÷ 115200，10 位含起始位与停止位）。如果用轮询，这 89 ms 里 CPU 要反复读状态位、判断、读数据寄存器、写内存——每字节至少三四次外设访问，累计上千次循环（示意量级），而且绝大部分时间是在外设那里等，不是在算东西。

DMA（Direct Memory Access，直接存储器访问） 把这条链路改成硬件自治：CPU 只写几个寄存器（源地址、目的地址、数量、方向、位宽），然后一句"开始"，DMA 控制器就在外设与内存之间自己搬。每搬一个数据项，它不需要取指令、不需要压栈、不需要你写一行代码；你只在"搬完一半"和"全搬完"时各被打断一次。

DMA 不会让总线变快：它和 CPU 抢的是同一条总线、同一片 SRAM，多个 stream 同时搬还会按优先级排队。它省下的是"CPU 亲手搬"这一整段软件开销——搬运这种不需要思考的活，交给硬件比交给软件便宜一个量级。

流、通道与请求源

F4 的 DMA 是三层结构：控制器 → 流 → 通道。搞清这三层，映射表就不再是天书。

STM32F407 有两个 DMA 控制器（DMA1、DMA2），每个控制器有 8 个流（stream）。一个流就像一条独立的搬运通道：有自己的源地址、目的地址、剩余数量与中断标志。麻烦的地方在于——每个流能听谁的是芯片里固定接好的：每个流可以选择 8 个通道（channel）之一，而通道对应的是具体的请求源（USART1_TX、ADC1、SPI1_RX…）。这张"谁连谁"的表就是参考手册里 DMA 章节的请求映射表，CubeMX 选外设时会替你查好。

地址自增与数据位宽

四个旋钮：两端地址各自增不自增、两端各按多宽搬。配错任何一个，数据就错位。

PAR（外设地址寄存器） 与 M0AR（内存地址寄存器） 各存一个起始地址，NDTR 存数量。每搬一个数据项，硬件把"允许自增"的那一侧地址加上一个位宽（8 位加 1、16 位加 2、32 位加 4），NDTR 减 1。所以"外设地址固定 + 内存地址自增"是最常见的一对：外设的数据寄存器就那一个地址，每来一个数据都往同一个地方写；而内存缓冲要一个接一个地排下去。

位宽决定"一个数据项多大"。外设是 8 位数据寄存器、内存却想按 16 位存储，就必须开 FIFO 模式让硬件做打包与拆包；直连模式（FIFO 关闭）要求两端位宽一致，不一致时数据会错位——这正是"串口收了一半数据""ADC 采样值整体偏移"这类怪现象的常见原因。还要记住：位宽只描述单次搬运的宽度，不改变字节序，多字节数据在内存里的排列仍然按小端存放（F4/G4 是小端）。

两个必查的坑：对齐与单位
① 对齐：32 位传输要求地址按 4 字节对齐，16 位按 2 字节对齐，否则可能触发总线错误或传输出错标志。② NDTR 的单位是数据项：配 16 位宽、NDTR = 64，实际搬的是 128 字节。接 CS 片选、算超时时按"字节数"想问题，写寄存器时按"数据项数"填，是最容易出的一处换算错误。

单次、循环与 HT/TC 中断

两种模式决定"搬完之后怎么办"，两个中断决定"你什么时候知道进度"。

单次模式（Normal）：NDTR 减到 0 时硬件关掉该流的使能位，传输结束。要再传，必须重新设置长度并再次启动。循环模式（Circular）：NDTR 减到 0 的瞬间被自动重装成初值，硬件从缓冲开头继续搬，永不停止——这正是连续采样、DAC 输出波形、串口持续接收想要的。

HT（Half Transfer，半传输） 与 TC（Transfer Complete，传输完成） 是 DMA 仅有的两个进度通知：NDTR 减到一半时置 HT 标志，减到 0 时置 TC 标志。中断使能位在 CR 里（HTIE / TCIE），标志与清除方式见参考手册。它们真正的价值是回答一个问题——"哪一半数据此刻是安全的"：循环模式下缓冲一直被覆盖，用 HT 处理前半、TC 处理后半，你读的那一半就保证没被正在进行的传输踩到，这就是最简单的双缓冲。

循环模式下别用 NDTR 判断进度
你读到的 NDTR 只是一个瞬时值；TC 之后它立刻被重装，永远不会停在 0。想判断"第几块数据可用"，就用 HT/TC 回调维护计数（或用双缓冲标志位），别去猜 NDTR 现在到哪了。

和串口配合：收发交给 DMA

串口是 DMA 最典型的搭档：收一个字节、发一个字节都是"外设 ↔ 内存"。

串口的收发天生就是一串 8 位数据项在 UART 数据寄存器与内存缓冲之间流动，正好是 DMA 的活。HAL 把这套协作拆成两步：先用 `__HAL_LINKDMA` 把 DMA 句柄挂到 UART 句柄上，之后就能用 `HAL_UART_Transmit_DMA` / `HAL_UART_Receive_DMA` 一句话启动。

__HAL_LINKDMA(&huart1, hdmatx, hdma_usart1_tx) 做的是双向绑定：让 huart1.hdmatx 指向这个 DMA 句柄，同时让 DMA 句柄的 Parent 指回 huart1。HAL 的 UART 驱动在中断里就是靠这两根指针找到"该回调谁、该清哪个状态"——所以这行不能漏，也不能挂错方向（发送挂 hdmatx，接收挂 hdmarx）。

  1. 开时钟：DMA 控制器挂在 AHB1 上，先 __HAL_RCC_DMA2_CLK_ENABLE()；时钟没开，后面所有寄存器写入都无声无息地无效。
  2. 查映射表：USART1 的发送与接收分别接在哪个控制器、哪条流、哪个通道，是芯片固定接好的，照参考手册的请求映射表抄（CubeMX 会自动选）。
  3. 填四个关键参数：方向（发送是内存 → 外设）、两端自增（内存自增、外设不自增）、两端位宽（串口都是 8 位）、模式（发送用 Normal，接收常用 Circular）。
  4. 初始化并关联：HAL_DMA_Init 之后紧跟 __HAL_LINKDMA，把 DMA 挂到 UART 句柄上。
  5. 开中断：使能该流对应的 NVIC 中断（如 DMA2_Stream7_IRQn），优先级按实时性要求给。
  6. 启动与收尾：HAL_UART_Transmit_DMA / HAL_UART_Receive_DMA 启动，在 HAL_UART_TxCpltCallback（发送）与接收方向的半传输/完成回调里置标志、处理数据。
三个必须记住的点
① 缓冲要活到传输结束：把栈上的局部数组交给 DMA，函数一返回那块内存就被复用，现象是偶发乱码或数据错乱，且换个编译选项就"好了"，极难查。② `HAL_UART_Transmit_DMA` 是异步的：函数返回只代表"已经开始发"，不代表"发完了"；句柄处于 BUSY_TX 时再次调用会返回 HAL_BUSY。③ 只有完成回调里才能复用缓冲，别在主循环里一拍脑袋就把新数据写进去。
接收更推荐"循环 + 半边处理"
HAL_UART_Receive_DMA 配 Circular 模式，HT 回调处理前半、TC 回调处理后半，天然就是一个双缓冲：处理时另一半正在被写，互不干扰。再配合串口的空闲（IDLE）中断，就能做"不定长帧"接收——空闲即一帧结束，细节不在这里展开。

三种写法与缓存一致性

同一个"启动一次传输"，HAL、LL、寄存器三层各写一遍，你会发现自己其实只在填四个地方。

启动同一次 DMA 传输的三种写法

三者最终写的都是 PAR / M0AR / NDTR / CR 这几个寄存器，区别只在"谁替你算地址、谁替你选通道、谁替你清标志"。

缓存一致性只对有数据缓存的内核才是问题：Cortex‑M7（如 STM32H7）带 D‑cache，DMA 直接写内存时 CPU 可能仍读缓存里的旧值，需要在传输前后做 clean / invalidate；M4/M4F（F407、G474）没有数据缓存，不涉及这件事——所以你现在写的代码不用查这一条，但换到 H7 时必须补上。

把 DMA 和启动流程放在一起看很有意思：启动流程回答"上电后 CPU 从哪儿取第一条指令"，DMA 回答"CPU 之外还有谁能直接动内存"。两者指向同一件事——总线与存储器是共享资源，谁在用它、按什么规则用，决定了系统的行为。

这一页收束成三层就够用了：请求源 → 流 / 通道 → 地址与数量，再配上方向、自增、位宽、模式四个旋钮，最后用 HT/TC 中断收尾。下一页进入 定时器/PWM：它和 DMA 是一对高频搭档（定时器触发 ADC、DMA 搬波形表），正好接着用。

常见错误与排查

错误现象怎么查 / 怎么改
只配了 DMA 却没使能对应流的 NVIC 中断（或中断函数名写错）数据其实已经搬完了，但 `XferCpltCallback` / `HAL_UART_TxCpltCallback` 永远不执行，主循环一直等标志按顺序查：串口/外设自己的中断使能位 → `NVIC->ISER[]` 是否放行 → `DMA2_StreamX_IRQHandler` 名字是否与启动文件向量表完全一致 → 里面有没有调用 `HAL_DMA_IRQHandler`。
把栈上的局部数组直接交给 DMA 发送偶发乱码、数据错乱或只发出前几个字节；改成 -O0 或加了打印又"看起来正常"，极难复现DMA 缓冲必须是 `static` 全局数组或堆上常驻内存，并且要活到 TC 回调之后；发送前先 memcpy 进常驻缓冲再启动。
位宽配错（外设 8 位、内存 16/32 位）却关着 FIFO串口收一半就不动了、ADC 采样值整体偏移或翻倍、缓冲区数据明显错位直连模式要求两端位宽一致；确实要打包/拆包就打开 FIFO 模式，并核对 NDTR 用的是"数据项数"还是"字节数"。
循环模式启动后以为"传完就停"，直接去改缓冲或再次启动数据永远在变、读到的值半新半旧；再次启动返回 HAL_BUSY；停止后缓冲还一直被动写入循环模式只有主动中止（`HAL_DMA_Abort` 等）才会停；读数据用 HT/TC 回调切分安全区，要停就明确写中止流程并把状态复位。
方向（内存 → 外设 / 外设 → 内存）或通道选错启动返回成功、NDTR 也在减，但外设一个字节都不出（或收到的数据被写进了错误的缓冲）照参考手册的请求映射表逐项核对：控制器、流、通道、方向四项必须同时对上；用 CubeMX 生成一版对照是最快的验证方式。

判断：既然用了 HAL_UART_Transmit_DMA，说明 CPU 不参与搬运，那么把一个函数内部的局部数组传给它也没问题——函数立刻返回时，数据其实已经发出去了。

记住这三句话

  1. 01DMA 省的不是带宽，而是 CPU 的参与次数：给定源地址、目的地址、数量、方向与位宽之后，搬运由硬件完成，CPU 只在启动、半传输和完成时出手。
