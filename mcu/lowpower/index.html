低功耗与看门狗Low Power Modes & Watchdog

让 MCU 按需睡深睡浅，用一个倒计时的狗保证它睡醒或跑飞后仍能自愈。

2 个交互实验 3 道小测验默认 STM32F407 / STM32G474（Cortex‑M4F）

学习目标

  • ·能说清 Sleep / Stop / Standby 三档睡眠各关了什么、丢了什么、唤醒后从哪里继续跑
  • ·会用 SCB->SCR 的 SLEEPDEEP 与 WFI/WFE 进入低功耗，并写出 HAL 三个 Enter 函数
  • ·知道 Stop 唤醒后为什么必须重配时钟，能列出合法唤醒源
  • ·会用“电荷 = 电流 × 时间”估算平均电流与电池寿命，并能区分 IWDG 与 WWDG 的职责

一句话解释

让 MCU 按需睡深睡浅，用一个倒计时的狗保证它睡醒或跑飞后仍能自愈。

生活化比喻

低功耗像打工人的三种休息

Sleep 是趴在工位上打个盹：电脑没关、文件还开着，有人叫你一声立刻接着干活。Stop 是关显示器趴下睡：桌上东西都还在，但灯灭了、空调停了，起来得自己重新开灯（重配时钟）。Standby 是下班锁门回家：第二天再来是拿着工牌重新进门（复位重启），桌上的草稿纸（SRAM）已经被清走了。看门狗则是老板的定时巡查：你必须在规定时间内在工位上签个到，人不在就换人（复位）。

为什么重要 / 用在哪里

  • 01电池寿命就是低功耗的直接产物：传感器节点 99% 的时间在等数据，醒着的那几十毫秒决定不了续航，睡着时的几 µA 才决定。
  • 02干扰与发热：功耗低意味着电源纹波小、温升低，模拟采样（ADC）的精度也更稳。
  • 03看门狗是量产必需的自愈机制：现场没人按复位键，程序跑飞只能靠狗把系统拉回来。
  • 04面试高频：三档模式的差异、Stop 唤醒后为什么要重配时钟、为什么不在中断里喂狗，这三问几乎必考。

为什么值得为“睡眠”写代码

先建立量级感：醒着与睡着之间差的是几百倍，不是百分之几。

在电池供电的节点里，MCU 的全部工作可以抽象成一个占空比问题：每 1 秒里醒 10 ms 干活、剩下 990 ms 睡觉。平均电流不是“运行电流打个小折”，而是运行电流被摊薄了约一百倍。搞清楚这件事，你就明白为什么值得为几毫秒的唤醒时间、为几 µA 的漏电去较劲。

  • 唤醒开销属于“醒着”的一部分：唤醒要花的几百微秒同样是运行电流，次数越多越亏，所以常听到“能一天报一次就别一秒报一次”。
  • 板级静态电流会兜底：稳压器静态电流、传感器待机电流、上拉电阻漏电，随便一项都可能比 MCU 的 Stop 电流还大。

三档睡眠模式对比

核心口诀：睡得越深越省电，但唤醒越慢、丢的东西越多、醒来之后越接近“重新开始”。

STM32 的低功耗模式本质是关掉不同层次的时钟与电源。Cortex‑M 内核看到的是 SLEEPDEEP 这一位：SLEEPDEEP=0 睡成 Sleep（只停内核时钟），SLEEPDEEP=1 睡成深睡，再由 PWR->CR 里的 PDDS/LPDS 决定是 Stop 还是 Standby。下表是三种模式的关键差异，背下来比背寄存器有用。

怎么选：先问“醒来还要不要原来那份现场”
要现场（变量、外设状态、通信链路）→ Sleep 或 Stop；只要“到点了重新采一次、重新连一次” → Standby。想省到极致又需要保持 RAM，还可以看 L 系列/G4 的“Standby + SRAM 保持”选项，那是厂商给的额外开关，不属于基础三档。

进入睡眠的硬件开关

真正让 CPU 停下来的只有一条指令：WFI 或 WFE。低功耗寄存器只是“把床铺好”。

WFI（Wait For Interrupt，等中断）：执行后 CPU 暂停取指，直到有中断请求（哪怕该中断被 NVIC 屏蔽，只要在 EXTI/外设处挂起就能唤醒，具体看模式与配置）。WFE（Wait For Event，等事件）：等的是“事件”，可以由中断、SEV 指令或事件寄存器置位产生。两者的差别在于：WFI 一定会进 ISR，WFE 可以在没有中断的情况下被事件唤醒继续执行——所以 Stop 里想“只醒来看看，不一定要处理中断”时常用 WFE。

深度由 SLEEPDEEP 决定：SCB->SCR 的 SLEEPDEEP 置 1 时，WFI/WFE 进入深度睡眠（Stop/Standby，具体哪个由 PWR->CR 的 PDDS 决定：PDDS=0 是 Stop，PDDS=1 是 Standby；LPDS 选择 Stop 时稳压器是否切到低功耗）。清 0 则是 Sleep。

  1. 开 PWR 时钟：低功耗相关的寄存器在 PWR 上，HAL 里用 __HAL_RCC_PWR_CLK_ENABLE()；没开时钟，后续写入全部无效。
  2. 选定睡眠深度：Sleep 清 SLEEPDEEP；Stop/Standby 置 SLEEPDEEP，并用 PWR->CR 的 PDDS/LPDS 区分（HAL 函数会替你算）。
  3. 配好唤醒源并使能中断：EXTI 线要配触发边沿与 HAL_NVIC_EnableIRQ；RTC 唤醒定时器要 HAL_RTCEx_SetWakeUpTimer_IT；Standby 还要 HAL_PWR_EnableWakeUpPin 使能 WKUP 引脚。
  4. 清掉旧的唤醒标志：__HAL_PWR_CLEAR_FLAG(PWR_FLAG_WU) 清 PWR->CR 的 CWUF，否则可能“刚睡下就醒”。
  5. 执行 WFI/WFE：HAL 里就是 HAL_PWR_EnterSLEEPMode / HAL_PWR_EnterSTOPMode / HAL_PWR_EnterSTANDBYMode，函数内部会自己置位 SLEEPDEEP 再执行指令。
  6. 醒来后收尾：Stop/Sleep 返回后继续跑（Stop 要重配时钟）；Standby 没有返回，直接复位重启。
“让 CPU 睡下”的三种写法

三种写法最终都落在“置/清 SLEEPDEEP + 执行 WFI”上，区别只是谁帮你算寄存器。

Stop 唤醒与重配时钟

这一段是低功耗最容易翻车的地方：醒来后的第一件事不是干活，是把时钟配回去。

为什么 Stop 醒来必须重配时钟：Stop 期间 HSE 与 PLL 全部关停，退出 Stop 时芯片会自动切回内部 HSI（F407 上 HSI 是 16 MHz 量级）以保证 CPU 能继续跑。此时 SYSCLK 不再是你精心配的 168 MHz，所有按 PLL 频率计算出来的时序全部错位：UART 波特率偏低导致串口乱码、HAL_Delay 变慢几十倍、定时器周期不对、SPI 速率也不对。所以标准动作是——唤醒后立刻调用 SystemClock_Config()（CubeMX 生成的那个函数），把 PLL 和总线分频重新配回来。

  • EXTI 线：按键、传感器中断脚、RTC 的唤醒输出都可以经 EXTI 唤醒；配置要点是触发边沿 + HAL_NVIC_EnableIRQ，且 Stop 期间不能用“电平敏感”的线（电平一直有效会立刻醒）。
  • RTC 闹钟 A/B 与唤醒定时器：RTC 在备份域，Stop/Standby 都活着，是最常用的“定时醒来”手段；HAL_RTCEx_SetWakeUpTimer_IT 设周期，HAL_RTCEx_DeactivateWakeUpTimer 收工。
  • WKUP 引脚：Standby 最常用的唤醒方式，要先 HAL_PWR_EnableWakeUpPin；F407 只有 1 个 WKUP 引脚（PA0），G474 有多路。
  • IWDG：Stop/Standby 里 IWDG 仍在计数，但它只能产生复位，不是“继续执行”的唤醒——别把它当成定时醒来的手段。
  • NRST：任何时候都能把芯片拉回复位状态，Standby 里等同重启。

功耗估算：电荷守恒的算术

低功耗不需要玄学：把“醒了多久、睡多久、各自多少电流”写下来，就能估算续航。

先看电荷：电流是电荷的流动速率，I × t 就是这段时间搬运的电荷量；电池标称的 mAh 本身就是“mA × h”的电荷单位。所以平均电流可以按“电荷加权”算：把每个状态贡献的电荷加起来，再除以总时间。

举例（全部为示意量级，用来练算法）：某个节点每 1 秒醒 10 ms，醒着时 90 mA；其余 990 ms 在 Stop，约 0.5 mA。代入公式：(90 × 10 + 0.5 × 990) / 1000 ≈ 1.4 mA。挂一块 2000 mAh 的电池，2000 / 1.4 ≈ 1400 小时，约 58 天。而如果一直不睡、按 90 mA 跑，只有约 22 小时——这就是“值不值得写睡眠代码”的答案。

估算时最容易漏的三项
① 唤醒开销：每次醒来都要把 HSI/PLL 拉起来，几 µs~几十 µs 的高电流不算白不算；② 稳压器静态电流：LDO 自己也要吃几 µA 到几十 µA，µA 级设计里它常是下限；③ 外围器件：传感器待机电流、上拉电阻漏电、LED 指示灯，往往比 MCU 的 Stop 电流大。

两种看门狗的区别

低功耗让系统长时间无人值守，看门狗就是那个“没人管也能自愈”的保险丝。

看门狗（Watchdog）是一个只会倒数的定时器：程序必须在它数到 0 之前“喂”一次（重新装载计数值），否则它就复位芯片。它的价值在于不依赖软件是否正常：主循环卡死、指针跑飞、任务饿死、硬件外设挂死时，喂狗动作不再发生，复位把系统拉回来。

IWDG 的键操作（F407/G474 一致）：向 IWDG->KR 写 0x5555 解锁，才能改 IWDG->PR（预分频）与 IWDG->RLR（重装值）；写 0xCCCC 启动看门狗（启动后不能软件关闭）；写 0xAAAA 喂狗，把计数器重新载入 RLR。改完 PR/RLR 后可以读 IWDG->SR 看更新是否完成。HAL 里对应 HAL_IWDG_Init 与 HAL_IWDG_Refresh，喂狗这一步被封装成 HAL_IWDG_Refresh(&hiwdg)。

WWDG 的寄存器：WWDG->CR 里除了 7 位递减计数器 T，还有使能位 WDGA（置位后看门狗开始工作）；WWDG->CFR 里配窗口值 W、预分频，以及“早期唤醒中断（EWI）”开关。喂狗（重装 T）必须落在“计数器已经降到窗口值以下、但还没到下限”的区间：太晚超时复位，太早（计数还在窗口之上）同样复位。具体字段与下限值见参考手册 WWDG 章节，HAL 侧对应 HAL_WWDG_Init 与 HAL_WWDG_Refresh。

为什么喂狗要放主循环，而不是定时器中断：定时器中断是硬件按固定周期触发的，它完全绕过了你的业务代码。如果主循环因为死等、跑飞、栈溢出、某个任务饿死而停摆，定时器 ISR 依旧准时执行、依旧在喂狗——看门狗被“养得好好的”，永远不复位，系统就那样静静地挂死。看门狗要监控的恰恰是“业务主流程是否还在推进”，所以喂狗点必须放在能证明主流程跑完一圈的地方：主循环末尾、或者 RTOS 里“每个任务都上报心跳后由监工统一喂”。

常见错误与排查

错误现象怎么查 / 怎么改
Stop 唤醒后没有重新配置时钟睡眠实验“成功”了，但串口发出乱码、`HAL_Delay(1000)` 变成好几秒、定时器周期不对Stop 退出后 CPU 跑在 HSI 上，唤醒后第一件事就是调用 `SystemClock_Config()`，再重新初始化依赖主频的外设。
进 Stop 前没清唤醒标志、或没配好唤醒源中断要么“根本没睡下去”，要么睡下去再也醒不过来（只能按复位）先 `__HAL_PWR_CLEAR_FLAG(PWR_FLAG_WU)` 清旧标志；再确认 EXTI/RTC 唤醒定时器的中断已使能、NVIC 已打开、触发边沿不是电平型。
把喂狗写在定时器中断里主循环早就卡死了，系统却一直不复位，现场表现为“设备彻底没反应但灯还在闪”喂狗点必须是主循环末尾或“监工任务”里；定时器 ISR 只能用来上报心跳，不能直接喂狗。
以为 Standby 醒来后变量还在唤醒重启后读到全局变量是随机值，程序行为莫名其妙Standby 会丢 SRAM：需要跨睡眠保存的数据放备份寄存器（RTC 的 BKP 寄存器组，见参考手册 RTC 章节）或写入 Flash/EEPROM，并在启动时判断唤醒来源。
照抄别人的超时时间，不按 LSI 的误差留余量实验室一切正常，低温或低压环境里设备周期性自己重启按手册给出 LSI 的最小频率算最长超时、按最大频率算最短超时，取交集后再留 30%–50% 余量（示意）；关键路径上也可以改喂狗策略而不是硬拉长。
