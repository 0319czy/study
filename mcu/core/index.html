内核与存储器CPU Core & Memory

内核只有 16 个寄存器，你的每个变量、每次函数调用都落在它们和 Flash/SRAM 的几段地址上。

3 道小测验默认 STM32F407 / STM32G474（Cortex‑M4F）

学习目标

  • ·能说出 R0–R12、SP、LR、PC、xPSR 各自负责什么，以及哪些是“被调用者保存”
  • ·讲清 MSP / PSP 双栈为什么存在，以及中断压栈时硬件到底存了哪些字
  • ·能把一段 C 变量对应到 .text / .data / .bss / 堆 / 栈，并看懂链接脚本的 MEMORY 片段
  • ·能解释 Bootloader 跳到 APP 时必须改 SCB->VTOR 的原因与步骤

一句话解释

内核只有 16 个寄存器，你的每个变量、每次函数调用都落在它们和 Flash/SRAM 的几段地址上。

生活化比喻

内核像厨师，存储器像一间有编号的厨房

厨师（CPU 内核）手上只有 16 个位置放东西：R0–R12 是案板上的小碟子，装正在切的菜；SP 是“叠好的盘子堆”的顶面标记，谁要用盘子就往下挪一格；LR 记着“等会儿回到哪道工序”；PC 指着“现在正在做哪一步”。Flash 是写满菜谱和存货的冷冻库（断电也在），SRAM 是案板（一关火就清空）。菜谱里说“取一勺盐”这种有初始量的原料，得在上岗前从冷冻库搬到案板——这就是启动代码搬 .data；而“拿个干净碗”这种全空的容器，不用从冷库搬，现场洗一下就行——这就是清 .bss。

为什么重要 / 用在哪里

  • 01HardFault 的绝大多数根因都在这一页：栈溢出、栈顶地址写错、向量表没重定位，都是“内存没摆对”，而不是外设配错。
  • 02会算内存，才配谈优化：同一句 static uint8_t buf[1024]，加不加初值、加不加 const，占的是 Flash 还是 SRAM 完全不同。
  • 03Bootloader / OTA 的地基：不做向量表重定位，APP 里的中断永远回不到 APP，现象诡异且难查。
  • 04看懂 .map 文件与链接报错：region RAM overflowed 这类报错只有理解了 MEMORY 与段分配才读得懂。

内核只有 16 个寄存器

C 语言看起来很自由，编译器最终只在这 16 个位置和栈之间搬数据。

Cortex‑M4 属于 ARMv7‑M 架构。程序员可见的寄存器一共 16 个：R0–R12 是通用寄存器，R13 / R14 / R15 有固定用途（分别是 SP 栈指针、LR 链接寄存器、PC 程序计数器），另外还有一个状态寄存器 xPSR（Program Status Register，程序状态寄存器，内部按用途分成 APSR / IPSR / EPSR 三个视图）。

为什么函数指针都要 +1（或写 0x0800xxxx 的奇数）
Cortex‑M 只执行 Thumb 指令，地址最低位为 1 表示“这是 Thumb 代码”。所以向量表里存的 Reset_Handler 地址、你写的函数指针，末位通常是 1；调试器显示函数地址时往往把这一位隐去，看起来是偶数——这只是显示习惯，不代表地址真的变了。写 Bootloader 跳转、注册回调时，别自己去做“对齐”把这一位清掉。
不要手改 PC / SP
除了 Bootloader 跳转这种必须接管 CPU 的场合，任何业务代码都不该直接写 PC 或 SP。需要“跳转”就用函数调用，需要“换栈”就让 RTOS 去做。乱改这两个寄存器造成的崩溃，现象往往和真正的原因完全无关。

栈：MSP、PSP 与压栈内容

栈不是“一块内存”，而是一条约定：SP 从高地址往低地址长。

Cortex‑M 的栈是满递减（full‑descending）：压栈时先把 SP 减 4 再写入，出栈时先读再 SP 加 4。所以 SP 永远指向“最后一个已压入的单元”，初始栈顶取 SRAM 的末尾（高地址），栈向下生长；堆（malloc 用的区域）向上生长。两边相向而行，中间那个空隙就是你的安全余量——相撞就是溢出。

MSPMain Stack Pointer
主栈指针。复位后 CPU 默认用它；所有异常/中断（Handler 模式）里硬件强制用 MSP。裸机程序通常只有它。
PSPProcess Stack Pointer
进程栈指针。只在 Thread 模式下可用，需要软件把 SP 切过去。RTOS 用它给每个任务分配独立栈，做上下文切换。
Handler / Thread 模式Handler mode / Thread mode
Thread 模式跑普通代码，Handler 模式跑异常和中断。从 Thread 进 Handler 由硬件完成，退出时靠 LR 里的 EXC_RETURN 标记自动还原。
EXC_RETURNException Return value
异常返回时 LR 里保存的特殊标记（形如 0xFFFFFFF9），它告诉硬件“回哪个模式、用哪个栈指针、要不要恢复浮点上下文”。

双栈的意义：中断永远在 MSP 上跑，任务代码跑在各自的 PSP 上。这样一个任务把栈踩爆，不会顺手把中断栈也踩坏——RTOS 靠这个特性把“任务栈溢出”这件事从“整机随机崩溃”降级成“某个任务挂掉”。裸机工程里通常只初始化 MSP，PSP 根本没被用过。

  • 进入异常时硬件自动压 8 个字：R0–R3、R12、LR、PC、xPSR，共 32 字节，并保证 8 字节对齐（不对齐时补一个填充字）。这就是“C 函数不用写任何代码也中断安全”的原因。
  • 开了 FPU 又多一截：如果异常发生时浮点上下文是活跃的，硬件会再压入 S0–S15、FPSCR 与一个保留字，共 18 个字；加上基础帧 8 个字，一共 26 个字（104 字节，见 ARMv7‑M 架构参考手册）。所以在中断频繁的系统里，MSP 余量要按最坏情况算。
  • xPSR 里的 IPSR 记着异常号：想知道“现在在哪个中断里”，读 IPSR 比自定义标志变量可靠，因为它由硬件维护。
  • AAPCS 要求 8 字节对齐：函数入口处 SP 必须 8 字节对齐，所以编译器可能在你的栈上塞填充。算栈用量时别只数局部变量。
栈溢出的典型表现与查法
厂商启动文件里 Stack_Size 常见默认值是 0x400（1 KB 量级，示意，务必看自己的启动文件）。递归、大局部数组、printf/sprintf 系列（栈开销很大）都可能把它踩穿。溢出的方向是往下，也就是先踩到 .bss 里的变量，所以症状往往是“某个毫不相关的全局变量莫名变了”“加一行打印就好了”。查法：看 .map 文件确认 _estack 与 .bss 的相对位置；在栈区预先填 0xA5A5A5A5 这样的水印，跑一段时间后看最深处的水印被冲到哪；实在不行就把 Stack_Size 调大、把大数组改 static。

Flash 与 SRAM：地址地图与五个段

“程序下载进去了”和“程序在跑了”，说的是两个不同的地址区间。

STM32F407 把片内 Flash 映射在 0x08000000，SRAM 映射在 0x20000000，外设寄存器在 0x40000000 一带，内核私有外设（NVIC、SysTick、SCB）在 0xE0000000 一带。上电时 Flash 还会被别名到 0x00000000（由 BOOT 引脚/选项字节决定启动映射，见参考手册），所以内核复位时从 0x00000000 取到的第一个字，其实就是 0x08000000 处那个栈顶值。

五个段决定了你的变量到底住哪。注意 .data 是“双份”的：初值必须跟着固件一起烧进 Flash（否则断电就没了），运行时再由启动代码复制到 SRAM 变成活数据。所以同一个 .data 变量既占 Flash 又占 SRAM，而 .bss 只占 SRAM。

  • 加 `const` 就往 Flash 挪：const 的全局表（字库、波形表、字符串）通常落在 .rodata，直接省下等量 SRAM。代价是只能读。
  • 不初始化的大数组最省事：全局大 buffer 不写初值 → .bss，固件体积不变，但 SRAM 照占。写个 = {0} 和完全不写，在 C 里对全局变量是同一回事（都进 .bss）。
  • 局部大数组是最贵的写法：局部变量在栈上，uint8_t buf[2048] 写在函数里就是一口气吃掉 2 KB 栈；写成 static 就搬到 .bss，栈立刻轻松。
  • CCM 不是普通 SRAM：它挂在 CPU 的 D‑bus 上，DMA 访问不到。把 UART/ADC 的缓冲放进去，DMA 收不到数据、还可能不报错——典型静默失败。
VMA 与 LMA：同一个段的两个地址
链接脚本里 .data 的 VMA（运行地址，Virtual Memory Address）在 SRAM，LMA（装载地址，Load Memory Address）在 Flash。烧写工具按 LMA 把初值写进 Flash；启动代码再按 VMA 把它们搬到 SRAM。看懂这两个词，.data 为什么“双份”、启动文件为什么要搬它，就全通了。

链接脚本与启动搬运

链接脚本决定段放哪，启动代码负责把 .data 搬过去、把 .bss 清零。

链接脚本（STM32 上通常是 .ld 文件，IAR 用 .icf、Keil 用分散加载 .sct）只回答两个问题：存储器从哪到哪（MEMORY 命令），每个段放哪里（SECTIONS 命令）。容量写错是最隐蔽的错误：LENGTH 写成比实际 SRAM 大，编译器不会报错，上板一用到大数组就 HardFault。

同一个全局变量，三种视角

C 代码里你只写了一个变量；编译器决定它进哪个段；链接脚本决定这个段最终落在哪个地址。

链接脚本给好了地址，还差一个干活的：Reset_Handler。下面这段是启动文件里汇编逻辑的 C 等价写法，看懂它就懂了“为什么 main 之前要搬内存”。

  1. 取初始 MSP：内核从 0x00000000（Flash 的别名地址）读第一个字，写进 SP。所以链接脚本的 _estack 必须合法。
  2. 取复位入口：读第二个字作为 Reset_Handler 地址，把它装进 PC — 这一步由硬件完成，没有软件参与。
  3. 搬 .data：按 LMA→VMA 复制初值，有初值的全局/静态变量从这一刻起才有正确内容。
  4. 清 .bss：把未初始化的全局/静态变量区整体清零，保证 C 标准承诺的“初值为 0”。
  5. 调 SystemInit()：配置时钟树、使能 FPU、设置向量表偏移（视工程配置），为 C 代码准备运行环境。
  6. 跑构造函数再进 main()：__libc_init_array() 执行 C++ 全局对象构造与 __attribute__((constructor)) 函数，之后才轮到你的 main()。

Bootloader 与向量表重定位

硬件复位永远从 0x08000000 取向量表，所以“把 CPU 交给 APP”必须靠软件完成。

带 Bootloader 的固件分成两块：Bootloader 占 0x08000000 起的区域，APP 从某个偏移开始（例如 0x08008000，示意，按你的 Flash 分区规划定）。复位后硬件只会去 0x08000000 取 MSP 和复位入口，所以 APP 想跑起来，Bootloader 必须手动做三件事：关掉自己的中断与外设、把向量表指针 `SCB->VTOR` 指向 APP 的向量表、把 MSP 换成 APP 的初始栈顶并跳到 APP 的 Reset_Handler。

  1. 校验 APP 是否有效：读 APP 起始地址的头两个字，检查是否像一个合法栈顶（落在 SRAM 区间）与合法入口（落在 Flash 区间），或用 CRC 校验。不合法就留在 Bootloader，别跳进一片空白。
  2. 关闭自己开的中断与外设：先关全局中断，再把 SysTick 和用过的外设停掉。否则跳过去以后旧中断还在触发，而它们的向量已经指向 APP 的表，立刻跑飞。
  3. 重定位向量表：写 SCB->VTOR = APP_ADDR。从此所有异常/中断都从 APP 的向量表取入口。
  4. 切换栈指针并跳转：把 MSP 设为 APP 向量表的第一个字，再把 PC 跳到第二个字。这一步要用 CMSIS 的栈指针设置函数 + 函数指针调用（写法见 core_cm4.h），因为它绕过了正常的函数返回机制。
  5. APP 自己也要设一次：这样 APP 单独烧写（不经 Bootloader）时同样能跑。CubeMX 工程通常在 system_stm32f4xx.c 里用 VTOR 宏配置，改分区时记得一起改。
忘了改 VTOR 的典型症状
程序能跑到 APP 的 main()（因为跳转是手工做的），但一开中断就炸：有的中断跑到 Bootloader 的旧入口，有的直接进 HardFault，现象看起来像“外设坏了”。调试器里读一下 SCB->VTOR 是否等于 APP 起始地址，五秒钟就能排除一类大问题。

内存类问题怎么查

内存 bug 的特点是“平时正常、偶尔炸”，所以要按固定顺序排除，而不是乱改代码。

  1. 先看炸在哪条指令：HardFault 时用调试器读 SP 附近的 8 个字，对照 R0–R3 / R12 / LR / PC / xPSR 还原出错现场。硬件已经自动压栈，这 8 个字就是事故快照。
  2. 再问“栈还是堆”：PC/LR 落在 printf、memcpy、浮点库这些吃栈大户里，十有八九是栈不够或被踩；落在 malloc 里就查堆。
  3. 对着 .map 文件看实际布局：确认 .data / .bss / 栈 / 堆的真实地址与剩余空间。链接成功不代表放得下，要看余量。
  4. 动手验证假设：怀疑栈就加大 Stack_Size、把大局部数组改 static；怀疑堆就关掉 malloc 改成静态分配；改完能稳定复现/消失，才算找到根因。
一条实用习惯
每次换型号、换链接脚本、改 Flash 分区，都先打开 .map 文件看三行：Flash 用了多少、RAM 用了多少、_estack 在哪。这三个数字对上，后面 90% 的内存类玄学问题根本不会出现。

常见错误与排查

错误现象怎么查 / 怎么改
把大数组定义在函数里当局部变量函数一进就 HardFault，或调用几次后其它全局变量被改；仿真器里 SP 掉出 SRAM 区间局部变量在栈上，`Stack_Size` 默认只有 1 KB 量级（示意）。大缓冲区改 `static` 或全局，让它进 .bss。
链接脚本 LENGTH 写成比实际 SRAM 大链接不报错，上板后一用到大数组就进 HardFault，换块板子现象还不一样对照数据手册把 MEMORY 的 LENGTH 改成真实容量，并留出余量；每次改型号都重新核对一遍。

把 DMA 缓冲区放在 CCM SRAM 里DMA 传输“完成”了但数据全是 0 或旧值，没有任何报错CCM 只连 CPU 的 D‑bus，DMA 访问不到；把缓冲改到 SRAM1/SRAM2 区。

记住这三句话

  1. 01内核只有 16 个寄存器：R0–R12 干通用活，SP/LR/PC 各有专职，xPSR 里的 IPSR 是判断当前中断号的可靠依据；栈是满递减，从 SRAM 末尾往下长。
