无线协议简介Wireless Protocols

无线把“线”换成了共享的空气：选协议，本质是在速率、距离、功耗之间做取舍。

3 道小测验默认 STM32F407 / STM32G474（Cortex‑M4F）

学习目标

  • ·能说清 2.4 GHz 与 Sub‑GHz 的取舍，知道 FSK / GFSK / OFDM 只是调制方式的名字
  • ·能用速率、距离、功耗、拓扑、场景五个维度，给 BLE / Wi‑Fi / LoRa / Zigbee 做选型
  • ·能分清 BLE 的连接与广播、Zigbee / Thread 的星型与网状、LoRaWAN 的星型，并说出各自的代价
  • ·会用占空比估算平均电流与续航，不再被“峰值电流小”这种说法误导

一句话解释

无线把“线”换成了共享的空气：选协议，本质是在速率、距离、功耗之间做取舍。

生活化比喻

无线像一座没有红绿灯的公共广场

有线通信像打电话：线接给谁，就只有谁听得见。无线像在一个公共广场上说话——空气是大家的，谁都能听见，于是所有规矩都只能靠“约定”。BLE 广播是站在广场上喊一句“我这儿有个温度值”，谁路过都能听；BLE 连接是两个人先约好“每 50 ms 对一次表”，之后按点对点私聊。Zigbee 网状是人群里互相传话（远的人靠别人转达），LoRaWAN 星型是所有人都只对广场中央的大喇叭喊话。占空比就是广场的“限时发言规则”：你喊得越少，电池越耐用。

为什么重要 / 用在哪里

  • 01物联网节点大多是无线：布线成本、移动性、户外部署这三件事，基本一票否决有线方案。
  • 02选型一次定三年：协议决定功耗、成本、认证和云端接入方式，选错往往要改板、重做认证，而不是改几行代码。
  • 03无线是系统问题，不是外设问题：天线、地平面、电源去耦、协议栈、地区法规（功率与占空比上限）都要一起看，MCU 代码只是其中一环。
  • 04现场排障靠量级直觉：宣传页写“100 米”，现场只有 10 米——知道链路预算、天线匹配、信道拥挤在哪个数量级上影响结果，才知道先查什么。

无线是共享的空气介质

先建立一个正确的物理直觉：无线不“传线”，它把电压差换成了电磁波。

发射端把数据调制到一段载波上，天线把电流变成电磁波辐射出去；接收端天线把波变回微弱电压，再解调出比特。整个链路里真正决定“能传多远、多快、多费电”的，是三个物理量：频段（波长决定绕射与穿透）、带宽（决定速率上限）、发射功率（决定喊多响，但被法规卡死）。

频谱一句话：2.4 GHz 是全球通用的 ISM 频段，波长短、天线小、带宽大，代价是穿透差、设备多、非常拥挤；Sub‑GHz（几百 MHz 量级，如 433 / 470 / 868 / 915 MHz 这些频段）波长长、绕射和穿墙更好，代价是带宽小、天线大、速率低。上面的数字是频段名字，各地允许的功率与占空比由当地法规规定，具体见法规与模组手册。

调制（Modulation）Modulation
把 0/1 映射成载波的某种变化（频率、相位、幅度）。下面三种只是“变化方式”的名字，不背参数。
FSKFrequency Shift Keying
频移键控：用两个不同频率表示 0 和 1。实现简单、抗幅度干扰，Sub‑GHz 小无线里很常见。
GFSKGaussian FSK
先对数据做高斯滤波再 FSK，让频谱边沿更平滑、邻道干扰更小。BLE 的物理层就是 GFSK。
OFDMOrthogonal Frequency Division Multiplexing
把带宽切成很多相互正交的子载波并行传。Wi‑Fi 用的是 OFDM 系列，效率高但对频偏敏感、峰均比大。
扩频（CSS）Chirp Spread Spectrum
用频率随时间扫动的“啁啾”承载信息，能在噪声底下解调出来，这是 LoRa 能跑几公里的根本原因。

空气是共享介质，这一点比任何参数都重要：同一时刻同一信道上只能有一个主要发言者，所以无线协议必须解决“什么时候能说、说多久、冲突了怎么办”。有线协议里几乎不用关心的“排队”，在无线里是第一等公民。

四种协议：一张表选型

先给结论：没有“最好的无线”，只有“在你这个场景里最不难受的取舍”。

读表三句话：① 速率和距离基本互斥——同样的功率，带宽越宽越容易被噪声淹没；② 功耗看平均不看峰值，醒来几十毫秒的峰值改变不了续航；③ 拓扑决定“谁帮你转发”，也决定了网络的复杂度和故障面。

  • 要和手机直连、传小数据 → BLE。手机原生支持、开发资料多、功耗可控。
  • 要传图片/视频/固件、设备常接市电 → Wi‑Fi。速率高、和 IP 网络天然打通，代价是功耗与配网复杂度。
  • 几百米到几公里、一天只报几次、电池要撑几年 → LoRa（Sub‑GHz 扩频），速率低正是它的省电手段。
  • 家里几十个设备要自组网、互相转发 → Zigbee / Thread。网状能扩覆盖，但路由节点通常要常供电。
一颗芯片里可以有多个射频
ESP32 这类 SoC 同时支持 Wi‑Fi 与 BLE，但两个射频共享同一套 2.4 GHz 前端，是分时工作的——Wi‑Fi 在传大数据时，BLE 的连接事件会被推迟。做双模产品时，“共存”是要专门设计的，不是免费送的。

连接、广播与网络拓扑

BLE 的广播/连接回答“怎么说话”，星型/网状回答“谁来转发”。

BLE 有两种工作方式。广播（Advertising）：不建立连接，发送方按自己的节奏周期性把一小段数据“喊”出去，谁路过谁听——成本最低、功耗最低，但载荷很小、没有确认与重传保证。连接（Connection）：双方先握手，之后按约定的连接间隔（几十 ms 量级，具体范围见规范）同步醒来收发，可以双向、可以加密、可以做流控，代价是两端都要按周期醒着。

星型 vs 网状的关键区别是“转发责任在谁身上”。星型里终端只负责说话，转发全交给中心——所以终端可以睡到天荒地老，但中心一挂全网哑火。网状里每个节点都可能是路由器，覆盖能像水波一样扩出去，代价是这些节点必须经常醒着听别人说话，功耗上去了，路由表维护、环路、时延抖动也全都来了。LoRaWAN 是星型：终端把包发给网关，网关转给网络服务器，终端本身不做转发——这正是它能用一节电池撑几年的原因，也是它覆盖完全依赖网关布点的原因。

功耗与占空比决定续航

续航是“平均电流”的函数，而平均电流是“占空比”的函数。峰值电流只是分子里的一个因子。

先给结论：电池寿命 = 电池容量 ÷ 平均电流，与峰值电流没有直接关系。一个节点每 10 分钟醒一次、发射几十毫秒、其余时间睡在 µA 级，那么哪怕发射瞬间是几十 mA，被摊薄之后平均也只有 µA 量级。反过来，一个一直连着的 Wi‑Fi 设备峰值和平均值差不多，电池几天就见底。

这条式子和 低功耗与看门狗 那一页是同一套算法：那边讲 MCU 怎么睡（Sleep / Stop / Standby），这边讲为什么必须睡——无线的发射与接收是整条链路里最贵的动作，不睡就没有续航。

  • 先算平均，再谈峰值：把“醒着多久 × 多大电流”和“睡着多久 × 多大电流”分别算出来相加，其他都是细节。
  • 电池寿命的实际上限常常不是 MCU：LDO/DC‑DC 的静态电流、传感器的待机电流、上拉电阻漏电、电池自放电，任何一项都可能比 MCU 的睡眠电流还大。
  • 占空比不只是省电手段，还是法规要求：部分 Sub‑GHz 频段对单设备占空比有上限，超了就是不合规，具体比例见当地法规与 LoRaWAN 区域参数。
  • “连得上”和“省电”是同一件事的两面：连接间隔、广播间隔越长越省电，但响应也越慢，最终要和产品体验一起定。
别用峰值电流估续航
“发射电流只有 40 mA，应该很省电”是最常见的误判。真正要问的是：它一天醒几次、每次醒多久、睡着时漏多少。这三个数才是续航公式的输入。

天线、匹配与共存

射频前端做不好，协议选得再对也白搭；2.4 GHz 还要额外面对“大家都在这儿说话”。

天线不是“接根线”。射频走线要按 50 Ω 阻抗设计，中间通常有 π 型或 LC 匹配网络 把模组输出调到天线最舒服的状态；天线周围要留净空区（不放铜、不放电池、不放金属外壳），地平面要完整。匹配没做好，功率会反射回功放，链路预算凭空损失几个 dB——dB 是对数，掉 3 dB 就是功率少一半，掉 6 dB 就是四分之一。

  • 天线位置：优先放板边或伸出外壳，远离电池、屏幕排线、金属结构件；人手遮挡也会让实测距离打对折。
  • 匹配元件照抄参考设计：模组厂商给的匹配网络与布局是调过的，自己“优化”之前先保证能量出来。
  • 用数据验证：拿 RSSI、丢包率、实际通信距离做对比实验，而不是“看起来能通就算过”。

2.4 GHz 拥挤共存一句话：BLE、Wi‑Fi、Zigbee、无线键鼠、微波炉都在 2.4 GHz 上抢时间，信道重叠加上各单位自己的占空比，表现出来就是重传变多、时延抖动、吞吐忽高忽低。缓解手段是跳频（BLE / Zigbee 本来就在跳）、信道规划（把网关的 Wi‑Fi 主信道挪开）、降低占空比，实在不行就换到 Sub‑GHz。

认证是另一条独立战线
射频产品要上市，还得过地区认证（如 CE / FCC / SRRC），涉及发射功率、杂散、占空比等一堆硬指标。用已认证的模组能大幅降低这部分工作量——这也是很多产品选择“MCU + 模组”而不是自画射频的根本原因。

接到 STM32 的三种路径

STM32 本身没有 2.4 GHz / Sub‑GHz 射频，所以“怎么联网”是一个架构选择，而不是一个外设配置。

三种常见路径：① UART/SPI + 无线模组（最常见，模组自带协议栈与认证）；② 换用自带射频的 SoC（如 ESP32，协议栈在片内，代码只做配置）；③ 直接用模组的 AT 指令（最快出原型，主机侧只做字符串收发）。三者的分界线不是“谁高级”，而是谁负责协议栈、TCP/IP 与认证。

  1. 定协议与指标：先写清距离、数据量、上报频率、电池寿命目标，再反推速率与占空比，最后才选协议。
  2. 按参考设计做硬件：模组供电、去耦、天线净空、匹配网络全部照抄厂商参考设计，别在第一版自作聪明。
  3. 打通最小链路：先用最简单的方式（AT 握手或示例工程）证明“能连上、能发出去”，再谈业务逻辑。
  4. 加状态机与重连：无线断连是常态。要有超时、重试、退避、看门狗——这段代码比“发送成功”那几行重要得多。
  5. 实测功耗与距离：用电流表测平均电流，用 RSSI/丢包率测链路，最后才敢写“电池能用几年”。

常见错误与排查

错误现象怎么查 / 怎么改
天线没做匹配，也没留净空实验室能通，装进外壳或贴到电池上之后距离骤降到几米；发射瞬间电流飙升甚至复位射频走线按 50 Ω 设计，匹配网络照抄模组参考设计，天线下方与周围留净空、地平面完整；用 RSSI 与实际距离对比验证，别用“能通”当验收标准。
广播间隔设得太长，扫不到也连不上手机端扫描半天才出现设备，或者刚点连接就超时；批量生产时“有的能用有的不能用”广播间隔和连接间隔都要在“被发现的概率”与“平均功耗”之间折中；排查时先把间隔调短验证链路，再逐步拉长测功耗，并确认设备确实在发**可连接**广播。
信道被 2.4 GHz 设备挤满实验室很稳，现场丢包和重传变多、时延忽高忽低；Wi‑Fi 一跑大流量，BLE 就掉线把网关/AP 的主信道与 BLE 广播信道错开，减少同时在线的高占空比设备；用抓包工具看重传率而不是只看“连没连上”，必要时改用 Sub‑GHz。
配网/认证失败，误判成硬件坏连不上 AP、反复重连、或者认证阶段就断开；换个路由器又能用逐项核对：SSID 是否隐藏、AP 是否只开 5 GHz、加密方式与是否要求 PMF、密码里有特殊字符、DHCP 是否分到地址；打开模组/协议栈的日志看它停在哪一步。
拿宣传页的“标称距离”当设计指标规格写 100 米，现场 10 米就掉线；换一批货表现还不一样按最差环境做链路预算并留余量（墙体、人体遮挡、天线朝向都算损耗），用实测 RSSI/丢包率定验收标准，把“距离”换成“在什么环境下、什么丢包率”。
