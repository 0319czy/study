USBUniversal Serial Bus

USB 是主机说了算的差分串行总线：主机发现设备、分配地址、调度每一次传输，设备只在被问到时应答。

3 道小测验默认 STM32F407 / STM32G474（Cortex‑M4F）

学习目标

  • ·能说清 USB 的主机/设备非对等模型：谁发现设备、谁分配地址、谁调度传输
  • ·能解释 D+/D− 差分与设备端上拉的作用，并知道 12 Mbit/s 是线速率而不是有效吞吐
  • ·能区分控制/中断/批量/同步四种传输“各保证什么”，并说出 EP0 在枚举中的角色
  • ·能按枚举六步讲出“插上 U 盘或虚拟串口后发生了什么”，并用 HAL + 中间件发出第一包 CDC 数据

一句话解释

USB 是主机说了算的差分串行总线：主机发现设备、分配地址、调度每一次传输，设备只在被问到时应答。

生活化比喻

USB 像一家只由经理派活的邮局

所有活都由经理（主机）派：他先看谁来了（检测上拉）、登记身份证（读描述符）、发工号（分配地址）、安排座位（选择配置），之后每一单都是他点名才办。员工（设备）不能自己跑去揽业务，只能在自己的信箱（端点）里等着叫号。想寄东西？经理说“取件”，员工才能把包裹递上去——这就是 IN；经理说“送件”，员工才能收下——这就是 OUT。方向和主动权，都握在经理手里。

为什么重要 / 用在哪里

  • 01“插上没反应”几乎都在最底层：供电、上拉、48 MHz 时钟、D+/D− 接反，任何一处不对，系统连枚举都进不去，应用代码写得再好也没用。
  • 02虚拟串口是嵌入式最常用的日志与命令通道：一根 USB 线同时供电和通信，CDC 类免去 USB‑TTL 芯片，理解枚举才能自己排查“为什么没有 COM 口”。
  • 03USB 是“描述符 + 主机软件”共同定义的系统：同一颗芯片可以做串口、键盘、U 盘、声卡，靠的就是描述符里的类与接口——不懂这层只会在驱动上瞎试。
  • 04HID / MSC / Audio 都在同一套机制上：学会端点、传输类型、枚举，再看任何一个标准类都是“换一份描述符 + 换一套请求”，迁移成本很低。

主机与设备：不是对等总线

先纠正一个最常见的误解：USB 不是“两根线的串口”，它是一个由主机绝对主导的总线。

USB（Universal Serial Bus，通用串行总线） 最容易被误解成“差分版的串口”。它其实是一套主机（Host）说了算的总线：主机负责发现设备、分配地址、安排每一次传输的时间片，还负责供电；设备只能“等叫号”，从不主动发起通信。所以你写的 STM32 USB 代码本质上是在扮演一个应答者——介绍自己、接收命令、在主机允许时把数据交上去。

  • 枚举与地址：新设备插上后，由主机读描述符、分配唯一地址（1～127 量级）并选择一个配置；设备自己不能挑地址。
  • 调度与带宽：每个 1 ms 帧（全速）里发哪些包、给谁多少带宽，全部由主机安排；设备没有“抢总线”的能力，这和 CAN 的仲裁完全不同。
  • 供电：VBUS 的 5 V 由主机提供，设备在枚举完成前只能取很少的电流（100 mA 量级，配置后最多 500 mA 量级，以规范与主机能力为准）。
  • 一个端口一个设备：主机端口后面要么是一台设备，要么是一台 Hub；想接多台就靠 Hub 扩展，而不是像 RS485 那样把多台挂到同一对线上。
第 1 层

电气 / 物理层

先问：线怎么接、电平怎么变？

  • ·四根线：VBUS、D+、D−、GND，其中 D+/D− 是一对差分信号
  • ·设备端 1.5 kΩ 量级的上拉（示意值）告诉主机“我接上了”
  • ·全速线速率 12 Mbit/s 量级，高速 480 Mbit/s 量级
第 2 层

包与事务层

先问：一次传输由哪些包组成？

  • ·令牌包说明“找谁、什么方向”，数据包搬数据，握手包回 ACK/NAK
  • ·一个“事务”是最小传输单位，硬件自动重试失败的握手
  • ·主机把事务排进帧/微帧的时间表，设备按表应答
第 3 层

设备与描述符层

先问：主机怎么认识这台设备？

  • ·端点（Endpoint）是设备侧的收发信箱，EP0 固定用于控制传输
  • ·描述符自描述：设备、配置、接口、端点、字符串
  • ·枚举就是“读描述符 → 分配地址 → 选择配置”的过程
第 4 层

设备类与应用层

先问：这些字节代表什么？

  • ·类（Class）约定接口语义：CDC 是串口、HID 是键鼠、MSC 是存储、Audio 是声卡
  • ·主机按类加载标准驱动，应用层再读写串口/文件/音频
  • ·同一套底层机制，靠“类 + 接口”区分用途

电气上，D+ 与 D− 是一对差分信号：接收端看两根线的电压差，共模干扰在相减时被抵消。设备端在 D+ 上加一个 1.5 kΩ 量级的上拉（示意），主机检测到 D+ 被拉高就知道“有设备接入”，随后发起复位与枚举——所以“上拉没生效”在主机眼里就是“什么都没插”。低速设备把上拉接在 D− 上，主机由此区分低速与全速。

差分不等于“能拉很长”
USB 用差分是为了抗共模干扰、降低 EMI，但线缆长度与拓扑仍然受限（通常几米量级，以规范与线材为准）。想长距离、多节点，那是 RS485 / CAN 的地盘，不是 USB 的强项：USB 是“短距离、高速率、带供电、可热插拔”的组合拳。

端点与 EP0：设备侧的信箱

主机跟设备说话，从来不是说“设备你好”，而是说“某个端点的某个方向”。

端点（Endpoint）是设备内部一个可被寻址的“收发信箱”：有编号、有方向、有最大包长。主机发来的每个包都写明“去哪个端点的哪个方向”，设备按这个地址把数据放进或取出对应的缓冲区。设备用描述符把端点声明出来，主机照着建一条管道（Pipe）——所以端点属于设备，管道是主机侧对“一条已配置通道”的叫法。

端点Endpoint
设备侧可被寻址的收发单元，由端点号 + 方向 + 传输类型 + 最大包长共同定义。
EP0Endpoint 0
每台设备都必须有的控制端点，负责枚举时的标准请求与之后的类请求；它是唯一双向的端点。
管道Pipe
主机侧对一条已配置端点通道的抽象，包含方向、传输类型与调度参数。
端点地址Endpoint Address
端点号与方向的组合；HAL/中间件里用一个字节表示，方向位区分 IN 与 OUT。

IN / OUT 都以主机为视角：IN 是“设备 → 主机”（主机把数据“读进来”），OUT 是“主机 → 设备”（主机把数据“写出去”）。这条约定很反直觉，但它是排查“方向搞反”这类问题的钥匙：设备侧看到 IN 端点，意思是这条通道专门负责往主机发数据。

每个端点的方向是固定的（EP0 是唯一的例外）：一个端点要么只发、要么只收，不能一会儿当 IN 一会儿当 OUT。描述符里声明的方向必须与代码里使用的方向一致，否则主机会按描述符去“取”，设备却在另一条通道上“推”，现象就是枚举过了却一个字节也传不动。

EP0 是设备的门面：上电后主机只能用“地址 0 + EP0”跟设备对话，枚举的全部标准请求（读描述符、设地址、选配置）都走 EP0。控制传输一次只能搬很小的包（几十字节量级，具体以描述符声明为准），所以大块数据永远走批量/中断/同步端点——EP0 只负责“谈配置”，不负责搬正事。

三个容易混的概念
端点 ≠ 引脚：端点是协议层概念，引脚是电气层。端点 ≠ 缓冲区：端点是可寻址单元，FIFO/缓冲区是它背后的存储。EP0 ≠ 唯一端点：EP0 管控制，数据必须另开端点。
端点是有限资源
芯片支持的端点数由硬件决定（见数据手册），不是想要多少就有多少。功能多的时候，要么把功能拆成不同接口做成复合设备，要么让多个功能复用同一对批量端点——别指望每个功能都独占一对 IN/OUT。

四种传输类型：四档服务质量

控制、中断、批量、同步，区别不在“快慢”，而在“保证什么”。

USB 把传输分成四种类型，本质是四档服务质量（QoS）：有的保证“一定送到”，有的保证“一定按时到”，有的只保证“每帧给你留了位置”。选错类型，问题不在驱动写得对不对，而在需求一开始就没对上。

选择的直觉：“一个字节都不能少” → 批量或控制；“晚到就没用，但偶尔丢一帧能忍” → 同步；“数据小、要尽快、还要可靠” → 中断。批量的“可靠”也有前提——主机得一直在调度它；设备被拔掉或主机过载，重试救不回来。

“中断传输”不是 MCU 的中断
名字里的“中断”指它按固定节奏打断主机的空闲去轮询你，跟 Cortex‑M 的 NVIC 中断没有关系。STM32 侧收包当然也会进 USB 外设中断，但那只是“硬件收到一个包”，与传输类型是两码事。
同步传输不背锅
音频设备用同步传输，是因为要“每帧一包、不能忽快忽慢”；代价是丢包不重传。所以做 USB 音频时，抖动与丢包要在应用层用缓冲、重采样去吸收，而不是指望 USB 帮你补。

枚举：主机怎么认识设备

从“总线上多了个东西”到“我知道它是什么”，中间只有六步，而且全部由主机驱动。

枚举（Enumeration）是主机“认识”设备的过程。整个过程由主机发起、设备配合应答；设备侧唯一能主动做对的，就是把描述书写对、把端点按描述符打开。

  1. 接入与复位：设备端上拉生效，主机检测到连接后发起总线复位；设备回到默认状态，此时只能用地址 0 通信。
  2. 先读设备描述符的前几个字节：主机只读开头一小段，目的是拿到 EP0 的最大包长——不然之后的大段描述符没法安全传输。
  3. 分配地址：主机发 SET_ADDRESS，设备此后改用新地址；地址 0 留给下一个还没分配地址的设备。
  4. 读完整描述符：用新地址读完整设备描述符，再读配置描述符——配置描述符里嵌套着接口与端点描述符，主机的“能力清单”就来自这里。
  5. 读字符串与类请求（可选）：厂商名、产品名、序列号来自字符串描述符；有些类还要额外的类描述符或请求（例如 HID 的报告描述符）。
  6. 选择配置：主机发 SET_CONFIGURATION 选定一个配置，设备进入已配置状态，各接口对应的类驱动开始工作——到这一步，虚拟串口才会出现在 PC 上，U 盘才会被挂载。
默认状态 Default
刚复位，只能响应地址 0 的标准请求
地址状态 Address
已分配地址，但还没选配置，不能做类数据传输
配置状态 Configured
配置已选定，端点可用，类驱动开始收发
挂起 Suspended
总线空闲，设备应尽量省电，等待唤醒
描述符是“自描述 + 长度字段”
主机不是按固定偏移硬读，而是靠每个描述符的 bLength / bDescriptorType 一路跳下去，配置块再用 wTotalLength 判断总长。任何一处长度写错，后面全部错位——这就是“枚举到一半失败”最常见的原因。
枚举失败请分层查
电气（上拉、供电、VBUS 检测、48 MHz 时钟）→ 描述符（长度、端点数量、类字段）→ 类请求（HID 报告描述符、CDC 设置波特率）→ 主机驱动（INF 与类驱动匹配）。从上往下查，比盯着应用代码快得多。

常见设备类：四种“标准用法”

同一套 USB 底层，靠“类”告诉主机该怎么用它——选类几乎等于选“要不要自己写 PC 驱动”。

设备类（Device Class） 是“这类设备该怎么用”的标准约定：键盘、U 盘、声卡、串口在协议层都只是端点加请求，靠类代码区分。主机读到类代码，就加载对应的标准驱动——这也是“免驱”的来源。

复合设备（Composite Device）：一个物理设备、一个 USB 地址，里面用多个接口分别实现不同的类——比如“键盘 + 鼠标”共用一个插头，或者“CDC 串口 + MSC 存储”二合一。主机为每个接口加载各自的驱动；接口一多，接口关联描述符（IAD）和描述符总长就成了最容易写错的地方。

“免驱”不是没有驱动，而是系统自带标准类驱动：HID / MSC / Audio 由操作系统内置，插上就能用；CDC 在 Windows 上还要看系统版本与 INF 匹配，Linux 上通常直接出现 /dev/ttyACM0 之类的节点。自定义类（厂商自定义）没有现成驱动，必须自己写或提供 INF——所以“能用标准类就别自定义”是条实打实的经验。

代码：用 CDC 发出第一包

目标是把 STM32 做成虚拟串口，把一行文本发给 PC——不手写描述符，全部用 CubeMX 生成的框架。

下面按“从零到能发”的顺序走一遍。真正容易踩的不是发送函数，而是时钟（没有 48 MHz 一切免谈）、接收要重新挂、以及发送是异步的这三件事。

  1. CubeMX 选设备模式：USB_OTG_FS 选 Device（G474 直接选 USB 外设），Middleware 里勾 CDC；D+/D− 是固定复用引脚，不能像普通 GPIO 那样随便挪。
  2. 确认时钟：全速 USB 需要 48 MHz 时钟（F407 由 PLL 的 Q 分频提供，具体见时钟树），时钟没配对，USB 内核根本不工作——这是“插上没反应”的头号原因。
  3. 初始化：生成的 MX_USB_DEVICE_Init() 会初始化 PCD、注册 CDC 类并启动设备栈；主循环里不要重复调用它。
  4. 接收：PC 发来的数据进 CDC_Receive_FS() 回调；处理完必须把接收重新挂上（中间件的 USBD_CDC_ReceivePacket，CubeMX 生成的 CDC_Receive_FS 末尾已经帮你调了），否则只收到第一包。
  5. 发送：在主循环里调 CDC_Transmit_FS()；返回 USBD_BUSY 说明上一包还没发完，要等完成回调再发，不能原地死等。
同一个“发一包”的三种视角

自下而上：HAL 的 PCD 驱动负责端点与单次收发，中间件负责协议与类语义，寄存器层则是这些动作最终落到硬件的样子。

发送是异步的，缓冲要“活到发完”
CDC_Transmit_FS 只是把指针交给中间件，并没有复制数据。函数返回后立刻改写缓冲，发出去的可能就是半截新数据。稳妥做法是双缓冲，或“完成回调里再发下一包”。
上板验收顺序
先看设备管理器 / dmesg 有没有出现新设备 → 再看有没有 COM 口或 /dev/ttyACM* 节点 → 最后才看应用层收发。节点都没有，去查枚举与驱动；节点有但收不到，去查端点方向与类请求。

常见错误与排查

错误现象怎么查 / 怎么改
枚举失败：插上后主机毫无反应，或显示“未知 USB 设备”设备管理器出现未知设备/黄色感叹号，Linux 下 `dmesg` 连“检测到连接”都没有，程序却跑得好好的按层查电气：先确认 VBUS 检测是否生效（自供电板常需要接 VBUS 或改配置）、48 MHz 时钟是否真的就绪、D+/D− 有没有接反、设备端上拉是否生效。连“连接”都检测不到，先别怀疑描述符。
描述符长度或数量写错枚举到读配置描述符时失败，或只识别部分接口；Windows 报“设备描述符请求失败”，Linux 下 `lsusb -v` 读出来的字段明显错位逐项核对 `bLength` / `bDescriptorType` / `wTotalLength`、接口里 `bNumEndpoints` 与实际端点描述符数量是否一致；用 USBView、`lsusb -v`、`dmesg` 看主机到底读到了什么，和工程里的数组逐字节对比。
端点方向搞反（把 IN 当 OUT 用）枚举正常、设备也认出来了，但数据一个字节都传不动；发送函数一直返回忙或直接报错，接收回调从不触发记住 IN/OUT 是主机视角：发送用 IN 端点、接收用 OUT 端点；端点方向由描述符里的端点地址决定，代码里必须用同一套宏。对照描述符与 `HAL_PCD_EP_Open` 的调用参数，别自己写端点号。
驱动/类请求没对上（Windows 上没有 COM 口）设备管理器里能看到设备但没有 COM 口，或显示为其他类别；换到 Linux 却直接出现 `/dev/ttyACM0`优先用标准 CDC‑ACM，Windows 新版通常能自动匹配 usbser.sys；自定义类或多接口复合设备要提供 INF 并检查 IAD 与接口类字段。先用另一套系统交叉验证，能快速区分“设备问题”还是“主机驱动问题”。
忽略发送忙状态，缓冲区被覆盖日志偶发截断、错行或整段丢失；发送频率越高越明显，降低频率就“自愈”检查 `CDC_Transmit_FS` 的返回值，`USBD_BUSY` 时不要强发；把待发数据放进队列，在发送完成回调里再发下一包，并保证缓冲区在发完前不被改写。

一块自制的 STM32 板子插到 PC 上，设备管理器显示“未知 USB 设备”，程序本身运行正常。下列哪些排查动作是对的？（多选）

第 3 题判断进阶

判断：USB 的同步（Isochronous）传输既有固定的带宽保证，又会在出错时自动重传，所以适合传输文件。

记住这三句话

  1. 01USB 是主机/设备模型，不是对等总线：主机枚举、分配地址、调度传输，设备只在被问到时应答；IN/OUT 都以主机视角定义。
  2. 02四种传输是四档服务质量：控制管枚举与请求、中断保证时延、批量保证送达、同步保证带宽——选错类型，代码再对也不满足需求。
  3. 03跑不通先分层：电气与 48 MHz 时钟 → 描述符长度与端点数量 → 端点方向与类请求 → 主机驱动；描述符和方向是最高频的两个坑。
