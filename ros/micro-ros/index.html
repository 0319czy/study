micro-ROS

micro-ROS · ROS 2 on Microcontrollers

一句话解释一句话解释：micro-ROS 把 ROS 2 的通信能力装进单片机——让只有几十 KB 内存的 MCU 也能直接跟 ROS 2 网络对话，不用再写一堆自定义串口协议。

学习目标

学完这页你应该能做到

  • ✓能说清 micro-ROS 的 client / agent / DDS 三层架构
  • ✓能列举适合与不适合用 micro-ROS 的场景
  • ✓能说出资源受限下的四条设计原则（消息小、频率低、静态分配、少回调组）
  • ✓能描述一次「MCU 发布消息到 ROS 2 网络」的完整链路
  • ✓知道它与 ROS 1 时代 rosserial 的对应关系

🧩生活化比喻 · 给只会说方言的小工配翻译

MCU 就像只会说方言的小工：它不懂 DDS，内存也装不下整套 ROS 2。micro-ROS 给小工配了一个翻译（agent）——小工用简化协议（XRCE-DDS）跟翻译说话，翻译再替它接入整个 ROS 2 工地广播。

  • MCU 端 = 小工（跑 micro-ROS client 库）
  • Agent = 翻译（跑在 Linux 主机或树莓派上）
  • DDS = 工地广播系统（其他 ROS 2 节点）

🎯为什么重要 / 用在哪里

机器人上大量实时任务在 MCU 上：电机控制、编码器读取、IMU 采样、舵机驱动。过去要靠自定义串口协议对接，现在 micro-ROS 让它们直接成为 ROS 2 节点。

  • 电机驱动板直接发布 /wheel/odom、订阅 /cmd_vel
  • 分布式传感器：多个 MCU 各管一处，统一进 ROS 2 网络
  • 实时性：MCU 保证控制环周期，Linux 端只做上层逻辑
  • 降低胶水代码：不用再维护二进制串口协议

#三层架构：谁在替谁说话

micro-ROS 的三层
层运行位置职责
client（rclc / rcl）MCU 上创建节点、发布订阅、定时器；把数据序列化成 XRCE-DDS
agentLinux 主机 / 树莓派接收串口或 UDP 上的 XRCE-DDS，翻译成标准 DDS，接入 ROS 2 图
DDS 网络主机与局域网正常的 ROS 2 通信，其他节点完全感知不到 MCU 的存在
关键点：MCU 上不跑 DDS，也不跑完整 rclcpp。所以「MCU 上的节点」在 ros2 node list 里能看到，但它的能力是裁剪过的。

#什么时候该用，什么时候不该用

适用性判断
场景建议原因
电机闭环、编码器读取适合实时性强，数据量小，天然属于 MCU
IMU 采样 100~1000Hz适合（注意频率与消息大小）需要硬实时，但对带宽要求不高
图像/点云传输不适合带宽与内存都不够，应交给 Linux 端
复杂规划算法不适合算力与内存不够
简单状态上报、指令下发非常适合替代自定义串口协议的最佳场景

#资源受限的四条设计原则

MCU 通常只有几十到几百 KB RAM。micro-ROS 能用，但必须按嵌入式的思路设计，而不是照搬 PC 上的写法。

  • 消息要小：能用 uint8 数组就别用大结构体，避免频繁发大消息
  • 频率要合理：传感器 50Hz 足够就别发 500Hz，带宽和 CPU 都是成本
  • 静态分配：尽量不用动态内存，缓冲区大小编译期确定
  • 回调要短：回调里不要阻塞、不要长循环，否则整个 executor 卡住
如果通信频繁失败，先看 agent 端日志与串口波特率。波特率太低（例如 115200）会成为瓶颈，常见做法是提高到 921600 或改用 UDP。

#最小示例：MCU 上的发布者

$ ros2 run micro_ros_agent micro_ros_agent serial --dev /dev/ttyACM0
  • serial使用串口传输；也可以选 udp4 走网络
  • --dev /dev/ttyACM0MCU 挂载的串口设备；插拔后编号可能变化，建议用 udev 固定
$ ros2 run micro_ros_agent micro_ros_agent udp4 --port 8888
  • udp4通过 UDP 连接，适合无线或高带宽场景
  • --port 8888监听端口，MCU 端要配置成同一地址与端口
固件构建流程在不同版本之间变化较大（micro_ros_setup、colcon 或 PlatformIO 集成等方式都有），请以 micro-ROS 官方文档与所用开发板的教程为准，不要混用不同版本的命令。

结论提示

micro-ROS 让 MCU 成为「一等公民」节点：对上，它和其他 ROS 2 节点没有区别；对下，它受限于内存、带宽与实时性，所以消息要小、频率要稳、回调要短。

学习示意：真实 DDS 还会做可靠传输、序列化与网络优化；这里只画逻辑关系。

排障

常见错误与排查

先看现象，再想原因，最后按步骤验证

  • 🚨现象：MCU 端程序跑起来了，但 ros2 node list 里没有它

    原因：agent 没启动、串口权限不足，或两端的传输配置不一致。

    1. 确认 agent 已启动且没有报错
    2. 把用户加入 dialout 组或设置正确的设备权限
    3. 检查波特率、端口号、UDP 地址是否与固件一致

  • 🚨现象：通信一段时间后卡死或重启

    原因：内存碎片或缓冲区溢出，常见于动态分配与超大消息。

    1. 改用静态分配，编译期确定缓冲区大小
    2. 缩小消息体，降低发布频率
    3. 检查栈大小，回调里避免大数组局部变量

  • 🚨现象：延迟很大或丢消息

    原因：串口波特率太低，或 MCU 回调里做了阻塞操作。

    1. 提高波特率或改用 UDP
    2. 把长任务移出回调（用状态机分片处理）
    3. 降低消息频率，只发必要字段

  • 🚨现象：烧录后完全没反应、串口无输出

    原因：固件与开发板不匹配，或时钟/串口初始化配置错误。

    1. 确认固件是给这块板子编译的
    2. 先用一个最小点灯/串口打印程序验证工具链
    3. 检查时钟树与外设初始化是否与板级支持包一致

收尾

记住这三句话

  1. 01

    MCU 端跑 client，主机端跑 agent，中间走 XRCE-DDS。

  2. 02

    消息要小、频率要稳、回调要短、内存要静态。

  3. 03

    它替代的是自定义串口协议，不是替代 Linux 端的大算力节点。
