TF2 坐标变换

TF2 · Transform Tree / Broadcast / Lookup

一句话解释一句话解释：TF2 是 ROS 的坐标系翻译官——任意两个坐标系之间的位置和朝向关系，它都能在正确的时间点上算出来，让激光、地图、机器人本体说的是同一种语言。

学习目标

学完这页你应该能做到

  • ✓能说清 map / odom / base_link / laser 四层坐标系的含义与关系
  • ✓能画出并检查一棵 TF 树，知道为什么不允许多个父节点
  • ✓会用 static_transform_publisher 与代码广播静态/动态变换
  • ✓会用 tf2_echo、view_frames 排查 TF 问题
  • ✓能解释「TF 查询要用数据时间戳而不是当前时间」的原因

🧩生活化比喻 · 楼层平面图上的「我在哪」

想象一栋大楼：地图告诉你楼在园区里的位置，楼层号告诉你在这栋楼的第几层，房间号告诉你在这个楼层的哪一间。要从园区坐标算出「相机镜头在园区里的位置」，就要一层层换算：园区 → 大楼 → 楼层 → 房间 → 相机。TF2 就是自动做这套换算的计算器。

  • 每个坐标系（frame）是一个「位置参照物」
  • 相邻两级的关系叫一条变换（transform）
  • 一条链路的乘积，就是两个坐标系之间的换算

🎯为什么重要 / 用在哪里

机器人身上有几十个坐标系：底盘、激光、相机、机械臂末端、世界地图。任何「把传感器数据变成动作」的过程都要做坐标换算，TF 断了，整个系统就瞎了。

  • 导航：激光点要变到 map 才能建图，目标点要变到 base_link 才能执行
  • 机械臂：末端位姿要换算到基座坐标系才能做逆运动学
  • 可视化：RViz2 的 Fixed Frame 全靠 TF 支撑
  • 排障：TF 报错是 ROS 里最高频的错误之一

核心概念

中英对照 + 一句话解释

坐标系Frame
一个有名字的参考原点与朝向，例如 base_link、laser_link、map。
变换Transform
两个坐标系之间的平移 + 旋转，数学上是 4×4 齐次矩阵。
TF 树TF Tree
所有坐标系的父子关系构成的一棵有向树，任何两个坐标系之间必须有一条通路。
静态广播static_transform_publisher
不随时间变化的变换，例如底盘到激光的安装位置，发到 /tf_static。
动态广播TransformBroadcaster
随时间变化的变换，例如 odom 到 base_link，按控制频率持续发布。
四元数Quaternion
表示旋转的四元数 (x, y, z, w)，ROS 消息里统一用它而不是欧拉角。

#四个必须先认识的坐标系

ROS 导航栈有一套约定俗成的坐标系名字。不理解它们的分工，就无法理解「为什么我的激光在 RViz 里是歪的」。

常见坐标系分工
坐标系含义由谁发布
map全局地图坐标系，长期稳定，不随机器人漂移定位节点（amcl、slam_toolbox）
odom里程计坐标系，连续平滑但有累积漂移轮式里程计或视觉里程计
base_link机器人本体坐标系，原点一般在底盘中心机器人的本体描述（URDF 中的 base）
laser_link / camera_link传感器安装位置静态变换（安装尺寸固定）
map 与 odom 之间是定位节点不断修正的关系：odom 会漂，map 不会，所以定位节点发布 map→odom 来「拉回」漂移。这条边丢了，导航就无法把目标点放到正确位置。

#TF 树的硬规则：一个孩子只能有一个爸爸

TF 树是有向树而不是图：每个坐标系只能有一个父节点，但可以有多个子节点。如果两个节点同时发布同一个 child 的变换，就会被判定为冲突。

  • 所有坐标系必须连成一棵树，不能出现两棵互不相连的树（断链即无法查询）
  • 同一条边不能有多个广播者——多机器人或多进程重复广播是常见事故
  • 坐标系名区分大小写，斜杠开头的绝对名容易踩坑，建议统一不加前导斜杠
  • 树太深会让查询变贵，但一般几十个坐标系完全无压力

#静态广播：安装尺寸不会变

激光雷达焊在底盘上，位置永远不会变，这类变换用静态广播一次性发布，之后所有节点都能查到，不用反复计算。

$ ros2 run tf2_ros static_transform_publisher --x 0.15 --y 0 --z 0.2 --yaw 0 --pitch 0 --roll 0 --frame-id base_link --child-frame-id laser_link
  • --x --y --z子坐标系原点在父坐标系中的平移（米）
  • --roll --pitch --yaw欧拉角（弧度）；新版参数顺序可用 --frame-id 与 --child-frame-id 明确指定
  • --frame-id父坐标系（挂在谁身上）
  • --child-frame-id子坐标系（被挂上去的那个）
不同版本的 static_transform_publisher 参数写法有差异：老写法用位置参数（x y z yaw pitch roll frame_id child_frame_id），Humble 里推荐用带 -- 的具名参数。以 ros2 run tf2_ros static_transform_publisher --help 的输出为准。

#动态广播与查询：时间戳是关键

odom 到 base_link 的变换随机器人移动而变化，需要按频率持续广播。查询时最重要的参数是「查询哪个时刻」，而不是「现在」。

#三个排查命令

$ ros2 run tf2_ros tf2_echo map base_link
  • map源坐标系（target）
  • base_link目标坐标系（source）；输出会持续打印两帧之间的变换
$ ros2 run tf2_tools view_frames
  • 无参数抓取当前 TF 树并生成 frames.pdf，一眼看出是否断链、是否有重复父节点
$ ros2 run tf2_ros tf2_monitor
  • 无参数统计每条边的发布频率与延迟，找出「谁发得太慢」
如果 tf2_echo 报错说两个坐标系之间没有连接，先用 view_frames 看树——8 成的问题都是某一段边没有发布者。

结论提示

TF 查询就是「沿树做矩阵乘法」。链路断一环，查询立刻失败；查询时刻选错，值就是错的。所以 TF 排障永远先看树是否连通、再看时间戳是否对齐。

学习示意：真实变换是 4×4 齐次矩阵，这里用连线与文字表达「沿树相乘」。

排障

常见错误与排查

先看现象，再想原因，最后按步骤验证

  • 🚨现象：tf2_echo 报错说两个 frame 之间没有连接

    原因：TF 树断链：中间某个变换没有发布者，或两台机器不在同一 ROS_DOMAIN_ID。

    1. view_frames 生成 PDF，看树到底断在哪一段
    2. 确认该段的广播者节点在运行（ros2 node list 找它）
    3. 检查两端的 ROS_DOMAIN_ID 与网络是否一致

  • 🚨现象：回放 bag 时 TF 查询超时报 Lookup would require extrapolation

    原因：查询用了当前时间或超前的未来时间，而 TF 数据只到过去某个时刻。

    1. 查询用数据自带的时间戳，而不是 Time()
    2. 回放时加 --clock，并让节点 use_sim_time 为 true
    3. 适当放宽 lookup 的 timeout，但不要无限等

  • 🚨现象：同一个 child 有两份变换，RViz 里抖成两个位置

    原因：两个节点同时广播同一对父子关系（例如两个 ekf 节点都在发 odom→base_link）。

    1. view_frames 或 tf2_monitor 找出重复的广播者
    2. 只保留一个，其余停掉或改名
    3. 检查 launch 是否重复启动了同一节点

  • 🚨现象：RViz 里机器人模型和激光对不上，差一个固定角度

    原因：静态变换的欧拉角单位或顺序写错（弧度 vs 角度、yaw/pitch/roll 顺序）。

    1. 确认参数单位是弧度（90° = 1.5708）
    2. 用 rviz 的 TF 显示确认坐标轴方向
    3. 用 tf2_echo 对比实际值与设计图纸
