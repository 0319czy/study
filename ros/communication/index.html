通信机制

Communication · Topic / Service / Action / Parameter / QoS / DDS

一句话解释一句话解释：ROS 用四种方式让程序互相说话——话题像广播、服务像打电话、动作像带进度的长任务、参数像贴墙上的配置表；QoS 决定「话要不要一定送到」。

学习目标

学完这页你应该能做到

  • ✓能按场景选对通信方式：什么时候用话题、服务、动作、参数
  • ✓能用 ros2 topic / service / action / param 系列命令观察与测试数据流
  • ✓能写出最小的 rclpy 发布者、订阅者、服务客户端
  • ✓能解释 reliability / durability / depth 的含义，并知道传感器数据为什么用 best_effort
  • ✓能说出 ROS 2 用 DDS 发现机制替代 mc/roscore 的原因

🧩生活化比喻 · 广播、电话、外卖、公告栏

话题是广播电台：谁想听就调频，主播不需要知道有几个听众。服务是打电话：拨通后等对方回答，没接通就只能干等。动作是点外卖：下单（goal）后能看到骑手位置（feedback），最后收到餐（result），中途还能取消。参数是公告栏：写在上面的数字，运行时可以改。

  • 广播（话题）适合持续的数据流：激光、图像、速度指令
  • 电话（服务）适合「问一句答一句」：查询模式、开关灯
  • 外卖（动作）适合耗时任务：导航到目标点、机械臂抓取
  • 公告栏（参数）适合配置：最大速度、话题名、控制频率

🎯为什么重要 / 用在哪里

机器人 90% 的 bug 都不是算法错，而是数据没传到、传错类型、或者两端 QoS 不匹配。通信机制是排查一切问题的入口。

  • 架构选型：选错通信方式，后面会出现「按了没反应」「界面卡死」等一堆体验问题
  • 性能：高频传感器数据用话题 + best_effort，比服务轮询省资源得多
  • 排障：ros2 topic hz / info -v / echo 是定位「数据到没到」的三板斧
  • 面试：话题/服务/动作的区别、QoS 的三种策略几乎必问

中英对照 + 一句话解释

话题Topic
带名字的广播频道，发布者发、订阅者收，多对多，不阻塞。
发布者 / 订阅者Publisher / Subscriber
往话题写数据的节点叫发布者，从话题读数据的叫订阅者。
服务Service
一问一答的同步调用，客户端发请求，服务端回响应，一个服务只有一个服务端。
动作Action
为长任务设计：先发 goal，过程中有 feedback，结束给 result，还能中途 cancel。
参数Parameter
节点的配置项，有名字和类型，可以在启动时或运行时修改。
QoSQuality of Service
服务质量策略：可靠性、持久性、队列深度等，决定消息怎么丢、怎么留。
DDSData Distribution Service
ROS 2 底层的通信中间件标准，负责自动发现节点并传输数据。
队列深度Depth
缓存多少条没来得及处理的消息，超出后按策略丢最旧的或最新的。

#先分清四种通信方式

选通信方式只看两件事：要不要「回应」，以及任务「长不长」。不需要回应、持续发 → 话题；需要回应且很快 → 服务；需要回应但很久、还想看进度 → 动作；只是改配置 → 参数。

四种通信方式对比
维度话题 Topic服务 Service动作 Action参数 Parameter
通信模型多对多广播一对一问答一对一带进度读写配置
调用是否阻塞不阻塞阻塞等响应异步，可查进度/取消阻塞
有无反馈无只有最终响应有 feedback + result无
典型场景激光、图像、速度指令查询模式、清空地图导航到点、机械臂抓取最大速度、控制频率
底层实现DDS 话题两个话题拼成（请求/响应）话题 + 服务组合服务 + 参数事件
很多人以为服务和动作是「另一种传输」，其实在 DDS 层面它们也是话题：服务 = 请求话题 + 响应话题，动作 = goal/feedback/result/cancel 四组话题的组合。

#话题：像广播电台一样发数据

话题的核心是「解耦」：发布者不知道有多少订阅者，订阅者也不知道数据从哪来。这使得系统可以随时增删模块。

每个话题有固定的消息类型。类型不一致的两个节点是连不上的——这也是「为什么我收不到消息」的第一嫌疑人。

  • 队列深度（depth）：订阅者处理不过来时缓存几条，超出按策略丢弃
  • 话题名可以用命名空间区分，例如 /robot1/scan 与 /robot2/scan
  • 高频大数据（图像、点云）优先用话题，不要用服务轮询
$ ros2 topic list -t
  • topic list列出当前所有活跃话题
  • -t同时显示每个话题的消息类型，写代码前先确认类型名
$ ros2 topic hz /turtle1/pose
  • hz测量话题的实际发布频率，用来确认「数据是不是真的在流」
  • /turtle1/pose目标话题名（必须和 list 里显示的完全一致）
$ ros2 topic info /turtle1/pose -v
  • info看这个话题有几个发布者、几个订阅者
  • -vverbose，额外打印两端的 QoS 配置，排查「收不到」的关键命令

#服务：打电话办事

服务是「请求-响应」模型，客户端发一个请求就阻塞等待（同步调用），服务端处理完返回结果。一个服务名只能挂一个服务端。

服务不适合长任务：如果服务端处理 5 秒，客户端这 5 秒就卡住了，界面会「假死」。长任务请用动作。

$ ros2 service list -t
  • service list列出所有服务
  • -t显示服务类型，例如 example_interfaces/srv/AddTwoInts
$ ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 3, b: 5}"
  • /add_two_ints服务名
  • example_interfaces/srv/AddTwoInts服务类型（包名/srv/类型名）
  • "{a: 3, b: 5}"请求内容，YAML 语法；字符串必须加引号防止被 shell 拆开

#动作：长任务 + 进度反馈 + 可取消

动作是「带外挂的服务」：它由多组话题 + 服务拼成，因此同时具备目标、反馈、结果、取消四种能力。导航到目标点、机械臂抓取、机械臂回零，标准做法都是动作。

  • goal：客户端发目标，服务端接受或拒绝
  • feedback：执行过程中持续回报进度（例如剩余距离、完成百分比）
  • result：结束时的最终结果（成功/失败/被取消）
  • cancel：客户端可以中途撤销，服务端必须响应 cancel 请求
$ ros2 action list -t
  • action list列出所有动作服务器
  • -t显示动作类型，例如 turtlesim/action/RotateAbsolute
$ ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.57}" --feedback
  • /turtle1/rotate_absolute动作名
  • turtlesim/action/RotateAbsolute动作类型（包名/action/名字）
  • "{theta: 1.57}"目标值：转到 1.57 弧度（约 90°）
  • --feedback持续打印反馈，不加就只能看到最终结果

#参数：运行时改配置

ROS 2 的参数是「节点的」而不是全局的（这点和 ROS 1 的参数服务器不同）。节点必须先声明参数，才允许被设置。

参数常用于：最大速度、控制频率、话题名、坐标系名、标定系数。调试时改参数比改代码快得多。

$ ros2 param list
  • list列出所有节点的所有已声明参数
$ ros2 param dump /turtlesim > turtlesim.yaml
  • dump把某个节点当前参数导出成 YAML，便于保存与复现
  • /turtlesim目标节点名
$ ros2 param load /turtlesim turtlesim.yaml
  • load从 YAML 批量加载参数
  • turtlesim.yaml参数文件路径

#QoS 与 DDS：消息怎么丢、怎么留

QoS（服务质量）是 ROS 2 相对 ROS 1 最重要的进步之一：同一份话题代码，可以用不同「投递承诺」发送。通信两端 QoS 不兼容时，能看到话题但收不到数据——这是 ROS 2 最经典的坑。

$ ros2 topic info /scan -v
  • /scan疑似有问题的话题
  • -v打印发布端与订阅端的 QoS；两边 reliability/durability 不一致就会收不到
常用 QoS 策略
策略常用取值含义典型搭配
Reliabilityreliable / best_effort要不要保证送达（best_effort 允许丢包）传感器用 best_effort；控制指令用 reliable
Durabilityvolatile / transient_local晚加入的订阅者能否收到历史消息地图/静态 tf 用 transient_local
DepthKEEP_LAST(n) / KEEP_ALL队列缓存几条高频数据 depth=1
Historykeep_last / keep_all缓存策略一般是 keep_last
DDS 负责「找得到彼此」：同一网络、同一 ROS_DOMAIN_ID 的节点会自动发现。所以在同一台电脑开多个仿真、或者实验室多人共用网络时，改 ROS_DOMAIN_ID 是隔离通信的标准做法。

发布 / 订阅

一个发布者、两个订阅者：看消息包如何被复制并投递，以及队列深度与丢包的关系。

第 1/5 步
解说发布者 /talker 生成一条消息，只 publish 一次，它不知道有多少订阅者。
  • 节点
  • 话题（广播）
  • 消息包

观察问题

  1. 发布者需要知道有几个订阅者吗？
  2. 订阅者 A 处理慢的时候，消息会排队还是被丢掉？
  3. 再加一个订阅者，发布者的代码需要改吗？

结论提示

话题是解耦的广播：发布者只管发，订阅者数量变化不影响发布者。每个订阅者有自己的队列，队列满后按 QoS 策略丢弃旧消息——这就是「处理慢的订阅者会丢数据」的原因。

学习示意：真实 DDS 还会做可靠传输、序列化与网络优化；这里只画逻辑关系。

交互实验

服务请求 / 响应

客户端发请求后阻塞等待；对比服务端迟迟不响应时会发生什么。

第 1/5 步
解说客户端发起请求 add(a=3, b=5)，然后进入阻塞：在响应返回前它什么都做不了。
  • 节点
  • 服务（一问一答）
  • 消息包

观察问题

  1. 请求发出后，客户端在做什么？
  2. 服务端如果 3 秒才回复，客户端界面会「卡住」吗？
  3. 为什么长任务不该用服务？

结论提示

服务是同步问答：请求发出后调用方只能等。服务端慢，调用方就卡；所以耗时任务要用动作，或者用异步调用加超时。

交互实验

动作：目标 / 反馈 / 结果

下发一个长任务目标，过程中观察反馈流，最后看结果，并演示中途取消。

第 1/5 步
解说客户端发送 goal（目标）：例如「导航到 (3.0, 2.0)」或「转动到 90 度」。
  • 节点
  • 动作（长任务）
  • 消息包

观察问题

  1. 反馈（feedback）和结果（result）有什么区别？
  2. 取消（cancel）后，服务端会立刻停止吗？
  3. 为什么导航到目标点适合用动作而不是服务？

结论提示

动作把长任务拆成「目标 → 多次反馈 → 最终结果」，并允许取消。它天生适合耗时、需要进度展示、可能要中断的任务。

交互实验

QoS / DDS 匹配

调节两端的 reliability 与 durability，观察什么时候消息「明明有却收不到」。

第 1/5 步
解说两端 QoS 都是 reliable + volatile：发布端承诺「保证送达」，订阅端要求「保证送达」，匹配成功。
  • 话题（广播）
  • 消息包
  • 规划路径
  • 障碍物

观察问题

  1. 发布端 reliable、订阅端 best_effort 能通信吗？反过来呢？
  2. durability = transient_local 的发布者，晚加入的订阅者能收到旧消息吗？
  3. depth 改成 1 与 10，订阅者补看历史消息的能力有什么变化？

结论提示

QoS 匹配是「发布端承诺 ≥ 订阅端要求」。qos 不兼容时话题能列出、但数据不会到达。传感器数据用 best_effort + depth 1 是行业默认，静态地图用 transient_local 才能让后启动的节点也拿到。

匹配规则：发布端的承诺必须能覆盖订阅端的要求。要求更高的一侧会让连接建立失败。

排障

常见错误与排查

先看现象，再想原因，最后按步骤验证

  • 🚨现象：ros2 topic list 能看到话题，echo 也有数据，但自己的订阅者一条都收不到

    原因：两端 QoS 不兼容（最常见：传感器 best_effort，订阅端默认 reliable）。

    1. ros2 topic info /话题 -v 对照两端的 reliability 与 durability
    2. 把订阅端 QoS 改成与发布端一致（或更宽松）
    3. 确认订阅的消息类型与话题类型完全一致

  • 🚨现象：服务调用报 service not available

    原因：服务端没启动，或服务名拼错，或服务端在不同 ROS_DOMAIN_ID。

    1. ros2 service list 确认服务名存在
    2. 检查两端 ROS_DOMAIN_ID 是否相同
    3. 客户端加 wait_for_service 并打印等待日志，先确认「服务在不在」

  • 🚨现象：动作目标发出后被拒绝（goal rejected）

    原因：目标值超出机器人可达范围，或动作服务端正在执行另一个目标。

    1. 检查目标是否在可达工作空间内
    2. 先取消上一个目标或等待其结束
    3. 查看动作服务端日志，确认拒绝原因（通常是参数校验）

  • 🚨现象：话题名带前导斜杠，换机器或加命名空间后就找不到

    原因：代码里写死了绝对名 /scan，命名空间重映射失效。

    1. 话题名尽量写相对名（scan），让命名空间生效
    2. 必须绝对名时，在 launch 里用 remappings 显式重映射
    3. ros2 node info 查看节点实际使用的话题名
