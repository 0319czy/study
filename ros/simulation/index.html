仿真

Simulation · Gazebo / Gazebo Sim / Sensors / Clock

一句话解释一句话解释：仿真就是先在电脑里把机器人跑一遍——用物理引擎代替真实世界，让你在没有硬件、不怕撞墙的情况下验证算法。

学习目标

学完这页你应该能做到

  • ✓能说清仿真闭环里有哪些环节，以及各自对应什么话题
  • ✓知道 Gazebo Classic 与新版 Gazebo（Gazebo Sim）的关系与命名差异
  • ✓能解释传感器插件的作用与常见配置项
  • ✓能说明为什么仿真必须统一 use_sim_time 并发布 /clock
  • ✓能列出仿真与真机的差异（差距在哪、要注意什么）

🧩生活化比喻 · 飞行模拟器

飞行员先在模拟器里练，因为坠机不要钱。机器人也一样：算法先在 Gazebo 里跑通，再去真机上验证。区别是模拟器里的物理是算出来的，所以「仿真能过」不等于「真机能过」。

  • 虚拟世界：world 文件定义地面、光照、障碍物
  • 虚拟机器人：URDF/SDF 模型 + 传感器插件
  • 虚拟时间：/clock 让所有节点按仿真时间走

🎯为什么重要 / 用在哪里

没有仿真，调一次导航要搬一次机器人；有仿真，一晚上能跑几百次实验。

  • 零成本试错：撞墙、翻车、撞人都不心疼
  • 可复现：同样的 world、同样的随机种子，结果可复现
  • 并行：一台服务器同时跑多个仿真实例（用不同 ROS_DOMAIN_ID 隔离）
  • CI 里跑冒烟测试：每次提交都验证「导航能到达目标点」

#两个 Gazebo：先搞清楚你装的是哪个

这是 ROS 2 学习者最容易迷路的地方：网上教程一半讲 Gazebo Classic，一半讲新版 Gazebo，包名、启动命令、插件名都不一样。先确认自己环境里装的是哪个，再照对应教程做。

两代 Gazebo 的差异（以 Humble 时期常见组合为例）
维度Gazebo Classic新版 Gazebo（Gazebo Sim）
典型版本11.xFortress / Garden / Harmonic 等发行版
启动方式gazebo 或 ros2 launch gazebo_ros ...gz sim 或 ros2 launch ros_gz_sim ...
ROS 集成包gazebo_ros / gazebo_ros_pkgsros_gz_sim / ros_gz_bridge
模型格式URDF 或 SDF以 SDF 为主，URDF 可转换
传感器插件libgazebo_ros_ray_sensor.so 等gz-sim 传感器系统 + 桥接
注意：Humble 官方支持的是 Gazebo Classic 11；新版 Gazebo 的 ROS 集成在不同发行版之间改过包名（ros_ign_* 改为 ros_gz_*）。用哪套就以你系统里 ros2 pkg list 实际存在的包为准，别照抄网上不同版本的命令。

#仿真闭环：数据怎么转一圈

一次「让机器人走起来」的仿真闭环包含五个环节，缺一个就动不了。

  • 控制器节点算出速度指令，发布 /cmd_vel
  • 差速驱动插件订阅 /cmd_vel，把速度变成轮子转速
  • 物理引擎积分出新的位姿，发布 /odom 与 TF
  • 传感器插件按物理结果生成 /scan、/camera 数据
  • 算法节点（SLAM、Nav2）消费这些数据，再产生新的 /cmd_vel
真机上 /odom 来自编码器，仿真里来自插件计算。所以「仿真里里程计很准、真机上漂移严重」是正常的——仿真默认不会给你加噪声与打滑。

#传感器插件：把物理世界变成消息

插件是 Gazebo 与 ROS 的接口：它挂在模型或传感器上，仿真每推进一步就调用一次，把结果转成 ROS 消息发布出去。

#桥接与时间：两个必须配对的开关

新版 Gazebo 的原生消息不是 ROS 消息，需要 ros_gz_bridge 做双向转换；同时仿真器要发布 /clock，节点要设 use_sim_time，两边时间才一致。

$ ros2 run ros_gz_bridge parameter_bridge /cmd_vel@geometry_msgs/msg/Twist@gz.msgs.Twist
  • parameter_bridge桥接节点，按「话题@ROS类型@gz类型」的格式声明要转的话题
  • /cmd_vel要桥接的话题名
  • geometry_msgs/msg/TwistROS 2 侧的消息类型
  • gz.msgs.TwistGazebo 侧的消息类型；用 @ 分隔，方向由两边类型决定
$ ros2 param set /my_node use_sim_time true
  • use_sim_time让节点使用 /clock 的仿真时间，而不是系统时间
  • true布尔值；也可以在 launch 里作为参数传入，更推荐
忘了开 use_sim_time，就会出现「TF 查不到、定时器疯狂触发、bag 回放全乱」的连锁问题。仿真与回放场景一定要第一时间检查它。

#仿真能过，真机不一定能过

仿真里没有打滑、没有电池电压下降、没有轮胎磨损、没有传感器噪声与延迟。把仿真当「第一道关」，真机当「最终验证」，不要反过来。

  • 给仿真加噪声：激光距离噪声、里程计打滑、相机曝光
  • 给通信加延迟：仿真默认是理想网络，真机 Wi-Fi 会丢包
  • 限速：仿真里撞墙没事，真机会坏
  • 保留真机测试清单：急停、限速、看门狗、人工干预通道

结论提示

仿真闭环 = 算法 → 指令 → 物理引擎 → 传感器数据 → 算法。物理引擎是核心，插件是接口，/clock 是时间基准。三者缺一，闭环就跑不起来。

学习示意：真实仿真还包含求解器步长、碰撞响应、物理材质与渲染，这里只表达数据闭环。

排障

常见错误与排查

先看现象，再想原因，最后按步骤验证

  • 🚨现象：仿真启动了，但机器人不动

    原因：没有 /cmd_vel 订阅者（驱动力学插件没加载），或话题名不匹配。

    1. ros2 topic list 看 /cmd_vel 有没有订阅者（info -v）
    2. 确认驱动插件加载在正确的模型上
    3. 检查控制器发布的话题名与插件订阅的是否一致

  • 🚨现象：RViz2 里传感器数据时间是 0 或一直不更新

    原因：没开 use_sim_time，或 /clock 没发布。

    1. ros2 topic echo /clock 确认有数据
    2. 给所有节点设置 use_sim_time 为 true
    3. 检查仿真器是否因为性能问题暂停（暂停时不发 /clock）

  • 🚨现象：新版 Gazebo 话题一个都没有

    原因：忘了启动 ros_gz_bridge，Gazebo 原生话题不会自动变成 ROS 话题。

    1. 启动桥接节点并声明需要转换的话题
    2. gz topic -l 看 Gazebo 原生侧有没有数据
    3. 确认两边的消息类型匹配

  • 🚨现象：仿真卡顿、CPU 占用极高

    原因：物理步长太小、渲染太重、世界模型太多。

    1. 降低 update_rate 与物理步长精度
    2. 关闭不必要的可视化（headless 模式）
    3. 减少光照与阴影，或改用更简单的碰撞体
