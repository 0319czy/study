调试与安全

Debugging & Safety · Logs / QoS / Crash / Boundaries

一句话解释一句话解释：调试是用证据把「它不工作」变成「哪一段不工作」；安全是给机器人留好边界——限速、急停、看门狗，让它在出错时不伤人、不毁机。

🧩生活化比喻 · 医院的分诊台

病人（机器人）说不舒服，医生不会立刻开刀，而是先量体温、再拍片、再验血——按顺序排除。调试也一样：先确认「活着没」，再确认「数据有没有」，再看「数据对不对」，最后才改算法。

  • 分诊 = 先用命令行看系统结构
  • 量体温 = 看话题有没有数据、频率是否正常
  • 拍片 = RViz2 看可视化的实际效果
  • 开刀 = 改代码。这是最后一步

🎯为什么重要 / 用在哪里

机器人系统复杂、耦合深，能快速定位问题的人，效率是别人的好几倍。而安全边界是「必须有」而不是「最好有」——一次失控就可能损坏硬件甚至伤人。

  • 排障效率：80% 的问题在「数据流」层就能定位，不必读算法源码
  • 可复现：日志 + bag 让问题可以交给别人复现
  • 安全合规：限速、急停、看门狗是实验室与产品的底线要求
  • 面试与工程评审：如何定位问题、如何保证安全是必问项

#排障决策树：按顺序问五个问题

不要一上来就改代码。按这个顺序走，多数问题在第二步就能定位。

  • 1. 节点活着吗？ros2 node list / ros2 lifecycle get
  • 2. 数据在流吗？ros2 topic list、ros2 topic hz、ros2 topic echo
  • 3. 数据被谁收？ros2 topic info -v、rqt_graph
  • 4. 数据对不对？RViz2 可视化、时间戳、坐标系
  • 5. 算法逻辑对吗？日志、单步调试、bag 回放复现
每一步都要拿到「证据」（命令输出），而不是靠猜。改代码前先能复现问题，否则改完也不知道有没有修好。

#日志：让程序自己说清楚

ROS 2 的日志有级别、有时间戳、有节点名。用对级别，才能在几十个节点的输出里找到关键信息。

$ ros2 run my_pkg my_node --ros-args --log-level debug
  • --ros-args后面的参数交给 ROS 参数系统解析，而不是节点自己的 argv
  • --log-level debug把该节点日志级别调到 DEBUG，看到更详细的过程
$ ros2 run my_pkg my_node --ros-args --log-level warn
  • --log-level warn只输出 WARN 及以上，减少刷屏，现场调试常用

#QoS 不匹配：最经典的「明明有却收不到」

现象很迷惑：ros2 topic echo 能看到数据，rqt_graph 也显示连着，但你的订阅者回调一次都不触发。八成是 QoS 不兼容。

$ ros2 topic info /scan -v
  • -v打印发布者与订阅者的 QoS 配置，逐项对比 reliability 与 durability
匹配规则速记
发布端订阅端能否通信
reliablereliable能
reliablebest_effort能（订阅端要求更低，允许）
best_effortreliable不能（订阅端要求更高，无法满足）
volatiletransient_local不能（订阅端要历史，发布端不保留）
transient_localvolatile能（订阅端只要最新）
传感器类话题的行业默认是 best_effort + KEEP_LAST(1)。写订阅者时若用了默认 QoS（reliable），就会接不上激光/相机驱动。

#节点崩溃：留下证据再重启

「重启一下就好了」是最坏的习惯——问题会再次出现，而且你什么也没学到。崩溃时先收集证据。

  • 先看日志里最后一条输出，定位是哪个回调/哪一步崩的
  • 用 gdb 的 bt（backtrace）看调用栈，比读代码猜快得多
  • 能复现的话，录一段 bag，离线反复触发
  • 检查是否内存越界、空指针、以及回调里访问了已释放对象
$ ros2 run --prefix "gdb -ex run --args" my_pkg my_node
  • --prefix用指定命令包裹节点启动，这里用 gdb 包住，崩溃时直接停在栈上
  • gdb -ex run --args让 gdb 启动程序；崩溃后可用 bt 查看调用栈
$ ulimit -c unlimited
  • ulimit -c unlimited允许生成 core dump 文件（需要当前 shell 支持，且系统未禁用）
如果崩溃发生在 rclcpp 内部而不是你的回调里，多半是「对象生命周期」问题：node、publisher 被提前析构，而回调还在用。

#时间与 TF：两个隐蔽的坑

仿真、回放、跨机器运行时，时间不一致会导致 TF 查询失败、定时器乱触发。这类问题不会报「时间错了」，只会报「查不到变换」。

  • 回放/仿真：确认 /clock 有数据，节点 use_sim_time 为 true
  • TF 查询：用数据时间戳而不是 now()
  • 多机：确认各机器时钟同步（NTP），否则 TF 缓存对不上
  • TF 断链：view_frames 看树是否连通、是否重复父节点
$ ros2 topic echo /clock --once
  • /clock仿真时间源；没有输出说明仿真器没启动或未发布时钟
$ ros2 run tf2_ros tf2_monitor
  • 无参数看每条 TF 边的频率与延迟，快速发现「谁没在发」

#安全边界：写进设计，而不是靠运气

学习环境可以大胆试，真机必须设边界。以下每一条都对应一类真实事故。

  • 限速：控制器里设 max_vel_x / max_vel_theta，并在底盘固件里再做一次硬限幅（双保险）
  • 急停：物理急停按钮 + 软件急停话题（例如 /estop），任何一层触发都要立刻停
  • 看门狗：底盘超过 300ms 没收到新指令就自动停车，防止上层卡死
  • 域隔离：真机与仿真用不同 ROS_DOMAIN_ID，避免测试指令打到真机上
  • 权限最小化：SROS2 证书只给需要的节点；凭据与密钥不进 git
  • 通信边界：不要直接开放 DDS 到公网；跨网段用受控桥接
  • 代码边界：不要让脚本默认执行运动指令，运动命令必须有显式的启动参数
  • 电池与温度监控：电压过低自动减速、返航或停车
教学示例中的「发一条 /cmd_vel」在真机上意味着轮子真的会转。任何让机器人运动的命令，都应该在仿真或支起轮子的情况下先验证。

QoS 不匹配排查

模拟一对「话题在、数据不到」的发布订阅，通过调整两端 QoS 让数据重新流动。

第 1/5 步
解说两端 QoS 都是 reliable + volatile：发布端承诺「保证送达」，订阅端要求「保证送达」，匹配成功。
  • 话题（广播）
  • 消息包
  • 规划路径
  • 障碍物

观察问题

  1. 哪一种组合会让数据完全不通？
  2. durability 设为 transient_local 后，晚启动的订阅者能收到历史消息吗？
  3. 为什么传感器数据推荐 depth 为 1？

结论提示

QoS 匹配是「发布端承诺要覆盖订阅端要求」。排查口诀：先 topic info -v 看两端，再改订阅端向发布端靠拢（要求放低），传感器场景统一 best_effort + depth 1。

匹配规则：发布端的承诺必须能覆盖订阅端的要求。要求更高的一侧会让连接建立失败。

排障

常见错误与排查

先看现象，再想原因，最后按步骤验证

  • 🚨现象：所有节点都起来了，机器人就是不动，也没有报错

    原因：指令没到（QoS/话题名不匹配），或底盘处于未使能/急停状态。

    1. ros2 topic info /cmd_vel -v 看订阅者是否存在且 QoS 匹配
    2. ros2 topic echo /cmd_vel 确认上层真的在发
    3. 检查底盘使能状态与急停开关（硬件层面）

  • 🚨现象：节点反复崩溃，日志只有几行就没了

    原因：段错误（空指针/越界/生命周期问题）或内存耗尽。

    1. 用 gdb --prefix 启动，崩溃后 bt 看栈
    2. 检查回调里访问的对象是否已被释放
    3. 留意是否在回调中做大数组分配导致 OOM

  • 🚨现象：仿真里正常，真机上定时器频率忽快忽慢

    原因：没开 use_sim_time 导致回放时时间异常，或真机 CPU 负载过高。

    1. 确认 use_sim_time 设置正确
    2. 检查是否有高频日志或大消息拖慢主线程
    3. 把耗时任务移出回调，或用多线程 executor 并明确回调组

  • 🚨现象：两台电脑上的节点互相看不到

    原因：ROS_DOMAIN_ID 不同，或网络/防火墙阻断了 DDS 的多播与端口。

    1. echo $ROS_DOMAIN_ID 对比两端
    2. 确认在同一网段且多播可用（必要时配置 DDS 的 discovery 参数）
    3. ros2 doctor 检查网络与配置
